# Research: Record and Playback Paths with a Modeled Memory (feature 006)

Decisions for feature 006. They build on [spec 001's research](../001-pipeline-skeleton/research.md) (R-05 sanitizing and narrowing, R-08/R-09 the rate converters, R-10 latency), [spec 003's](../003-vas/research.md) (R-05/R-06 the emission rule and event positions) and [spec 005's](../005-limiter-agc/research.md) (R-01 the limiter at the host rate). Figures below were derived on 2026-10-11 from the committed code (`rate.rs`, `voiceband_coeffs.rs`, `pipeline.rs`) and are pinned by unit tests at implementation; the hardware review's probe figures (B1) are re-measured by `narrowing_delta` (R-02).

## R-01 Restructuring: shared halves, three path instances (FR-001, FR-002, FR-007, FR-009)

- **Decision**: `pipeline.rs`'s `DeviceChain` splits into two types in a new `paths.rs`:
  - `RecordHalf { record: RecordStage, run_record, clamp: ClampStage, vas: VasStage, run_vas, mute }` with `process(d: f64) -> RecordOut`, where `RecordOut::Keep(f32) | Resume(f32) | Drop` and the `f32` is the **narrowed** post-VAS sample (`narrow_device`, R-02; a muted sample is `Keep(0.0)` after the region's first, which is `Resume`-less as today: mute mode reports its region through the counters exactly as spec 003 R-09, with the sample +0.0).
  - `PlaybackHalf { playback: PlaybackStage, run_playback }` with `process(d: f32) -> f64` (`f64::from(d)` then stage 10 if it runs).
  - `RecordPath { limiter, run_limiter, down: Option<PolyphaseDown>, half: RecordHalf, counters: EventCounters }` with `push(x: f32) -> Option<RecordOut>` (one host sample in; at most one device outcome out) and `PlaybackPath { half: PlaybackHalf, up: Option<PolyphaseUp> }` with `push_device(d: f32)` and `try_next_host() -> Option<f32>` (at the identity rate `push_device` stores one pending sample and `try_next_host` returns it once).
  - The **one-pass** `tick(x)` becomes: `if tap_after_agc { limiter only }`; else `if let Some(out) = self.one_pass.rec.push(x) { if let Some(kept) = counters.record(out) { self.one_pass.play.push_device(kept) } }; self.one_pass.play.try_next_host().map(narrow_out)`. The tap flags live in the halves' `run_*` fields as today (`run_vas` false at taps before the VAS; `run_playback` false at taps before stage 10).
  - `Pipeline` holds three instances: `one_pass: (RecordPath, PlaybackPath)` (the existing stream, own state), `recorder: RecordPath` and `player: PlaybackPath` (the split paths, reset at every start, FR-004). The recorder's and player's halves ignore the tap (clarify Q5): `RecordHalf::new(settings, honour_tap: false)`.
- **Why bit-identity follows**: the one-pass and record-then-play run the same stage objects' code in the same order on the same sequence of device samples; the only state that could differ is the converters', which are fresh at a recording's start just as at a one-pass stream's start; and the playback path consumes exactly the stored device samples the one-pass's interpolator consumed. Spec 003 R-05's emission rule (`try_next_host` emits once `written > latest`) makes the emitted values independent of when the host asks, so the device-driven playback produces the same host samples as the host-driven one-pass (R-06 settles the counts).
- **Events in the record path**: the recorder's `EventCounters` is constructed with `l = m = 1`, so positions and lengths are in the recording's device samples from its start (FR-006), while the one-pass keeps the host-rate positions of spec 003.
- **Alternatives**: one shared set of instances (rejected: Complexity Tracking row 1); keeping `DeviceChain` whole and building the player as "a chain with everything but stage 10 bypassed" (rejected: it would run the VAS's bookkeeping on playback and could not take an `f32` store as input without a second narrowing point).

## R-02 The narrowing point and the measured delta (FR-009; hardware review B1)

- **Decision**: `paths::narrow_device(d: f64) -> f32 = sanitize::narrow_out(d)` (round to nearest, subnormals to 0.0, saturation at ±`f32::MAX`) applied to every kept post-VAS sample, in the one-pass and in the recorder alike, for every tap but `AfterAgc` (which never reaches the device chain). The store holds the `f32`; the playback half widens with `f64::from`, which is exact. With the clamp on the sample is within ±1.0 so saturation never acts. With everything bypassed the record path's output is the sanitized input at the identity rate only: the `bypass_all` entries at **6 kHz** are expected unchanged (no arithmetic before the narrowing), while at the six converting rates the decimator's 64-bit output is what gets rounded, so those entries may change like any other; the `agc_only` entries never reach the device chain and are unchanged at every rate. The test confirms rather than assumes.
- **Physical defence** (not a claim of fidelity): at this point the device has an 8-bit µ-law code (A-003, verified); 24-bit mantissa rounding is 16 bits finer than the device. The CHANGELOG says "inaudible, recorded because output changes".
- **Measurement**: a `__test-hooks` constructor `Pipeline::__with_device_narrowing(settings, enabled: bool)` keeps the un-narrowed path. The flag and its per-sample branch exist only under `cfg(feature = "__test-hooks")` (the harness always builds with it); the shipped build has no branch and no flag. The hook stays, so the delta remains measurable after later changes (Complexity Tracking row 6). `tests/narrowing_delta.rs` runs every golden stimulus through both at the seven rates and reports, per file, the share of differing samples and the maximum |Δ| in output LSBs; it asserts max |Δ| ≤ 2 output LSBs (one input LSB through stage 10's gain ≤ 1.0 plus the interpolator's ≤ 1.0 passband gain and a second rounding; engineering target) and prints the figures the CHANGELOG quotes. The review's probe: 34.8 % of samples differ, max 2.98e-8 at 6 kHz on the default configuration; the committed figures are whatever the test prints at the re-bless.
- **Procedure**: one commit `feat!: narrow the device-rate stream after the VAS to f32 (spec 006 FR-009)` containing the narrowing **in the existing `DeviceChain`** (the point where `DeviceOut::Keep`/`Resume`/`Mute` carry the post-VAS sample on toward stage 10), the hook, `narrowing_delta.rs`, the three re-blessed files with their SHA guards, and the CHANGELOG entry. Nothing else in it: no refactor. After it, any golden difference inside the feature is a defect (R-09), and the halves refactor (R-01) is proven by the unchanged SHA guards.
- **Alternatives**: narrowing at the interpolator's output only (no: the store would still hold 64-bit values); storing 64-bit (rejected by the user); a 1-LSB tolerance (rejected: Complexity Tracking row 2).

## R-03 The memory: a reserved store, a span table, time accounting (FR-010 – FR-013, FR-017, SC-007; A-038, A-039)

- **Decision**: `memory.rs`:
  - `Memory { store: Vec<f32>, spans: Vec<Span>, capacity_samples: usize, max_recordings: usize }` with `Span { start: usize, len: usize }`. Construction: `Vec::new()` then `try_reserve_exact(capacity_samples)` and `try_reserve_exact(max_recordings + 1)` (the extra span is the recording in progress); failure returns `Error::AllocationFailed` instead of aborting (`alloc::vec::Vec::try_reserve_exact` is available on 1.85 in `no_std` + `alloc`). The reservation is virtual on every supported platform until pages are written, so the idle footprint is small while the reported reservation is `capacity_samples × 4 + (max_recordings + 1) × size_of::<Span>()` bytes (`footprint_bytes()`, SC-007: 86 400 000 + 1 600 = 86.4 MB at the defaults; the README states 86 MB).
  - **Capacity**: `capacity_samples = capacity_s × 6000` (A-026; A-038: time counted in stored device samples). `used = store.len()` (the recording in progress included), `remaining = capacity − used`, `count = spans.len()` minus the in-progress one, `slots_remaining = max_recordings − count`.
  - **Append** (record path, per block): `push` within capacity never reallocates; the transport stops the recording at the exact sample where `store.len() == capacity` (FR-012) and reports `StopReason::MemoryFull`.
  - **Close**: the in-progress span becomes recording `count + 1`, or is discarded if no input was fed (FR-012, A-039: `fed_any == false`; the flush is skipped, so `len == 0` and nothing to truncate).
  - **Erase(n)** (FR-013): `store.drain(span.start .. span.start + span.len)` (a memmove of what follows, bounded by the store's size, no allocation), remove the span, subtract `len` from the later spans' starts (renumbering is implicit: the index is the number minus one). **Erase all**: `store.clear()`, `spans.clear()`. Both keep the capacity.
  - **Import** (FR-014): after validation (R-04), `store.extend_from_slice` within capacity, push a span.
  - **`Clone`**: manual, so the clone reserves the same capacity (`Vec::clone` would allocate only `len`, and a cloned pipeline would then grow, violating SC-007 and FR-017).
  - **`reconfigure`** (FR-019): allowed only when idle; builds the new paths; if `new.capacity_samples ≥ store.len()` and `new.max_recordings ≥ spans.len()` the store is kept when the capacity is unchanged, else a new `Vec` is reserved (`try_reserve_exact`) and the data copied; otherwise `Error::StoredExceedsCapacity`. **`reset`**: resets the three path instances and the transport to idle; the memory is untouched.
- **Ranges** (`validate.rs`): `capacity_s` 1 ..= 86 400 (one second to 24 hours; above the device's 3 600 the documentation says "not the device's"; engineering target), `max_recordings` 1 ..= 9 999 (engineering target). A zero or out-of-range value is `Error::InvalidSetting { Setting::MemoryCapacityS | MemoryMaxRecordings }`, which is the spec's "capacity too small" refusal (Key Entities).
- **Alternatives**: `vec![0.0; capacity]` (rejected: 86 MB of pages committed and written at construction, 20 ms, for nothing); per-recording `Vec`s (rejected: allocation at start, fragmentation, and `erase` would free memory that `start` must then reacquire); a ring or arena with free lists (rejected: no use case for in-place reuse that `drain` does not cover at this size).

## R-04 The exported byte form and the CRC (FR-014; contracts/recording-form.md)

- **Decision**: version 1 of the form is a 32-byte little-endian header, the samples, and a trailing CRC-32:

  | Offset | Size | Field | Value |
  |---|---|---|---|
  | 0 | 8 | magic | `"RRDR60RC"` (ASCII, no terminator) |
  | 8 | 2 | form version | 1 |
  | 10 | 2 | flags | 0 (reserved; an importer rejects non-zero as unsupported) |
  | 12 | 4 | device rate, Hz | 6000 (A-026) |
  | 16 | 2 + 2 + 2 | library version major, minor, patch | the exporting engine's (informational) |
  | 22 | 2 | reserved | 0 |
  | 24 | 8 | sample count K | ≥ 1 |
  | 32 | 4·K | samples | `f32` little-endian bit patterns |
  | 32 + 4·K | 4 | CRC-32 | IEEE 802.3 polynomial (0xEDB88320 reflected), init 0xFFFFFFFF, final xor, over bytes 0 .. 32 + 4·K |

  `export_len(n) = 36 + 4·K`. **Validation order on import** (each a distinct refusal): length < 8 or magic mismatch → `UnknownForm`; version ≠ 1 or flags ≠ 0 → `UnsupportedFormVersion { version }`; length ≠ 36 + 4·K, device rate ≠ 6000, K = 0, CRC mismatch, or any sample whose bit pattern is NaN, ±Inf or subnormal → `Damaged`; K > remaining samples or no slot → `DoesNotFit`. Only then is the memory touched. "Within the record path's output range" (FR-014) is defined as finite and non-subnormal: with every stage bypassed the record path's output is the sanitized input, which is any normal `f32`, so no magnitude bound is honest (the data model says so; a later encoded form can tighten it).
- **CRC-32**: a `const fn`-built 256-entry table (1 KB, `static`) and a byte loop in `form.rs`; about 20 lines, no dependency, bit-reproducible. Cost ≈ 0.6 ns/byte: 50 ms for a full 86 MB store, bounded, in a call that is not real-time (FR-017).
- **Why a trailing CRC and a leading count**: the host can size its buffer from `export_len` before exporting; the CRC detects every single-byte alteration and every truncation (the length check does too); a forged sequence with a valid CRC is caught by the finite/non-subnormal scan (review B10). A later version 2 (encoded frames, after A-004) changes the version field and keeps the header; an engine of this feature refuses it as `UnsupportedFormVersion` (US3 scenario 5).
- **Alternatives**: a text or JSON container (rejected: `no_std`, and no need); SHA-256 (rejected: a dependency in the core, and integrity against accident is the goal, not against tampering); storing the host rate (rejected: the recording is device-rate by construction).

## R-05 The transport: states, calls, refusals, C mapping (FR-003 – FR-006, FR-008, FR-013, FR-015, FR-019, FR-020)

- **Decision**: `transport.rs` holds `State { Idle, Recording, Playing }`, `Route { Speaker, Earphone }` (`#[non_exhaustive]`, default `Speaker`), and the public calls on `Pipeline` (contracts/rust-api.md). Transitions: `start_recording` (Idle → Recording; refuses `RecordingInProgress`, `PlaybackInProgress`, `MemoryFull`, `NoRecordingSlots`; resets the recorder; opens the in-progress span), `record` (Recording only, else `NotRecording`), `stop_recording` (Recording only; flush unless nothing was fed; close or discard; → Idle), `start_playback(n)` (Idle → Playing; refuses `NoSuchRecording { number }` when `n == 0 || n > count`, and the two in-progress reasons; resets the player; positions at the span), `play` (Playing only, else `NotPlaying`; at the drain's end → Idle and `finished = true`), `stop_playback` (Playing only, else `NotPlaying`; → Idle, no drain), `erase(n)` and `erase_all` (refuse `RecordingInProgress`; while playing the played recording or all: stop playback first, then erase; another recording: erase and, if its number is below the played one, decrement the player's current number), `import` (refuses `RecordingInProgress`; allowed while playing since it only appends), `export` and `export_len` (always allowed), `set_route`/`route` (always; stored on the pipeline, survives reset and reconfigure), `state() -> EngineState { state, route, current: Option<u32>, speaker_muted: bool }` with `speaker_muted = state == Recording` (FR-003), the one-pass calls (refuse `RecordingInProgress` / `PlaybackInProgress` with the pipeline unchanged).
- **Reports**: `RecordInfo { stored: usize, events: usize, paused: bool, stopped: Option<StopReason> }` (`StopReason::MemoryFull`, `#[non_exhaustive]`); `stop_recording -> StopOutcome { flush: RecordInfo, result: StopResult }` with `StopResult::Kept { number: u32, length: u64 } | DiscardedEmpty`; `PlayInfo { produced: usize, finished: bool }`; `MemoryStatus { capacity_samples, used_samples, remaining_samples, max_recordings, count, slots_remaining }` (all `u64`/`u32`, device samples; seconds derived by the caller as samples ÷ 6000, or by the `*_seconds()` helpers that divide in `f64`).
- **Errors** (`Error`, `#[non_exhaustive]`, fourteen new): `RecordingInProgress`, `PlaybackInProgress`, `NotRecording`, `NotPlaying`, `MemoryFull`, `NoRecordingSlots`, `NoSuchRecording { number }`, `DoesNotFit`, `UnknownForm`, `UnsupportedFormVersion { version }`, `Damaged`, `StoredExceedsCapacity`, `AllocationFailed`, and `BufferTooSmall { needed }` for `export` into a short buffer. The spec's "capacity too small" is the existing `InvalidSetting` naming `MemoryCapacityS` or `MemoryMaxRecordings`, not a new variant. C statuses 6–19 in that order (contracts/c-api.md); `error_to_status_and_field` maps each; the `_ => InvalidArgument` arm stays for future variants.
- **Why `Pipeline` and not a separate `Memory` handle**: the spec's state model is one engine with one state; the C API has one opaque pointer; the one-pass refusal while recording needs the same object. A `Memory` type exists internally and could be exposed later without breaking this.
- **Alternatives**: a `Recorder`/`Player` pair of public types borrowing the memory (rejected: lifetimes across the C boundary, and two handles that must agree on state); callbacks for "finished" or "stopped" (rejected: Principle IV, no callbacks in the core).

## R-06 Sample counting: flush, playback length, drain, latencies (FR-005, FR-007, FR-008, FR-016, SC-008)

- **Converter facts** (`rate.rs`, `up.rs`, `down.rs`): host sample n sits at prototype time n·l, device sample k at k·m. The decimator emits device sample k at host step ⌊k·m/l⌋; the interpolator emits host sample n once device sample ⌊n·l/m⌋ has been written (`try_next_host`). Each converter's linear-phase delay is D host samples, `delay_host` in the plan; the prototype spans 2D host samples. Per rate:

  | Host rate | l/m | prototype taps | D (host samples) |
  |---|---|---|---|
  | 6 000 | identity | — | 0 |
  | 8 000 | 3/4 | 241 | 40 |
  | 16 000 | 3/8 | 481 | 80 |
  | 44 100 | 20/147 | 8 761 | 219 |
  | 48 000 | 1/8 | 477 | 238 |
  | 88 200 | 10/147 | 8 741 | 437 |
  | 96 000 | 1/16 | 953 | 476 |

- **Stage figures** (`voiceband_coeffs.rs`, computed 2026-10-11, pinned by unit tests): group delay at 1 kHz τ_rec = 0.5387 and τ_play = 0.3133 device samples; impulse-response peaks 0.570 (stage 4) and 0.631 (stage 10); **N₁₀ = 121**: the first device sample after which stage 10's impulse response stays below 10⁻⁵ of its own peak (−100 dB relative; 95 at −80 dB, 146 at −120 dB). The review's 112 used a different reference; FR-008's text is amended to 121. A unit test computes N₁₀ from `PLAYBACK_SOS` and asserts it equals the constant, so a coefficient change cannot silently invalidate the drain.
- **Latencies in host samples, each rounded once** (FR-016; review B4): `record = round(D + τ_rec · host/6000)`, `playback = round(D + τ_play · host/6000)`, one-pass as 001 R-10 `round(2D + (τ_rec + τ_play) · host/6000)`. A bypassed stage contributes 0. Default configuration:

  | Host rate | record | playback | sum | one-pass (committed table) |
  |---|---|---|---|---|
  | 6 000 | 1 | 0 | 1 | 1 |
  | 8 000 | 41 | 40 | 81 | 81 |
  | 16 000 | 81 | 81 | 162 | 162 |
  | 44 100 | 223 | 221 | 444 | 444 |
  | 48 000 | 242 | 241 | 483 | 483 |
  | 88 200 | 445 | 442 | 887 | 887 |
  | 96 000 | 485 | 481 | 966 | 966 |

  The sum equals the one-pass figure at every rate (SC-008's "within one host sample" has margin). The harness measures the playback onset against the reported figure (±1).
- **Stop flush** (FR-005): `stop_recording` pushes `record_latency` host zeros through the recorder (limiter, decimator, half), storing what comes out and reporting it as a block; skipped when `fed_any` is false (B5). Then the span closes.
- **Playback length before the drain** (FR-007; review B3): the player pushes stored samples into the interpolator and calls `try_next_host` after each push until it returns `None`; for K stored samples this yields exactly **⌈K·m/l⌉** host samples at every rate (host sample n is emitted while ⌊n·l/m⌋ < K). The one-pass over the same input followed by `record_latency + ⌈m/l⌉` host zeros produces at least that many samples (R-01's argument plus B3's bound), so the prefix rule in FR-007 is testable: the harness compares the first ⌈K·m/l⌉ samples. At the identity rate the player emits one sample per stored sample.
- **Per-block playback**: `play(output)` loops: `if let Some(y) = up.try_next_host() { write } else { pull the next stored (or drain) device sample through the half into up }` until `output` is full or the drain is complete; bounded work per output sample (at most one device sample per host sample since host ≥ 6 kHz, and at most ⌈m/l⌉ host samples per device sample). The identity rate pulls one stored sample per output sample.
- **Drain** (FR-008; review B2): after the K-th stored sample, the player keeps pulling device-rate zeros through the playback half and the interpolator until it has emitted **`drain_len = ⌈N₁₀·m/l⌉ + 2D`** host samples past the ⌈K·m/l⌉-th; then `finished = true` and the state returns to idle. With stage 10 bypassed N₁₀ is 0 (the drain is the interpolator's 2D alone; 0 at the identity rate). `drain_len` is readable before playback starts (`drain_samples()`). Default configuration: 121 / 242 / 483 / 1 328 / 1 444 / 2 653 / 2 888 host samples at the seven rates (20.2 ms at 6 kHz, 30.1–30.2 ms elsewhere). The harness check: a 0 dBFS 1 kHz tone recorded with the VAS bypassed and stopped on a positive peak; the last 1 ms of the drain below −80 dBFS at every rate (engineering target; the interpolator's response to the last non-zero device sample has ended by 2D, and stage 10's tail is 100 dB down).
- **Cross-rate check** (US1 scenario 5; review B9): a −20 dBFS 1 kHz tone, 5 s, VAS bypassed, recorded at 48 kHz, played at 44.1 kHz (the engine reconfigured between, which keeps the memory) against the one-pass at 44.1 kHz; level and frequency by a least-squares sinusoid fit over the last second (`analysis::fit`), ±0.1 dB and ±0.1 Hz (expected < 0.02 dB: both decimators are flat to ±0.01 dB). No aligned phase is needed for a fit.
- **Alternatives**: a drain of one latency (rejected: B2's −20 dBFS cut); comparing the drain with the one-pass (rejected: the one-pass's record filters ring into trailing silence, so they differ by construction; spec FR-008); reporting latencies in device samples (rejected: B4's double rounding).

## R-08 Measurement harness (FR-022; SC-002 – SC-008)

`split_checks.rs`, every check a `MeasurementResult` with requirement and trace IDs, run by `split_matrix` at the seven rates and by the story tests:

- `golden_equivalence(rate)` (SC-002): for every committed golden entry at `rate` whose configuration is applicable (`golden::applicable_entries()`: the 154 at the default tap as they are; the 42 `vas_only`/`vas_mute` entries with `playback_stage_enabled = false` and the tap left at its default for the paths; the 21 `agc_only` excluded), build the stimulus, record it in blocks of 4 801 samples (a prime-ish block so block boundaries fall everywhere), stop, **play it back in the same engine** in blocks of 997 until finished (US1 must not depend on US3's import), take the first `n_samples` of the pre-drain output and compare its SHA-256 with the entry's; also compare the VAS events' positions for the VAS entries after converting the recording's device positions to host positions (⌈kept·m/l⌉, spec 003 R-06), and the `paused` flag.
- `live_equivalence(rate)` (FR-007): the harness's own stimulus set (the golden stimuli plus the speech-like pattern over a floor and a 30 s silence-then-burst) through record-then-play and through the one-pass of the input followed by `record_latency + ⌈m/l⌉` zeros; bit-identical prefix; the playback length equals ⌈K·m/l⌉ exactly; two partitions each.
- `length_rule(rate)`: K from 1 to 50 stored samples, made by recording K host samples at 6 kHz with every stage bypassed (one stored sample per input sample) into an engine that is then reconfigured to `rate` before playback (reconfigure keeps the memory, FR-019); each plays back to exactly ⌈K·m/l⌉ samples plus `drain_len`. No import involved.
- `route_identity(rate)` (FR-015): the same recording played on each route is bit-identical.
- `two_items(rate)` (FR-004, A-037): a +9 dBFS burst recorded as item 1, then a −20 dBFS tone as item 2 in the same engine; item 2's playback equals a fresh engine's one-pass of the tone (the recorder was reset at start). US1 scenario 5's first two clauses (length and bytes unchanged by the playback rate; equal to a fresh engine's import) are checked in US3's `round_trip`, not here.
- `cross_rate_tone(record_rate, play_rate)` (US1 scenario 5): as R-06, for 48 → 44.1 kHz in the story test and the full 7 × 7 grid in `split_matrix`'s release-mode `--ignored` run.
- `capacity_time(rate)`, `capacity_count(rate)`, `capacity_mute(rate)`, `erase_renumber(rate)`, `empty_discarded(rate)` (US2, SC-003): capacity 10 s and max 3 recordings; stop sample exact; reasons; figures; mute mode costs memory; numbering after erase; the empty case.
- `round_trip(rate)`, `corruption_set(rate)` (US3, SC-004): export → import into a fresh engine at each of the seven rates → identical length and playback; the set: truncation at every 4 096-byte boundary and at the last byte, a single-byte flip at each of 64 positions spread over header, payload and CRC, a foreign sequence (random bytes with a valid magic), version 2, flags 1, a NaN sample with a recomputed CRC, a subnormal sample, K = 0, an oversized import; each refused with the stated reason and the memory unchanged (status before and after).
- `state_table(rate)` (SC-005): every (state, call) pair from the spec's FR-003 and Edge Cases, the reason asserted, the state unchanged after a refusal; mirrored in `ffi_parity` with the C codes.
- `drain_level(rate)` (FR-008): the full-scale tone cut on a peak; last 1 ms of the drain ≤ −80 dBFS; `drain_len` matches the produced count exactly; `finished` only after it.
- `latency_sum(rate)` (SC-008): the two reported latencies sum to `latency_samples()` within 1; the playback onset of an impulse recording measured against `playback_latency_samples()` ±1.
- `footprint()` (SC-007): `footprint_bytes()` ≤ 90 MB at the defaults and equal to the reported reservation; unchanged after recording to the limit, erasing and importing.
- `timing` (SC-006; release, `--ignored`): ns per host sample for record + play versus the one-pass on the same 60 s stream; the ratio reported, asserted ≤ 1.25.
- **Mutation** (SC-002's teeth): a harness-side mutant that drops the first stored sample before playback, and one that flips a CRC bit before import, must each fail their check.

## R-11 Performance, memory and CI (SC-006, SC-007, 001 FR-022)

- Per host sample the split costs the one-pass's work plus an `f32` store push and pop (two memory operations) and the transport's state check per block, not per sample. Expected ratio 1.00–1.05.
- The reservation is lazy on macOS, Linux, Windows and iOS: `malloc` of 86 MB returns untouched pages, so a test suite that constructs thousands of default pipelines (the matrices) commits nothing it does not write. Each test that records to the limit at the default capacity writes 86 MB once; the US2 scenarios use a 10 s capacity (R-08) and only `footprint()` and one `capacity_time` case at 6 kHz run at the default (a 60-minute recording at 6 kHz is 21.6 M samples, about 1 s in debug through the paths; acceptable, and `--ignored` in release for the seven-rate variant).
- No CI workflow change. The coverage job gains the new unit tests (all cheap); the C smoke test gains the loop.

## R-13 Risks

- **Bit-identity surprises in the refactor**: the order in tasks is narrowing in the existing `DeviceChain` + hook + `narrowing_delta` + re-bless (one commit, nothing else) → refactor into halves, proven by the unchanged SHA guards → split. A refactor that moves a golden hash is a defect, never a re-bless.
- **`Vec::clone` capacity**: covered by the manual `Clone` and a unit test asserting `footprint_bytes()` equality after clone.
- **Windows commit charge**: an 86 MB `HeapAlloc` commits address space but not pages; the golden matrix runs on Windows already with far smaller allocations; if a Windows runner shows memory pressure, the matrices' pipelines can use a 60 s capacity through `configs`, since no 001–005 check touches the memory.
- **`try_reserve_exact` on 32-bit targets**: none supported; `capacity_samples` fits `usize` everywhere (86 400 × 6 000 = 518 M < 2³²).
- **Erase cost**: a memmove of up to 86 MB (≈ 10 ms); documented as not real-time safe; no allocation.
- **The drain's last samples are not exactly zero** (stage 10's tail continues below −100 dB; the interpolator's ring then holds those tiny values): the check is a level, not exact zeros; determinism makes it reproducible.
- **Mute mode and the flush**: the flush's zeros may extend a muted region; the region closes at stop with the samples stored (zeros), consistent with FR-011's "muted time costs memory".
- **Import while playing** appends after the played span and cannot move it; erase of a lower-numbered recording while playing moves the played span's start, so the player holds a cursor relative to the span, re-based by `erase` (unit-tested).
- **A-037 reversal**: if a capture shows carried limiter charge between items, the recorder's limiter is simply not reset at start (one line) and the equivalence rule gains a condition; no interface change.
