# Tasks: Speech Codec (CELP, 4 kbit/s)

**Input**: Design documents from `specs/008-celp-codec/`: [plan.md](plan.md) (› "Task order"), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/) (codec-design, recording-form, rust-api, c-api, golden-format), [quickstart.md](quickstart.md).

**Tests**: REQUIRED. Constitution III says tests are written first and must fail before the implementation exists. Every story phase lists its tests before its implementation tasks. The calibration (Phase 1) exists before any codec code so that the tolerances the US1 checks assert have a basis; the spec's floors (±1.5 dB, ±3 dB, 4 dB) are written first and tightened once to the calibrated figures.

**Organization**: Setup and calibration → US1 (P1, MVP: the codec in the record path, the playback path and the one-pass) → US2 (P2: frames in the memory, form version 2) → US3 (P3: manifest, registers, README) → US4 (P4: the C surface) → Records, timing, coverage, reviews, the codec golden bless last, the PR. The order follows plan.md › "Task order".

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel (different files, no dependency on an incomplete task)
- **[Story]**: the user story the task belongs to (US1 – US4)
- Paths are relative to the repository root.

## Conventions that apply to every task

- **Traceability**: cite spec 008 FR, SC and S-/A-IDs in code comments, rustdoc and test names, e.g. `// A-026: 6 kHz device rate`, `// 008 FR-003: 80 bits per 120 samples`, `// S-008 §2.16: the 17-bit codebook`, `// A-040: frame length and look-ahead (design constant, not the device's)`. Every design constant in `codec/` is commented `// design constant (008 R-02; tools/celp-design)` or `// engineering target (008 FR-0xx)`; none may be called measured.
- **The three golden files do not move** (FR-021): `golden`, `golden_agc`, `golden_vas` and their SHA guards stay green through every task; every pre-008 harness configuration sets `speech_codec_enabled = false` (T006). No task touches those JSON files. The codec's own golden is blessed once, in T063, after the post-implementation hardware review.
- **Fixed point only in `codec/`** (R-03): no `f32`/`f64` arithmetic inside the encoder or decoder beyond the input and output conversions of contracts/codec-design.md; no `rr_dr60_detmath`; every operation an explicit `saturating_*`, `wrapping_*` or `checked_*` method or a range-proven primitive; `#![deny(clippy::arithmetic_side_effects)]` on the module; ties resolve to the lowest index.
- **Terminology** (spec Clarifications): names carry `speech`, `encoder`, `decoder` or `frame`; "the codec" alone in prose means the speech codec; the PCM codec of stages 4 and 10 is always named with its stage.
- **Wording** (FR-023): every new string, rustdoc, README and CHANGELOG sentence follows the claims policy and spec 007's denylist: "modeled on a 4 kbit/s CELP-class coder of the period", never "the DR60's codec", "the same codec", "measured" (except of the harness's own figures), "closely matches" or "verified"; nothing about what recordings contain. Never weaken a denylist stem or a length rule to make a string pass.
- **Story boundaries (Principle VII)**: `us1_codec.rs` uses engines and the codec-only configuration only (no form bytes, no registers, no C); `us2_frames_memory.rs` the memory, the form and small capacities; US3 the cross-check; US4 compares C with Rust.
- **Real-time safety**: the per-block calls, start, stop and the figure reads allocate nothing (`alloc_free`); the FIFO, frame buffers and codec state are fixed-size; the store is reserved at construction or reconfigure.
- **Before ticking a task**: `cargo fmt --all -- --check`, `cargo clippy --all-targets --all-features -- -D warnings` and `cargo test --all-features` must pass (inside a story's test-first window, that story's new tests are the expected red). The MSRV gate carries `RUSTFLAGS="-D warnings"` like CI.
- **Commits**: Conventional Commits, on branch `008-celp-codec`, after each task or logical group. Merge to `main` only through a green PR, and only after the user says so.

## Implementation strategy

- **MVP = Phase 1 + US1**: the codec audible and measured in the one-pass and in record-then-play, the three goldens untouched; nothing of the form, the manifest or the C surface is needed for it.
- **Incremental**: each story closes with a commit and a coach review; the manifest and README re-bless lands with US3 (strings only); the codec golden is blessed once, last, after the post-implementation hardware review, so a table change found by that review costs no re-bless.
- **One golden file, one bless**: any later change to the frame bytes is a model change and a CHANGELOG entry (FR-021), never a quiet re-bless.
