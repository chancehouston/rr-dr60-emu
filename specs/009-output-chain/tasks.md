# Tasks: Output Chain (volume and power amplifier, speaker, earphone; stages 11–13)

**Input**: Design documents from `specs/009-output-chain/`: [plan.md](plan.md) (› "Task order"), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/) (output-chain-design, rust-api, c-api, golden-format), [quickstart.md](quickstart.md).

**Tests**: REQUIRED. Constitution III says tests are written first and must fail before the implementation exists. Every story phase lists its tests before its implementation tasks. The design script (Phase 1) exists before any chain code so that the figures the tests pin have a source the Rust never computes for itself.

**Organization**: Setup → US1 (P1, MVP: the two routes, the volume, the clipper, the templates, in the playback path and the one-pass) → US2 (P2: the whole chain, the equivalences, the controls' timing, the earlier checks) → US3 (P3: manifest, registers, README) → US4 (P4: the C surface) → Records, timing, coverage, reviews, the S-003 read, the output golden bless last, the PR. ## Conventions that apply to every task

- **Traceability**: cite spec 009 FR, SC and S-/A-IDs in code comments, rustdoc and test names, e.g. `// A-031: clip ceiling 1.15 V at the 2.8 V rail the schematic marks (S-002) (S-002, S-006)`, `// 009 FR-009: controls land at the next block`, `// A-010 (revised): speaker template, low confidence`, `// A-044: the loaded volume law`. Every constant in `stages/output_coeffs.rs` and `stages/output.rs` is commented `// design constant (009 R-02 – R-04; tools/output-chain)` or `// engineering target (009 FR-0xx)`; none may be called measured.
- **The four golden files do not move** (FR-016): `golden`, `golden_agc`, `golden_vas`, `golden_codec` and their SHA guards stay green through every task; every pre-009 harness configuration sets `output: OutputSettings::BYPASSED` and keeps `tap = Tap::AfterPlayback` where it was the default (T007). No task touches those JSON files. The chain's own golden is blessed once, in T046, after the S-003 read (T038) and the post-implementation hardware review (T043).
- **The design script is the source of every figure** (R-02 – R-04; contracts/output-chain-design.md): the Rust pins figures the script prints (`VOLUME_REFERENCE`, the −3 dB points, the template's peak and 1 kHz reading, the group delays, `N_OUT`, the knee's distortion bracket, the loaded law at six positions), never its own output; `--write` must regenerate `output_coeffs.rs` byte-identically; the harness checks the Rust against the design's discrete realization, and the script's `--check` checks that realization against the analog prototype.
- **The chain is `f64` IEEE arithmetic with no platform math function** (FR-012; R-04): the clipper is compares, multiplies and one subtraction; the loaded law is two divides per block; the sections are the biquad's arithmetic. No `libm`, no `rr_dr60_detmath` inside the per-sample path.
- **Controls at block boundaries only** (FR-009; R-01): `route` and `volume` are read once per processing call by `OutputChain::set_controls`; nothing in the per-sample path reads a control.
- **Wording** (FR-018): every new string, rustdoc, README and CHANGELOG sentence follows the claims policy and spec 007's denylist: "modeled on the circuit and the datasheet", "a template of a small speaker", never "measured" of the device, "the DR60's speaker", "accurate", "verified" or "closely matches"; nothing about what recordings contain. Never weaken a denylist stem or a length rule to make a string pass.
- **Story boundaries (Principle VII)**: `us1_output.rs` uses engines and the output-only configurations (no registers, no C); the chain equivalences in US2 use the default configurations; US3 the cross-check; US4 compares C with Rust.
- **Real-time safety**: `set_volume`, `volume`, `set_route`, the per-block calls, `play` and `start_playback` allocate nothing (`alloc_free`); the chain's state is fixed-size; coefficients are constants.
- **Measurement lessons that apply**: evaluate responses with the DTFT at exact frequencies (004 R-07), never from adjacent FFT bins; a 1 kHz tone whose peak is read sample by sample starts on the host grid's peak phase (`stimulus::peak_phase`, 005 R-03; 008); distortion is measured at 44.1 kHz and above only (D8); audio-heavy loops run at `configs::measurement_rates()`, per-rate figure tables at `all_rates()`.
- **Before ticking a task**: `cargo fmt --all -- --check`, `cargo clippy --all-targets --all-features -- -D warnings` and `cargo test --all-features` must pass (inside a story's test-first window, that story's new tests are the expected red). The MSRV gate carries `RUSTFLAGS="-D warnings"` like CI.
- **Commits**: Conventional Commits, on branch `009-output-chain`, after each task or logical group. Merge to `main` only through a green PR, and only after the user says so.

## Implementation strategy

- **MVP = Phase 1 + US1**: the two routes audible and measured in the one-pass and in playback, the volume control and the taps, the four goldens untouched; nothing of the manifest or the C surface is needed for it.
- **Incremental**: each story closes with a commit and a coach review; the manifest and README re-bless lands with US3 (strings only); the output golden is blessed once, last, after the S-003 read and the post-implementation hardware review, so a constant or template change found by either costs no re-bless.
- **One golden file, one bless**: any later change to the chain's output is a model change and a CHANGELOG entry (FR-016), never a quiet re-bless.
- **The script is upstream of the Rust**: a figure that fails a bound is fixed in the script's inputs or the Rust's realization and the file regenerated; the bound and the pinned literals follow the script, never the Rust's own output.
