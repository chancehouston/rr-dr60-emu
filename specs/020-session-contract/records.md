## Guide: "Processing record" (new section after "Scheduled changes and the change log")

## Processing record

Since 0.20 the engine can write, for any recording in its memory, a **processing record**: one text document that says how that recording was processed. It is written beside the exported stored form and never inside it (the stored form is unchanged). It carries the engine's identity (the library version and each modeled stage's model version), the host rate, the seed, the recording counter the microphone-noise stream was keyed with, the stored form's version, encoding and unit count, a digest of the stored form, every setting as it was when the recording started, and the run: the record-side change entries with their positions in the input clock, the voice-activation events with the kept position, the removed length and the host-input position each aligns with, the totals the engine counted, the memory's remaining capacity at the start, and how the recording ended (the stop call or the memory filling), with the stop's input position, the padding start and the input samples total. **It contains no time, no place, no device identity, no recording number and nothing of the app's.**

**What the digest shows.** `recording_digest` is a 64-bit FNV-1a over the exported stored form's bytes. Equal digests mean the same bytes: a record and a recording belong together. Any single-byte difference is detected; unrelated forms coincide at 2⁻⁶⁴. It says nothing about who made the recording, when, or what reached the microphone, and it is not a signature: anyone with the library can write a consistent record for any audio. The last line, `record_checksum`, is the same function over the record's own bytes, so a truncated or altered record is refused.

**The re-render.** An engine built at the record's host rate, settings, seed and counter (`Pipeline::new_at_counter`), whose memory is filled to the record's remaining capacity, that records the same input samples with the record's entries scheduled on the record stream at their positions and stops the same way (after exactly the stop's input position, or by the memory filling) produces a stored form with the record's digest, bit for bit. The harness checks it at every host rate. The condition is the **library version**: the record names it, and the reader reports when yours differs. The re-render describes how the recording was processed; it does not vouch for what the input contains.

**The form.** One field per line, `name = value`, ASCII, LF; the first line `rr_dr60_processing_record_version = 1`; integers decimal; real numbers as the shortest decimal that reads back to the same bits (exact in every correctly rounding parser: Rust, Swift, Python, the C library); `true`/`false`; a choice as the control manifest's engine value; an unknown value is an absent line. The event and change lines are space-separated fields named by the `event.fields` and `change.fields` lines before them; event positions are device samples (6000 Hz) except the host-input position, which is a host sample. The form has no comment syntax: a line that is not `name = value` is refused. See `specs/020-session-contract/contracts/record-form.md`.

**Reading a record** (`record::read`, C `rr_dr60_processing_record_read`) ends in one of three ways:
1. **Refused** (an unknown form version, a malformed line, a missing field, a checksum that does not match the bytes): "This is not a processing record this library can read: <reason>." Nothing else is reported.
2. **Read, and this library is the one that wrote it:** every field is in the read-out; with the recording in the memory, `recording_digest_matches` says whether the record and that recording belong together; with the kept microphone audio, the re-render reproduces the recording.
3. **Read, with differences reported as flags, never as refusals:** "Written by library 0.20.0; this library is 0.21.0" (the re-render may differ; the record still describes the recording); "stage 5's model version differs" (a difference confined to playback-side stages does not touch a stored byte); "host rate differs"; "N setting names this library does not know"; "the app collected fewer events or entries than the engine counted (N of M)"; "the record and recording <number> do not belong together" (the digests differ); "`origin = imported`: the recording was brought in from a stored form, so the record names only that form and its digest; there is nothing to re-render."

**The seed and the counter.** Draw the seed once per engine from the system's random source, never from a device, user or app identifier; with the recording counter every recording has its own microphone-noise stream, so a new seed per recording is allowed (`reconfigure` while idle) but not needed. Persist the seed and the counter with the app's state and build the engine at them (`new_at_counter`), so recordings made across launches stay distinct and re-renderable.

**The feed point.** Two apps re-rendering the same audio must feed bit-identical samples. Quantize your capture to 24-bit integers at the point you feed the engine, store those losslessly, and convert with `input::samples_from_i24` (x ÷ 2²³, exact for every 24-bit value) on both sides.

**Collecting the run.** The engine keeps no recording's events or entries (the processing path allocates nothing). Append the events and entries of every `record_with_changes` call and of `stop_recording_with_changes` to your own arrays, off the audio thread, sized from `max_events` and `MAX_CHANGES_PER_CALL`; pass them with the stop report to `processing_record_len` then `processing_record_write` (both outside the callback; `_len` is one counting pass, call it first). An inconsistent run (entries out of order, past the stop, or from another stream) is refused; a shorter run than the totals is written and flagged on reading.

**The timeline maps** (`timeline::`) are pure functions of the record's data. (a) A kept sample to its **nominal** host-input alignment: the latency convention (the record path's 1 kHz group delay) shifted by every removed gap at or before it, widened to the direct-path window (the decimator's half-length; with the codec on, the frame's analysis window, about −40 … +10 ms re the frame start). It is a convention, not a measured onset, and it states a direct contribution: the gain, the gating and the coder's state depend on earlier input. (b) A host-input position to the kept sample it reaches or the event that removed it; and the one-pass's output clock to its input clock. (c) A playback device-output index to the place the speed stage computed there, leading the audible output by `playback_latency_samples()`. The ends are clamped and reported.

**Compatibility.** Every later library reads every earlier form version (a later version only adds lines). A recording stays importable and plays bit for bit under its stored form's rules; a re-render from the microphone audio needs the library version the record names, and a record stage whose model version moved is named in the read-out. Everything here is in the free tier of the project's own app (decisions.md, 2026-10-31), and none of it is a device behavior: a real recorder keeps no record of how it processed a recording.

One versioned text document per recording, written beside the stored form and never inside it (`processing_record_len` / `processing_record_write`; C `rr_dr60_processing_record_len` / `_write`), with the engine's identity (library and per-stage model versions), the host rate, the seed, the recording counter, the stored form's version, encoding and unit count, a 64-bit FNV-1a **digest** of the stored form (`digest::fnv1a64`, `recording_digest`, `recording_digest_matches`; C `rr_dr60_digest`, …), every setting as it was at the recording's start (a fixed per-slot block the engine fills at `start_recording`, reserved at construction, moved by `erase`), and the run the host collected (the record-side change entries, the voice-activation events with their host-input positions, the totals, the remaining capacity, the stop's input position and the padding start). A reader (`record::read`) refuses an unknown form version, a malformed line, a missing field or a checksum mismatch (statuses 31 – 34) and reports, as flags, a library, stage model or host rate difference, unknown setting names, a run shorter than the totals, an imported origin and a digest that does not match; the writer refuses an inconsistent run (35). `Pipeline::new_at_counter` / `rr_dr60_create_at_counter` builds an engine at a recording counter. Three pure timeline maps (`timeline::kept_to_input`, `input_to_kept`, `onepass_output_to_input`, `place_at`) and the feed-point helper `input::samples_from_i24`; the harness example `re_render` and its Swift port. The re-render contract: an engine built at the record's identity and configuration that records the same samples with the record's entries scheduled and stops the same way reproduces the stored form's digest, checked at seven rates, codec on and bypassed, with and without record-side changes, in drop and mute mode, for the stop call and the memory-full self-stop. The record contains no time, place, device identity, recording number or app data; the digest is a consistency check, not a signature. **Report changes:** `ChangeEntry.reserved` is now the **stream word** (`stream`: 0 none, 1 playback, 2 one-pass, 3 record; the C field keeps its name `reserved`); entries collected and stored by a 0.16/0.17 caller carry 0 and the writer refuses them as "no stream". `StopOutcome` gains `stop_input_position` and `padding_start_sample`; **`RrDr60StopOutcome` grows 64 → 80 bytes** on 64-bit targets (two `uint64_t` appended; no size field, the pre-1.0 ABI pass: recompile against the 0.20 header). The stage manifest's version line only; the control manifest unchanged; no new assumption (the record is data about a recording, not a device behavior).

## Case-file README lines (the app's; for the app repo)

This folder was exported by <app>. `recording.rrdr60` is the recording as the emulated recorder stored it; `recording.wav` is one playback of it (speaker route, the volume shown in the app); `recording.processing-record.txt` says how the recording was processed: the library version, every setting at the start, the changes made while recording and the moments the voice activation removed. The record's digest line matches `recording.rrdr60` byte for byte. It holds no time, place, device identity or recording number; `seed` is a random number the app drew and `recording_counter` is a running count of recordings the app's engine had started. With `microphone.i24` (included only if the sender chose to) and library <version> the recording re-renders to the same bytes. The record describes the processing; it says nothing about what reached the microphone.

## Wording rules

Keep out of public text: "verified", "authentic", "proof", "proves", "tamper", "genuine", "accurate", "honest", "true about"; say "describes". The read-out's incomplete-run copy: "the app collected fewer events or entries than the engine counted (N of M)", never "incomplete" alone. Map (a) is always "nominal alignment … a convention", never a measured onset.
