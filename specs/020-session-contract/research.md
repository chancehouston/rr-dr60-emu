# Research: Processing Record (spec 020)

## R-01 The direct-path window and the alignment (D8 a, b)

**Decision.** Kept device sample k aligns with host input centre c(k) = ⌈k · rate ÷ 6000⌉ + L + Σ{e.input_length · rate ÷ 6000 : e.output_position ≤ k}, where L = `record_latency_samples()` (the 1 kHz group delay through the record half, rounded to a host sample, spec 006) and the recorder's events carry device-sample lengths (spec 016's lesson; the one-pass's carry host samples). The direct-path window is c(k) ± ⌊(num_taps − 1) ÷ 2⌋ host samples of the decimator (`rate.rs`: `num_taps` of the rate plan; 0 at 6 kHz, the identity). With the codec on, kept k in frame f = ⌊k ÷ 120⌋ is widened to the kept range [120f − 240, 120f + 179] (the LPC window 60 past + 120 + 60 ahead and the 240-sample pitch memory, `codec/tables.rs`), converted to host samples by the same c(·). Mute mode: no input removed, the events' regions reported, the sum term is zero. The codec adds no shift for a stored recording: stored index = kept index (spec 008 FR-004); the 180-sample delay is the one-pass's line (`OnePassCodec`).

**Oracle.** (i) the splice arithmetic bit-exact: with the codec bypassed, drop-run stored sample k equals the VAS-bypassed run's stored sample k + Σ e.input_length (device units), bit for bit (the pre-gate streams are identical); (ii) the alignment within one device sample: a stimulus of 10 ms bursts at −20 dBFS at known host positions inside kept regions with silence that opens gaps; each burst's onset in the kept stream (the first sample above −40 dBFS) maps by (a) to an alignment containing the burst's host onset, and the host onset maps by (b) to that kept index within one device sample (rate ÷ 6000 host samples); with the codec on the tolerance is ±2 device samples (spec 008's cross-correlation figure).

**Alternatives.** A dependency support (unbounded through the IIR stages and the limiter's hold; not measurable); the 180-sample shift (wrong for a stored recording, hardware B4).

## R-02 Numbers, lines and the reader

**Decision.** `core::fmt::Display` for `f32`/`f64` prints the shortest decimal that round-trips (Grisu/Ryū since Rust 1.55, in core) and `str::parse::<f32>`/`<f64>` is correctly rounded (core's `dec2flt`); so a value printed with `{}` and parsed back is bit-identical. The writer formats into a `struct Sink<'a> { out: &'a mut [u8], pos: usize, overflow: bool }` implementing `fmt::Write`; `_len` runs the same writer with a counting sink (`out` empty, `overflow` ignored) so the bound is exact. Lines are `name = value\n` with one space each side; names are `[a-z0-9_.]+`; values never contain spaces except the event and change lines (space-separated fields). The reader walks the bytes once: line 1 must be `rr_dr60_processing_record_version = <n>` (n > 1 → `UnknownRecordVersion`; n = 1 read; a later n with every line we know is still refused, by D4's "unknown" rule: a reader never guesses at lines it does not know); the last line must be the checksum over every preceding byte (`RecordChecksumMismatch`); then each line's shape (`MalformedRecord`); the required fields (`MissingRecordField`); unknown `setting.` names counted; unknown other names ignored (forward compatibility within a version is not needed: a later form bumps the version). NaN/inf cannot be written (every setting validated); a parsed NaN/inf is `MalformedRecord`.

**Rationale.** Hex floats would be exact too but core has neither a hex-float printer nor parser; decimal shortest round-trip is exact in core and in every correctly rounding parser (Python, Swift, glibc/macOS `strtod`), which the guide states.

## R-03 FNV-1a 64

**Decision.** offset basis 0xcbf29ce484222325, prime 0x00000100000001b3; per byte: h ^= b; h = h.wrapping_mul(prime). Each step is a bijection on 2⁶⁴ (XOR with a byte, then multiplication by an odd constant), so two inputs of the same length that differ in one byte never collide; unrelated inputs coincide with probability 2⁻⁶⁴; deliberate collisions are easy (not a signature). Pinned by the published test vectors (`""` → 0xcbf29ce484222325, `"a"` → 0xaf63dc4c8601ec8c, `"foobar"` → 0x85944171f73967e8). Written as `fnv1a64:<16 lowercase hex digits>` on both the `recording_digest` and the `record_checksum` lines.

## R-04 The `SpeedPlace` automaton and map (c)

**Decision.** The integer state of `SpeedStage` that decides places and levels (`p5`, `active`, `requested`, `latched`, `fade: Option<Fade{old_k, old_p5, n}>`, `last_p5`, `stored` = K) moves into `pub(crate) struct SpeedPlace` with `fn step(&mut self, request: Option<u32>) -> Step { new_k, new_p5, old: Option<(k, p5, n)>, latched }` applied once per output exactly where `apply_request` and the fade bookkeeping run today; `SpeedStage` keeps the banks, the ring and the dots and calls `step`. `timeline::place_at(index, start_level, unit_count, entries)` replays `SpeedPlace` from the start level over the entries' positions mapped by `speed_landing` (spec 015's d(P)) and returns `PlaceState { place_fifths, level, fading: bool, old_place_fifths, latched }` at the given device output index. Bit-identical by construction; the speed and changes goldens (unmoved) and the A/B (level 3 and level 5 constant, 3 %) guard the refactor. Fallback if the A/B fails: keep `SpeedStage` as is and write `timeline::SpeedWalker` independently, pinned against `speed_device_outputs`'s trace on the six corner cases.

**Corner cases pinned** (US3 AS3): a request on the first output (switch at once); one landing on a fade's last output (waits one sample: the fade ends at n = N, then applies); a waiting request equal to the active level (starts nothing); a level-3 request during a wait (wait, then defer to the whole place); a request at or after the latch (dropped); two requests inside one fade (the latest wins).

## R-05 The slot block and the footprint

**Decision.** `SlotBlock { counter: u64, settings: Settings, remaining_samples: u64, events_total: u64, changes_total: u64 }` (the seed and the host rate are inside `Settings`); `Settings` is `Copy` and about 120 bytes, so a block is about 152 bytes; `Vec<Option<SlotBlock>>::with_capacity(max_recordings)` at construction (15 KB at 99, 1.5 MB at the 9999 ceiling: the one-mebibyte footprint test uses the default 99); `remove(i)` on erase (no allocation), `push(None)` on import, `clear` with `erase_all` and with a memory-emptying reconfigure. Written at `start_recording` after the counter is read (the block's counter is the keyed one); the totals: `events_total += 1` in `write_event` (already on the event's cold path), `changes_total += 1` where a record-stream landing is logged (spec 017's landing). `new_at_counter(settings, counter)` calls `Transport::with_counter(counter)` and keys the one-pass's capsule to it (today's `rekey` at construction with 0).

## R-06 The self-stop cell and the recipe

**Decision.** The record carries `run.remaining_samples_at_start` (the memory's `remaining_samples` before `open`). The harness's self-stop cell: the original engine's memory is pre-filled with a filler recording (bypass_all content imported, `stored_recording`'s pattern) so that the recording of interest stops itself; the re-render engine imports a filler of the same length before `start_recording` (an imported filler is bit-exact in length: samples or whole frames); the recipe documents "fill the memory to `capacity − remaining` before starting" and the example does it with a silent filler of that length (the content of the filler is irrelevant to the recording's bytes). With the codec on, the remaining is counted in units (frames × 120 samples); the record's field is in device samples as `MemoryStatus` reports.

**The recipe (examples/re_render.rs):** read the record → `Settings` from its configuration (the host rate from identity) → `Pipeline::new_at_counter(settings, counter)` → fill the memory → `start_recording` → `schedule_change(Stream::Record, position, control, after, tag)` for each `change.<i>` in order (refilling when 64 are pending: schedule up to 64, feed until the earliest lands, schedule more) → feed the raw audio (through `samples_from_i24`) in blocks up to the stop position → `stop_recording_with_changes` (or detect the self-stop) → `export` → `fnv1a64` → compare with `recording_digest`.

## R-07 The stop position and the padding

**Decision.** `stop_input_position` = the record stream's input position when `stop_recording` is entered (before the flush feeds zeros); with a self-stop, the input position at which the memory filled (the call's `input_samples_total` minus the samples after the fill, which the recorder knows: the kept count stops moving); `padding_start_sample` = `represented` (the kept count after the latency flush) with the codec on, the recording's length with it bypassed or after a self-stop (no padding is fed). The record's `run.input_samples_total` keeps spec 017's meaning (the stop's silence included), so `input_samples_total − stop_input_position` = the fed silence (the flush + the padding's host zeros). A re-render feeds exactly `stop_input_position` samples then calls the same stop.

## R-08 The C structs

**Decision.** `RrDr60StopOutcome` grows at the end by `stop_input_position` and `padding_start_sample` (two `uint64_t`; the struct has no size field, so an older caller's struct would be over-written by 16 bytes: the C doc comment and the CHANGELOG say the struct grew, as 0.13's `RrDr60PlayInfo` did; the pre-1.0 ABI pass adds size fields to the four report structs). New structs each start with `struct_size: u32` and follow spec 018's prefix-fill rule: `RrDr60RunData { struct_size, events: *const RrDr60VasEvent, event_count, changes: *const RrDr60ChangeEntry, change_count, stop: *const RrDr60StopOutcome }`, `RrDr60RecordReadout` (the identity scalars, the flags, a `RrDr60Settings`, the counts; about 320 bytes), `RrDr60InputAlignment { struct_size, centre, first, last, clamped }`, `RrDr60PlaceState { struct_size, place_fifths, level, fading, old_place_fifths, latched }`. Statuses 31 `UNKNOWN_RECORD_VERSION`, 32 `MALFORMED_RECORD`, 33 `MISSING_RECORD_FIELD`, 34 `RECORD_CHECKSUM_MISMATCH`, 35 `INCONSISTENT_RUN`.

## R-09 The writer's length

**Decision.** `processing_record_len(number, run)` runs the writer in counting mode and returns the exact byte count (deterministic: the same inputs give the same length); `processing_record_write` refuses a buffer shorter than it (`BufferTooSmall`, the existing status) and returns the bytes written. A bound for pre-sizing without a run: 4 KB + 64 bytes per event + 96 per entry (documented in the guide).
