# Research: Live Record-Side Values (017)

Each entry: decision, rationale, alternatives. Code references are to `main` at the 0.16 merge (`06e40b0`). The spec's reviews (coach 1 – 17, hardware B1 – B11, product M1 – M8) are applied in the spec; the plan reviews are recorded in plan.md when they land.

## R-01: Where the record-side state lives

**Decision.** `RecordPath` (`paths.rs:450`), the object both record-side streams are (the recorder's `recorder` and the one-pass's `one_pass.rec`), gets a `RecordCtl`: the **input clock** (`input: u64`, host samples processed), a `Schedule` (spec 015's, 64 entries), the cached `next_apply`, the stream's **last applied** record-side values (the eight, as `RecordValues { sensitivity, threshold_dbfs, hang_ms, onset_ms, knee_dbfs, attack_ms, release_ms, hiss_offset_db }`), a `landed` record (the last landed value and tag per control in the call) and a staging log of up to **72** entries (64 scheduled plus the eight cross-stream landings of R-02; coach 1, hardware B1). The at-once rule for the hiss reads `input == 0` (no flag: the clock's reset events are exactly construction, `reset`, `reconfigure`, `start_recording`; coach 7). Spec 015's `StreamState` in `PlaybackPath` is unchanged; the one-pass therefore carries two clocks and two schedules, one per path (spec D2). `RecordPath` becomes `repr(C)` with its hot scalars (`input_peak`, `limiter_input_peak`, the clock, `next_apply`) first and `ctl`'s two arrays (about 5.6 KB) last (the 015 lesson; hardware B8). **Shared rules with spec 015's `StreamState`** (the two state types stay separate because the sides' applied values differ in type and the playback type is blessed by `golden-changes-v1.json`; a unification is spec 020's if the session contract wants one entry type per stream): the clock resets at the stream's start events; the schedule is kept by the start call and cleared by every end; a pending change lands at the call's first sample with `next_apply = 0`; entries chain per stream; `repr(C)` hot fields first. One harness test runs the same scenario on both sides (`record_edge_cases::sides_share_the_rules`).

**Rationale.** The record stages (`mic`, `limiter`, `half.vas`) live in the path, the apply point is inside its per-sample `step`, and the recorder, the stop's feed and the one-pass's tick all go through it, so one implementation serves every record-side call, the front taps included (`front_only`).

**Alternatives.** The record-side schedule on the `Pipeline` (rejected: the apply point is in the path's per-input-sample step); a generic per-clock state shared with `StreamState` (rejected for this spec: the two sides' applied values differ in type; a later refactor if 020 wants it).

## R-02: The apply point: the top of input sample P

**Decision.** In `RecordPath::step` and `front_only`, **before** `sanitize_in`/`front`: `if self.ctl.input >= self.ctl.next_apply { self.apply_due() }`, then the sample is processed and `input += 1`. `apply_due` (cold) pops every entry with position ≤ `input`, applies it to the stage it names (R-03 – R-05), logs it (before = the stream's last applied value, after, tag), updates `last`/`landed`, and re-arms `next_apply`. Because the gate processes nothing between host samples, applying the gate's values at the top of input sample P makes the first device sample that sees them exactly k(P) = ⌈P · 6000 ÷ rate⌉ (the decimator emits device k when host ⌊k · rate ÷ 6000⌋ is pushed, `down.rs:53`: k(P) is the smallest k whose due index ≥ P), with no device-side apply point (hardware B6; the mirror of spec 015 R-02's speed argument).

**The cross-stream pending (spec D4).** The `Pipeline` keeps the readings in `self.settings` (the eight fields) and `record_tags: [u64; 8]` (the tag of the last landing per control). At every record-side call's entry (`record`, the stop's feed, `process*`) the path's `begin_call(&settings, &tags)` compares `self.settings`' eight values with the path's `last` (numerically; scheduled f32 values are normalized with `+ 0.0` as 015 does): each difference becomes a pending change applied at the call's first input sample **before** the stream's own due entries (015's plain-first rule), logged with the landing's tag, so a value landed on the recorder reaches the one-pass at the one-pass's first call after the recording ends (the one-pass is refused while a path is active). **`RecordPath::adopt(&settings)`** (hardware B2, spec 015's `start_playback` precedent) *applies* the settings to the three stages (`retune` if the limiter's three differ, `set_values` if the gate's four differ, `set_offset(.., at_once)` if the hiss differs) **and** sets `last`, with no entry; `start_recording` calls it on the recorder after its reset, `reset` on both paths, `reconfigure` rebuilds both from the settings. Without the apply, a hang landed on the one-pass would leave the recorder's stage at the old length while `last` said otherwise. **The mirror's tag** (coach 4, product M1): a record-side value landed on the other stream carries the landing's tag (D4); the playback side's three controls carry 0 there (spec 015's plain-change rule); the guide says so and the two rules align at spec 020's ABI pass (a mirrored bit beside the stream word in the entry's `reserved`).

**Alternatives.** Applying inside `RecordHalf::process` at the device rate for the gate's values (rejected: a second apply point and a device counter, the hole 015 found for the speed); a per-stream settings reading (rejected by D4).

## R-03: The limiter's retune

**Decision.** `Limiter::derive(settings: &AgcSettings, host_rate_hz) -> Derived { vbe6, charge_gain, dis_r11, dis_b5, ceiling_fs }` is factored out of `new` (`limiter.rs:188`) and used by `new` and by `retune(&AgcSettings)`, which writes those five fields and leaves `vc`, `vc_max`, `v_floor`, `v_limit`, `ln_k1`, `dt_over_c6` untouched. The two overdrive indices (`I(knee)`, `I(KNEE_REF_DBFS)`) are stored fields computed by the same function at construction, never literals, so an attack or release change is a few multiplies (about 100 ns) and only a knee change pays one 360-point sum (about 2.5 µs; hardware B8). The capacitor's continuity holds by construction: the analytic cap (`vc_target`) and the charge branch are mutually exclusive, so a retune never steps `vc` (hardware B4). A knee change moves `vbe6`, `ceiling_fs` and `charge_gain` (through `beta6_for(knee, attack)`); an attack `charge_gain`; a release `dis_r11`, `dis_b5` (hardware B5). The gain law `a(vc)` and spec 016's `charge()` are therefore continuous across a retune; `vc_target` uses the new ceiling. `overdrive_index(KNEE_REF_DBFS)` is a constant computed once. Cost about 5 µs (two 360-point indices); reported as the worst landing (FR-008, FR-009).

**Rationale.** A change at input 0 then equals construction bit for bit (the same arithmetic), and a mid-call retune keeps the 016 meter's running `vc_max`.

## R-04: The gate's values

**Decision.** `VasStage::set_values(settings: &VasSettings)` recomputes `threshold` (the formula of `new`, `vas.rs:82`: `exp(level_db · ln10 / 20)` with `level_db = threshold_dbfs + 3 · (3 − sensitivity)`), `hang` and `onset` (`device_samples`), and keeps `state`, `silent`, `run`, `since_sound`. The next `process` compares the kept counts with the new lengths (hardware B4: a silent count past the new hang pauses at the next non-sound sample, a sound run past the new onset resumes at the next sound sample). `hang_samples()` reads the new hang, so spec 016's `hang_remaining` (`hang.saturating_sub(silent)`) reads 0 while the count exceeds it.

**The event bound** (hardware B3; plan reviews coach 2, hardware B3): `RecordPath::max_events(frames, settings_hang)` takes `min(the stage's current hang, the settings' hang (the value the next begin_call or start_recording lands), every pending hang change's device_samples)` over the schedule's ≤ 64 entries (at the query, no allocation; the pending lengths through the same `value as f32` → `device_samples` round trip `set_values` uses) in place of `self.half.vas.hang_samples()` (`paths.rs:728`); `Pipeline::max_events` / `max_record_events` pass `device_samples(self.settings.vas.hang_ms)`. The spacing H_min + 2 stays a valid bound under a mid-block shortening (the pause fires when the count exceeds the current hang, so the gap since the last resume is at least min(H) + 2), in mute mode too.

## R-05: The hiss transition

**Decision.** `MicCapsule { gain, gain_from, gain_to, ramp_k, ramp_n, inv_n }` with `set_offset(db, at_once: bool)`: `gain_to = σ · 10^(db/20)` (the formula of `new`, `mic.rs:88`); at once → `gain = gain_to`, `ramp_k = ramp_n`; else `gain_from = gain` (the gain at this sample, a retarget included), `ramp_k = 0`. In `process`, before the draw: `if ramp_k < ramp_n { ramp_k += 1; gain = if ramp_k == ramp_n { gain_to } else { gain_from + (gain_to − gain_from) · s(ramp_k · inv_n) } }` with `s(u) = u²(3 − 2u)` (spec 011's `ramp_step` form), N = `volume_transition_samples(rate)`: the landing sample P is transition sample 1 (it carries s(1 ÷ N)) and sample **P + N − 1** is assigned the target exactly, spec 011's indexing (coach 3; the spec's "P + N" is restated). The idle path is one predictable compare; the draws (`gauss()`) are untouched, so the stream is the same under any gain (hardware B9). The at-once rule: `ctl.input == 0` at the apply (construction, `reset`, `reconfigure`, `start_recording` reset the clock) or the capsule bypassed (`MicFront` has no capsule: the value is logged, nothing moves). If the A/B needs it, the per-sample compare can move off the capsule by setting `next_apply = input` during a transition so the cold apply steps the gain (hardware B8); R-05's form stays if the cost fits. **Taken at T019 (2026-10-30):** the one-pass A/B read +2.52 … +3.49 % against 3 % with the capsule compare; the transition is now stepped by the apply point (`MicFront::ramp_step` before the draw), `next_apply` held on the next sample while `ramping()` (`RecordCtl::hold_next_sample`) and on the current sample across a call boundary, a schedule call or a clear (`hold_now`); `process` has no compare. The 714-entry golden was unmoved and caught the boundary hold being one sample late in the fold's first form.

**Rationale.** D3, D9; the 011 convention assigns the target exactly at sample N (coach 1).

## R-06: Validation at the schedule call

**Decision.** `schedule_change` (spec 015, `pipeline.rs`) gains the eight controls: by the control manifest's index (`controls::index_of`), the stream must be `Record` or `OnePass` (else `ControlNotOnStream`); the value is checked against `Setting::range` for the setting (finite, inclusive; the sensitivity also integral) and refused with `InvalidSetting { setting }` as `validate` would; stored as the setting's type (`f32`; the sensitivity `u8`) widened to the entry's `f64`. The eight controls are the only ones with the record path and a numeric value whose timing is live; everything else keeps `ControlNotOnStream`.

## R-07: The stop, the self-stop and the clock

**Decision.** The record stream's clock is `recorder.ctl.input`, one counter (coach 6): `input_position(Stream::Record)` returns it while recording and 0 otherwise. `stop_recording` applies pending changes during `feed_zeros` as during `record` (the same path code; the gate held open in the codec's padding overrides the *decision* only, so a hang or threshold change there has no effect on the stored samples while the gate's state follows the new values, hardware B11), then `close_recording` clears the schedule (the one place every end reaches: the normal stop, the self-stop at the memory limit and the `DiscardedEmpty` early return, which reports a total of 0 and no entries; coach 9); `StopOutcome` gains `input_samples_total: u64` (read from the clock before the path leaves the recording) and `changes: usize`; `RecordInfo` gains `changes: usize` and `input_samples_total: u64` too, so a self-stop's final position is readable (hardware B10); `stop_recording_with_changes(events, changes)` drains the staged entries (a change inside the fed silence is logged; one at or past the total is dropped). A refused `start_recording` leaves the schedule; `start_recording` keeps it, resets the clock and calls `adopt(&settings)`.

## R-08: The one-pass's two schedules and the log

**Decision.** `schedule_change(Stream::OnePass, …)` routes a record-side control to `one_pass.rec.ctl.schedule` and a playback-side one to `one_pass.play.ctl.schedule`; `pending_changes(OnePass)` is the sum; `clear_schedule(OnePass)` clears both; `input_position(OnePass)` reads `one_pass.rec.ctl.input`. The log-taking one-pass variants drain the record path's staged entries first, then the playback path's (each in landing order); `BlockInfo.changes` is the sum. `MAX_CHANGES_PER_CALL` becomes 2 · 64 + 3 + 8 = **139** (two schedules, one plain change per live control, one cross-stream landing per record-side value; the one-pass's attainable maximum is 138, since the speed is playback-only; the recorder's 72; the player's 67), the Rust and C constants; the 015 tests that pinned 67 are restated, and the C smoke's buffers, sized by the define, recompile unchanged (coach 1, hardware B1; the spec's D2 figure of 131 restated with the owner's plan sign-off).

## R-09: The clock helper and the landing helper

**Decision.** `changes::Clock { Input, Output }` and `changes::clock_of(control: u32) -> Result<Clock, Error>` (Input when the control's manifest paths include `RECORD`, Output otherwise: record wins for the idle controls on both paths, so the helper is total and informational for them; `NoSuchControl` past the list; `us2_controls` asserts the whole 29-entry vector; coach 8); `changes::record_landing(position, host_rate_hz) -> Result<u64, Error>` = ⌈P · 6000 ÷ rate⌉ (`UnsupportedHostRate` otherwise); C `rr_dr60_clock_of` (an enum `RrDr60Clock`) and `rr_dr60_record_landing`.

## R-11: Cost

**Decision.** One `u64` compare per input sample on the record path (the 015 pattern), nothing per device sample and, since R-05's fold, nothing in the capsule; measured by `tests/record_timing.rs` (the 0.16 API: a 10 s recording through `record` and the one-pass front, 48 kHz, fastest of 45) in a `record` mode of `scripts/ab-timing.sh` (3 %; `RR_DR60_RECORD_COST_CEILING` 0.05 on the label job; the record path alone is cheaper than the one-pass, so the budget may be tight: the fold of R-05 is the fallback), and `tests/record_pending_timing.rs` (head-only: one knee change per 4096 block; the worst block; the per-change bound stated as changes × retune, since 72 knee changes in one 32-sample block at 96 kHz would exceed the block's budget: documented, not chased) reported, run by the `record` mode after the asserted pair.

**Figures (T019, 2026-10-30, solo runs of `scripts/ab-timing.sh 06e40b0 record` on the development machine; 48 kHz, 4096 blocks, the default front, the codec bypassed, the record schedule empty; fastest of 45 runs × 3 alternations per build).** Run 1: record path 48.48 → 48.89 ns per host sample (**+0.41 ns, +0.85 %**), one-pass 72.67 → 74.50 ns (**+1.83 ns, +2.52 %**), both within the 3 % budget; with one knee change per 4096-sample block the record path reads 49.33 ns (+0.44 ns, +0.91 % against the empty schedule), the worst block 315.9 µs of the 85 333 µs budget (the retune's derivation once per block). Run 2 (same code): record +0.54 ns (+1.14 %), one-pass +2.14 ns (+2.97 %). Run 3 (after folding the `apply_after_front` mutant into the armed position, spec 015's lesson): record +1.76 ns (+3.62 %), one-pass +2.54 ns (+3.49 %): FAIL, with the run-to-run spread of the machine (spec 012 research R-09) now visible across the budget. Run 4 (after R-05's fold: the capsule's per-sample compare moved into the apply point, which holds itself on every sample of a transition): record **+0.43 ns (+0.90 %)**, one-pass **+0.63 ns (+0.86 %)**, both PASS; one knee change per block +0.29 ns (+0.60 %), the worst block 257 µs of 85 333. The record path's per-sample work is now one `u64` compare and one increment. The CI runner (x86-64, the `ab-timing` label on PR #47, 2026-10-30): record path 106.31 → 106.70 ns (**+0.40 ns, +0.37 %**), one-pass 186.88 → 186.64 ns (**−0.13 %**), ceiling 5 %; one knee change per block +1.39 ns (+1.30 %), the worst block 536 µs of 85 333. Lesson: the 714-entry golden caught the fold's first form holding the apply point one sample late across a call boundary (the only 48 kHz transition that crossed a 1024-sample block).
