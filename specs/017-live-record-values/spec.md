# Feature Specification: Live Record-Side Values

**Feature Branch**: `017-live-record-values`

**Created**: 2026-10-30

**Status**: Complete on `main` (PR #47 merged 2026-10-30, 24ffab9)

**Input**: User description: "017 live record-side values. As an app recording a session, I want the record path's values (the microphone sensitivity, the voice activation's threshold, hang and onset, the limiter's knee, attack and release, the capsule's hiss offset) to change during a recording and during the one-pass at a sample position, through the schedule and the change log spec 015 built, so that a user can adjust the recorder while it records and the session reproduces bit for bit. ## Overview

Since spec 015 the three playback-side controls land on an exact sample of their stream and every applied change is logged. The record side's values still change only idle: `reconfigure` rebuilds the paths, so a user who turns the sensitivity down while a recording runs today has to stop, reconfigure and start again, and a session that replays a recording cannot reproduce a change made mid-recording.

This feature makes eight record-side values **live** through the same schedule and log: a change carries a position in the stream's **input** clock (the samples the recorder or the one-pass has processed), lands on exactly that input sample (or the device sample k(P) the rate conversion emits for it, for the voice activation's values), is logged with the position it landed on, and leaves everything else as it is. The limiter's capacitor keeps its charge across a knee or release change, as a circuit would; the voice activation's running counts are kept and compared against the new lengths; the hiss level glides over 20 ms rather than stepping.

The owner's 2026-10-29 decision stands: the codec, the memory, the host rate and the latency-bearing bypasses are never live; the stage switches stay idle. Changing a value while recording is an emulator convenience: the device sets its sensitivity while stopped (S-001).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Adjust the recorder while it records (Priority: P1)

An app lets the user turn the sensitivity down (or any of the eight values) while a recording runs, by scheduling the change at the input sample the user's gesture corresponds to; the recording continues, the change lands on that sample at any buffer size, and the result equals what a recording made with the new value from the start would be from that sample on.

**Why this priority**: it is the feature; the product brief ranks the sensitivity second of all controls for group-hunt users and investigators (a judgement, controls-discussion § 2a, not user research).

**Independent Test**: for each value, on the recorder and the one-pass, a change at input sample 0 of a fresh stream is compared with the constant configuration (bit-identical), a change at P with the old constant run before its landing (per device sample with the codec bypassed, per frame with it on), and the output at the four partitions with each other; the log against the schedule.

**Acceptance Scenarios**:

1. **Given** a fresh recorder with a value scheduled at input position 0, **When** a stimulus is recorded, **Then** the stored samples are bit-identical to a recording configured with that value from the start; **Given** a fresh one-pass likewise, **Then** its output is bit-identical to the constant configuration's; for each of the eight values at seven rates, in drop and mute mode; the entry's position is 0 and its before/after values are the old and new settings.
2. **Given** a value scheduled at input position P inside a block, **When** the stream runs at block sizes 1, 64, 4096 and the irregular partition, **Then** the outputs and the concatenated logs are bit-identical; with the codec bypassed every post-VAS device sample before k(P) equals the old constant run's, and with the codec on every stored frame whose 120 samples plus the 60-sample look-ahead end before k(P) is byte-identical to the old run's.
3. **Given** the limiter's knee lowered (and separately raised) at P while a tone 10 dB over the old knee plays, **When** the stream runs, **Then** the hold capacitor's voltage is continuous across P (no reset) and 2 s after the landing the attenuation equals the new constant run's at the same stimulus time within 0.1 dB; **Given** the attack changed at P, **Then** the dead time of the first onset after the landing equals the new constant run's within spec 005 FR-011's tolerance; **Given** the release changed, **Then** the release time of the first release after the landing likewise.
4. **Given** the sensitivity raised by two levels (the threshold 6 dB lower) at P during a quiet passage that the old threshold would have paused, **When** the stream runs, **Then** the gate's decision changes from device sample k(P), the hang count already running is compared against the new length, no post-VAS sample before k(P) moves, and the splice events agree with a harness reference gate given the same change.
5. **Given** the hang shortened at P while silence is being kept with the count already past the new length, **When** the stream runs, **Then** the gate pauses at k(P) if it is non-sound, else at the next non-sound device sample, exactly as the reference gate; **Given** the onset shortened while paused with the run already past the new length, **Then** the gate resumes at the next sound device sample.
6. **Given** the hiss offset raised by 12 dB at P (P past the first sample), **When** the stream runs with the input silent at the tap after stage 1 with the amplifier bypassed, **Then** for every transition sample the ratio to the old constant run's sample equals the smoothstep's gain ratio within 2 ULP, from P + N on the output is bit-identical to the new constant run's (the same noise draws), and the level before P equals the old run's; at the whole engine the band level 1 s after P is within 0.1 dB of the new constant run's.
7. **Given** a record-side change scheduled at a position at or below the stream's input position, **When** the next call runs, **Then** it lands on the next input sample and the entry says so.
8. **Given** the hang shortened from 1000 to 50 ms by a change landing inside a block whose stimulus splices at the new hang, **When** `events` is sized by `max_record_events` before the call, **Then** every event is written (the bound used the pending hang).

### User Story 2 - The session reproduces (Priority: P2)

A recording made with changes mid-way is exported; a session replays the same input with the same schedule and gets the same recording; the one-pass with the same changes equals the recording played back.

**Why this priority**: replay is the reason the changes are positioned and logged.

**Independent Test**: record with changes twice from the same input and schedule (bit-identical stored forms); the one-pass with the same changes against record-then-play under spec 008 FR-009's rule; the schedule survives `start_recording` and is cleared by every end of a recording.

**Acceptance Scenarios**:

1. **Given** the same input, settings, seed, recording counter and schedule, **When** two engines record, **Then** the exported recordings are byte-identical and the logs equal.
2. **Given** a record-side schedule, **When** the one-pass runs it and a recorder records it and plays it back, **Then** the outputs are bit-identical under spec 008 FR-009's rule (the one-pass fed the record-latency silence; the output skipped by the codec's delay; the stop's padding count read after the stop), with the codec bypassed and on, in drop and mute mode.
3. **Given** changes scheduled before `start_recording`, **When** the recording starts and runs, **Then** they land at their input positions (position 0 on the first sample); **Given** changes past the fed input, **When** `stop_recording` runs, **Then** those inside the fed silence (the flush and, with the codec on, the padding) land and are logged in the stop's report, those at or past the final input position are dropped without an entry, the report carries that position, and the schedule is empty afterwards; **Given** a recording that stops itself at the memory limit, **Then** the schedule is cleared and the stopping call reports the entries that landed before the stopping sample.
4. **Given** a landed change on one stream, **When** `settings()` is read, **Then** it shows the new value from the landing; **When** the other stream next processes an input sample, **Then** it lands the value and logs it with the same tag; **When** `reconfigure(settings())` is then called, **Then** neither stream's output differs from a fresh engine's.

### User Story 3 - Validation, the manifest and C (Priority: P3)

The app schedules record-side changes through the C API with the same refusals as the idle path, reads the input position and the landing helpers, and the control manifest tells it which controls are live and which clock each uses.

**Independent Test**: every refusal stores nothing; the control manifest's eight entries read "live" and the canonical text matches; the C smoke's scheduled recording equals the Rust example's rows.

**Acceptance Scenarios**:

1. **Given** a value outside its range (a sensitivity 0 or 6, a threshold above 0 dBFS or below −60, a hang below 50 ms or above 10 000, an onset above 200 ms, an attack below 1 ms or above 50, a release below 200 ms or above 10 000, a hiss offset below −18 dB or above +12, a non-finite value), **When** it is scheduled, **Then** it is refused with the setting's existing error (`InvalidSetting`, naming the field) and nothing is stored.
2. **Given** a control that stays idle (a switch, the codec, the memory, the host rate, the seed, the tap, the voice activation's mode), **When** it is scheduled on any stream, **Then** it is refused with `ControlNotOnStream` and nothing is stored; a record-side control on the playback stream likewise; `stream_position(Stream::Record)` and `input_position(Stream::Playback)` are refused (no such clock).
3. **Given** the control manifest, **When** it is read, **Then** the eight entries' timing is "live" and every other entry's is unchanged; `clock_of` answers "input" for every record-path control and "output" for the three playback-side ones; the canonical text is re-blessed once.
4. **Given** a C program, **When** it schedules record-side changes on the record stream and the one-pass, records with `rr_dr60_record_with_changes`, stops with `rr_dr60_stop_recording_with_changes` and reads the input positions and `rr_dr60_record_landing`, **Then** it receives the Rust entries and outputs bit for bit.

### Edge Cases

- **Two clocks on the one-pass**: a route or volume change's position is an output index, a record-side change's an input index; each is reported where it landed in its own clock; `stream_position` reads the output clock and `input_position` the input clock; `clock_of(control)` says which a control uses. At the three front taps the input and output clocks coincide.
- **The recorder's clock** starts at 0 at `start_recording`, counts every host sample the stop feeds, and reads 0 while idle; the stop's report keeps the final position (positions at or past it have no microphone sample: spec 020's map labels the flush).
- **The sensitivity and the threshold** both move the gate's level (A-022: 3 dB per level from the level-3 threshold); both at one position: the pair's result; the manifest keeps both entries.
- **A hang or onset change while recording (not paused)** changes only the lengths; a silent count above the new hang pauses at the next non-sound device sample.
- **The hiss offset with the capsule bypassed**: accepted, logged, taken at once, no audible effect (as the idle setting).
- **A limiter change with the limiter bypassed**: accepted, logged, no effect until a `reconfigure` turns the stage on with the landed value.
- **The one-pass at a front tap**: at `AfterMicCapsule` and `AfterMicAmp` the limiter and the gate do not run, so their changes are logged with no effect; at `AfterAgc` the gate does not run; the hiss lands at every tap with the capsule on.
- **`reset` and `reconfigure`**: both one-pass clocks restart, the schedules are cleared, the landed values stay (they live in the settings); a hiss transition cut by `reset`, `reconfigure` or `start_recording` leaves the gain at the landed value.
- **Changes at one input position**: applied in submission order; for the limiter the last coefficients win; for the hiss two changes at one sample start one transition toward the last; for the gate the last lengths win.
- **The record-side entries' `before`** is the stream's last applied value, which after `reset`, `reconfigure` or `start_recording` is the settings' value.
- **Mute mode**: a landed threshold change moves which samples are stored as zeros, which the muted-region events report.
- **Determinism**: integer positions, exact landing rules, the hiss transition in spec 011's arithmetic, the limiter's retune in construction's.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The engine MUST accept a scheduled change of each of the eight record-side controls (`vas.sensitivity`, `vas.threshold_dbfs`, `vas.hang_ms`, `vas.onset_ms`, `agc.knee_dbfs`, `agc.attack_ms`, `agc.release_ms`, `mic.hiss_offset_db`, by the control manifest's indices) on `Stream::Record` and `Stream::OnePass`, the position in the stream's **input** clock (D2), the value validated exactly as `validate` validates the setting (the setting's `InvalidSetting` error, nothing stored); any other setting, and a record-side control on the playback stream, MUST be refused with `ControlNotOnStream`.
- **FR-002**: Schedules: the recorder one and the one-pass two (one per clock), each spec 015's (64 pending, position order, ties in submission order); `pending_changes(Stream::OnePass)` the sum, `clear_schedule` both; `pending_changes` and `clear_schedule` accept `Stream::Record`. The record schedule is kept by `start_recording`, applied during `record` and the stop's feed, and cleared by every end of a recording (`stop_recording` whether or not the flush runs, the self-stop at the memory limit, `reset`, `reconfigure`); a refused `start_recording` leaves it; recording and playback calls leave the one-pass clocks and schedules untouched. `input_position(Stream::Record)` (0 while idle) and `input_position(Stream::OnePass)` MUST be readable; `stream_position(Record)` and `input_position(Playback)` are refused. `max_record_events` and `max_events` MUST use the smallest of the current hang and every pending hang change.
- **FR-003**: A host-rate value MUST land on input sample P exactly. The limiter: the knee's detector threshold, ceiling and charge gain, the attack's charge gain, the release's two discharge coefficients, computed by construction's arithmetic and applied from sample P, with the hold capacitor's voltage, the call's peak voltage, the floor and the limit carried. The hiss: the gain follows `g_from + (g_to − g_from) · s(k ÷ N)` for k = 1 … N − 1 from P (s spec 011's smoothstep, N = 0.02 × rate) and is assigned `g_to` at sample P + N, the noise draws unchanged; a change during a transition starts a new one from the gain at that sample; a change on a stream's first input sample after construction, `reset`, `reconfigure` or `start_recording`, or with the capsule bypassed, takes the gain at once. A device-rate value (the gate's four) MUST take effect at device sample k(P) = ⌈P · 6000 ÷ rate⌉ with the running counts kept (D3's rules). A position at or below the stream's input position lands on the next input sample.
- **FR-004**: Each stream MUST keep its own applied record-side values; a change landed on one stream becomes pending for the other and lands at its next input sample, logged with the same tag. `settings()` MUST reflect the most recently landed value from its landing sample (a pending change does not show); `reconfigure(settings())` MUST then change no output from a fresh engine's on either stream. No new setter; the idle path is unchanged.
- **FR-005**: Every landed record-side change MUST be logged as a change entry (spec 015's form, the position in the input clock, before = the stream's last applied value, after, tag) by the call that processed the input sample it landed on: `record_with_changes(input, events, changes)` (`RecordInfo` gains the applied count), `stop_recording_with_changes(events, changes)` (`StopOutcome` gains the applied count and the final input position), and both one-pass log-taking variants, whose buffer carries both sides. The always-enough length `MAX_CHANGES_PER_CALL` becomes **131**. Entries carry no clock field: the control's side (`clock_of`) tells which; the map between the clocks and the events' bases is spec 020's.
- **FR-006**: With no record-side change scheduled the output MUST be bit-identical to 0.16 (the eleven audio golden files, their SHA guards, every smoke hash). A change at input position 0 of a fresh stream MUST equal the constant configuration bit for bit (every value, both streams, seven rates, drop and mute mode). A change at P MUST leave every post-VAS device sample before k(P) equal to the old constant run's with the codec bypassed, and with the codec on every stored frame whose 120 samples plus the 60-sample look-ahead end before k(P). Outputs and logs MUST be partition-independent (1, 64, 4096, the irregular partition). The one-pass with a schedule MUST equal record-then-play with the same schedule under spec 008 FR-009's rule, the codec bypassed and on, in both modes.
- **FR-007**: The gate's decisions after a change MUST equal a harness reference gate given the same device samples and the same change at k(P) (spec 003's data model with the new lengths applied there). The limiter: the attenuation 2 s after a knee change equals the new constant run's within 0.1 dB (a tone 10 dB over the old knee, both directions); the first dead time after an attack change and the first release time after a release change equal the new constant run's within spec 005 FR-011's tolerances; the capacitor voltage is continuous at P. The hiss: at the tap after stage 1 with silent input and the amplifier bypassed, every transition sample's ratio to the old run equals the smoothstep's within 2 ULP and the output from P + N is bit-identical to the new run's; at the whole engine the band level 1 s after P is within 0.1 dB of the new run's.
- **FR-008**: Deterministic and real-time safe as spec 015: no allocation, lock or I/O in any call; the per-change work bounded (the limiter's derivation at a landing, about 5 µs, reported); integer positions; the same inputs, settings, seed, counter and schedules give bit-identical outputs and logs on every platform. A new golden file (`golden-record-changes-v1.json`) MUST hold, per entry, the output digest and the full log over the eight values, both streams, both modes, the stop case and the seven rates.
- **FR-009**: The per-sample cost at 48 kHz with the schedules empty MUST be within D7's budget against the 0.16 merge commit on the record path and the one-pass, as a build comparison on the development machine and the CI runner (`ab-timing` label, the runner ceiling); with one knee change per block, and the worst block, reported.
- **FR-010**: Rust and C: `input_position`, `record_with_changes`, `stop_recording_with_changes`, `changes::record_landing`, `changes::clock_of` (the C forms with counts as out-parameters; the existing C report structures unchanged, the pre-1.0 ABI list); `ChangeEntry::position`'s documentation names both clocks; the control manifest's eight entries at timing "live" (one canonical re-bless; the kinds unchanged); the header regenerated.
- **FR-011**: Documentation: the user guide's "Scheduled changes and the change log" section gains the record side (the input clock, the eight values and their landing rules, k(P), the hiss transition, the stop rule, the two clocks of the one-pass, `clock_of`, the cross-stream landing, and "not a device behavior": the sensitivity is set while stopped, S-001); the real-time list; the CHANGELOG as version 0.17.0 (the 131 bound recorded); the control manifest's text re-blessed; the product notes of records.md; the stage manifest's version line only.
- **FR-012**: Not a device behavior: no assumption registered or amended, no stage's model version moves, no new setting; the control manifest's kinds (and so the free / Workbench line) unchanged.

### Out of Scope

- Live switches and bypasses (latency-bearing or enabling); the speech codec, the memory, the host rate, the seed, the tap, the voice activation's mode; a between-recordings real-time-safe apply (`reconfigure` stays the idle path; a change at position 0 while stopped covers these eight); the battery state (spec 018); the playback-stage bypass (021); the session snapshot and sidecar, the entry's stream word and the map between the clocks and the events' bases (020); plain setters for the eight values (D4); any claim about the device's behavior when its sensitivity changes mid-recording; the app's choice of exposing the live sensitivity in Recorder mode.

### Key Entities

- **Record stream**: `Stream::Record`, the recorder; clock = input samples fed since `start_recording` (the stop's feed included); one schedule; last applied values per record-side control.
- **Input clock** of the one-pass: input samples processed since construction, `reset`, `reconfigure`; beside spec 015's output clock; its own schedule.
- **Record-side change**: a scheduled change of one of the eight controls; lands by FR-003; logged as a change entry in the input clock.
- **k(P)**: the device sample ⌈P · 6000 ÷ rate⌉ at which a gate value scheduled at input P takes effect (`record_landing`).
- **Hiss transition**: N = 0.02 × rate input samples of the smoothstep on the hiss gain, assigned the target at P + N.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For each of the eight values on both streams at seven rates in both modes: a change at input 0 is bit-identical to the constant configuration; a change at P leaves the pre-landing output identical to the old run (per device sample with the codec bypassed, per frame with it on); outputs and logs identical at the four partitions: 0 mismatches.
- **SC-002**: The gate after a change equals the reference gate on every device sample (0 mismatches; the events equal); the limiter's attenuation 2 s after a knee change within 0.1 dB of the new run, the first dead time and release time within spec 005's tolerances, the capacitor voltage continuous; the hiss transition's ratio within 2 ULP of the smoothstep and bit-identical from P + N.
- **SC-003**: The eleven golden files and their SHA guards are byte-identical; the new golden is reproduced on every golden target; the C smoke's scheduled recording equals the Rust example's rows; record-then-play with changes equals the one-pass (codec off and on, both modes).
- **SC-004**: The log holds one entry per landed change with the input position, the chained values and the tag; the stop's entries and final position are reported; a change at or past the final position is dropped without an entry; one scenario lands 64 + 64 + 3 changes in one one-pass call (the 131 bound is tight); the event bound holds through a hang shortening.
- **SC-005**: The idle cost at 48 kHz is within 3 % of 0.16 on the record path and the one-pass (5 % on the runner); one knee change per block and the worst block reported.
- **SC-006**: Coverage stays at or above 80 % and within 1 point of the baseline (0.16: 97.49 % locally).

## Assumptions

- **D1 alternative:** every record-side setting live, the switches included (rejected: a bypass changes the latency or enables a stage from rest, which the owner excluded on 2026-10-29, and a toggle mid-stream breaks the record-then-play identity); only the sensitivity (rejected: the limiter's and gate's internals are the Workbench's content, and live monitoring through the one-pass needs them). Reversal trigger recorded: if a capture shows the sensitivity is a digital gain (A-033 H4/H5), its landing rule gains the hiss's 20 ms glide.
- **D2 alternatives:** the output clock for the record side too (rejected: the record stages act before the gate drops samples, so a change during a pause would have no position); the recording's stored-sample clock (the VAS events') for the recorder (rejected: the limiter and the hiss act at the host rate before the decimation, and the app's gesture and the kept microphone capture are in input time); one schedule across both clocks (rejected: the positions are not comparable); a shared 64 on the one-pass (rejected: spec 015's per-stream rule stays simple and the constant is a compile-time define apps size buffers by, so one change to 131 now).
- **D3 alternatives:** resetting the limiter's capacitor at a knee change (rejected: unphysical and a click); resetting the gate's counts at a hang change (rejected: a pause under way would restart its hang); stepping the hiss gain (rejected: a stepped noise level is audible); excluding the hiss from the input-0 identity instead of the at-once rule (rejected: spec 011's rule already exists and keeps one oracle for all eight).
- **D4 alternatives:** eight plain setters (rejected: spec 015's schedule at the current position is the same call, the setter scan of spec 014 would grow, and the idle path already exists); per-stream settings readings (`settings_of(stream)`; rejected as API growth; the cross-stream landing keeps one reading honest).
- **D5 alternative:** clearing the record schedule at `start_recording` (rejected: schedule-then-start, as the player); the range-minimum hang in the event bound whenever a hang change is pending (the simpler alternative to the precise minimum; rejected as needlessly loose).
- **D7:** the protocol of specs 011 – 016.
- **D8 alternative:** a one-sentence amendment of A-021 recording the mid-recording unknown (the coach's default; rejected for the cheaper direct citation of S-001, which is the sentence the note rests on; the register row would read "amended" and the cross-check would run).
- **D9 alternative:** a linear-in-dB glide (rejected: spec 011's smoothstep on the linear gain is the engine's one transition shape; a dB glide needs an exponential per sample).
- **D10 alternative:** guide text only for k(P) and the clock rule (rejected: the Swift package and spec 020 should read the engine's rule, not re-derive it). *Spec 020 (2026-10-31) delivered the clock maps: `timeline::input_to_kept` and `onepass_output_to_input`.*
