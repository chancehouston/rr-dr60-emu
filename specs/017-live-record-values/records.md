## Guide: a paragraph inside "Scheduled changes and the change log", after "The two streams and their clocks"

> **The record side (since 0.17).** Eight record-side values can be scheduled too: the microphone sensitivity, the pause threshold, the pause delay and the resume delay (stage 5), the limiter's threshold, attack and release (stage 3) and the hiss level (stage 1). They are positioned in the stream's **input clock**: the host input samples the recorder has processed since `start_recording` (the **record stream**, `Stream::Record`), or the one-pass has processed since construction, `reset` or `reconfigure`; `input_position(stream)` reads either. A control whose paths include "record" uses the input clock; one whose paths include "playback" uses the output clock, so the one-pass carries both and each entry's control says which. The limiter's values land on exactly input sample P with the hold capacitor's charge carried, as a resistor changed while the circuit runs; the hiss level moves to its new value over 20 ms from P (the noise itself is unchanged); the sensitivity, threshold and the two delays take effect at the first device sample derived from input sample P, the running counts kept. A landed value shows in `settings()`. The record schedule is kept by `start_recording` and cleared by `stop_recording` after the flush, so a change scheduled at position 0 while stopped lands on the first sample of the next recording, and one scheduled during a recording at a position already passed lands on the next input sample. **On the device the sensitivity is set with the MODE SELECT switch while the recorder is stopped (S-001); the manual does not say whether a unit accepts a change during a recording, and the other seven values are the model's constants. Changing any of them while recording is a feature of the emulator's API, not a device behavior:** no assumption is registered, no model version moves, and with no record-side change scheduled every output is bit-identical to 0.16.

Insert after "…so the one-pass carries both and each entry's control says which": (`changes::clock_of(control)` answers input or output for any control; `changes::record_landing(P, rate)` gives the device sample ⌈P · 6000 ÷ rate⌉ at which a gate value scheduled at input P takes effect, P itself at 6 kHz).

Also: read `input_position(Record)` just before stopping: it is the index of the last microphone sample plus one, entries at or past it landed inside the flush (the raw capture has no sample there), and the stop report's final input position minus it is the flush's length in host samples; a pending record-side change is not shown by `settings()` until it lands (read `pending_changes(Record)`); a change scheduled while stopped is logged at position 0 of the next recording; a change landed on the recorder reaches the one-pass at the one-pass's first call after the recording ends (the one-pass is refused while a path is active) and is logged there with the landing's tag, where a playback-side change mirrored since 0.16 is logged with tag 0 (D4; the two rules align at spec 020's ABI pass).

## CHANGELOG 0.17.0

> - **Scheduled record-side changes** (spec 017, 2026-11-xx; version 0.17.0; no audio change). Eight record-side values (`vas.sensitivity`, `vas.threshold_dbfs`, `vas.hang_ms`, `vas.onset_ms`, `agc.knee_dbfs`, `agc.attack_ms`, `agc.release_ms`, `mic.hiss_offset_db`) can be scheduled on the **record stream** (`Stream::Record`, reserved by 0.16) and the one-pass stream at a position in the stream's **input clock** (host input samples since `start_recording`, or since construction, `reset` or `reconfigure`; `input_position` / `rr_dr60_input_position`), validated as the setting is, and land as stated in the guide (the limiter's coefficients at sample P with the capacitor's charge carried; the hiss gain over a 20 ms smoothstep from P; the gate's values at the first device sample derived from P, counts kept). The record schedule is kept by `start_recording` and cleared by `stop_recording` after the flush; entries are reported by `record_with_changes` / `rr_dr60_record_with_changes` and, for the flush, `stop_recording_with_changes` (the count an out-parameter in C; the report structs unchanged); the one-pass's `process_with_events_and_changes` carries both sides, each control in its own clock. `changes::MAX_CHANGES_PER_CALL` / `RR_DR60_MAX_CHANGES_PER_CALL` moves **67 → 131** (two schedules of 64 plus the three plain setters; a host that sizes by the constant recompiles; one that hard-coded 67 still receives the first 67 entries and the true count, and truncates only in a one-pass call that lands more than 67 changes). New: `changes::Clock { Input, Output }` and `changes::clock_of(control)` / `rr_dr60_clock_of` (the clock a control is positioned and logged in, from its manifest paths), `changes::record_landing(P, rate)` / `rr_dr60_record_landing` (the device sample ⌈P · 6000 ÷ rate⌉ at which a gate value scheduled at input P takes effect), `input_position(stream)` / `rr_dr60_input_position`; `Error::NoSuchClock` (C status 29 `NO_SUCH_CLOCK`) for `stream_position(Record)` and `input_position(Playback)`; `StopOutcome` gains the recording's final input position (`input_samples_total`; in C an out-parameter of `rr_dr60_stop_recording_with_changes`). The real-time list gains the five calls. `settings()` reflects a landed value; no new setter. The control manifest's eight entries read timing **live** (kinds unchanged; canonical text re-blessed once). **A feature of the emulator's API, not a device behavior:** the device's sensitivity is set with MODE SELECT while stopped (S-001) and the manual does not say whether a change is accepted during a recording; no assumption is registered, no model version moves; with no record-side change the eleven audio golden files, their SHA guards and every smoke hash are unmoved; the stage manifest's canonical text moved in its version line only.
