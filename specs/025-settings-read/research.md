# Research: The Settings Read and Control Access by Index

The plan reviews (coach 1 – 14, hardware B1 – B9, product M1 – M5; 2026-11-01) are applied below; each restatement of the approved spec is dated in its Clarifications.

## R-01 The mapping and its exhaustiveness

**Decision**: `control_map.rs` holds `const TARGETS: [Target; CONTROL_COUNT]` in the manifest's order, read in O(1) by index (no string match on a call): `Target::Setting(SettingAccess)` (one variant per settings field, 26) or `Target::Live(LiveControl)` (route, volume, speed level, speed mode, battery). Exhaustiveness, closed three ways: (a) a core test asserts `controls()[i].identifier == TARGETS[i].identifier()` for every index, catching a new manifest entry, a reordered entry and a renamed identifier; (b) `fn _exhaustive(s: &Settings)` destructures `Settings` and its five sub-structures with no `..` (legal inside the core crate, where `#[non_exhaustive]` does not apply) and names each field's `SettingAccess` variant, so a new settings field fails to compile; (c) a core assertion that the number of `SettingAccess` variants equals the manifest's setting entries (26), so a field cannot be silenced with `_`. `get`/`set` are exhaustive `match`es on the variant. The option values of `Tap`, `VasMode`, `Route` and `SpeedMode` map by exhaustive matches (no wildcard; `fill_settings`'s `_ => 5` is not reused), each arm pinned against the manifest's `ControlOption.value`. The validator's field: the core's `error::Setting` (10 variants) maps by `setting_control(Setting) -> u32`, an exhaustive match; the C `rr_dr60_setting_field_control(uint32_t field, …)` takes the raw `u32` (a Rust enum parameter would make 99 undefined behavior) and maps the twelve meaningful `RR_DR60_SETTING_FIELD_*` values (host rate, tap, vas mode and the range-checked fields); 0, 3, the retired 5 and 6, and any unknown value return `NO_SUCH_CONTROL`; the test walks every value in the header.

**Rationale**: the draft's identifier `match` cannot be wildcard-free (a `&str` match needs `_`) and would scan strings per call; the table indexed by position with the three checks is O(1) and catches every kind of drift.

## R-02 The reading type and its C layout

**Decision**: Rust `enum ControlReading { Switch(bool), Integer(u64), Continuous(f32), Choice(u32) }` (`Copy`, `PartialEq`). C `RrDr60ControlReading { uint32_t struct_size; uint32_t value_type; uint64_t int_value; float float_value; uint32_t reserved; }`: offsets 0 / 4 / 8 / 16 / 20, 24 bytes, 8-aligned, no implicit padding, pinned by const assertions; the Rust declaration's `value_type` is `u32` (compared against `RrDr60ControlValueType`'s values) and the structure holds only integers and floats ("no bool or enum fields ever": a const-asserted comment), so a typed `read_unaligned` copy of a caller's reading is sound for every bit pattern. Published layouts `[24]` under spec 022's `write_sized`. **The reading is not added to the `--abi` rows, `examples/abi_rows.rs` or the Swift ABI fixture**: those are frozen by `scripts/abi-promise.sh`'s byte diff against 0.22's and 0.90's smoke; its size and offsets are printed by the new `--settings` mode and pinned in `abi_tests` (the spec's D11 narrowed; dated).

## R-03 The field-local C write and the in-place read

**Decision**: `rr_dr60_set_settings_control_value(settings, index, reading)`: the settings size read by `struct_size_at` (never `check_struct_size`, which forms `&RrDr60Settings`), equal to the settings size or refused; the reading's size read the same way (24 … 4096), the first 24 bytes copied by `read_unaligned`; the target field accessed through `&raw mut (*settings).field` with `write_unaligned` (and `read_unaligned` for reads: the caller's buffer may be unaligned); a switch written through `*mut bool` (sound, stores 1 or 0) and read through `cast::<u8>()`, refused unless 0 or 1; `tap` and `vas_mode` are `uint32_t` in the C struct, so a stored 99 is no undefined behavior and the repair case is sound. **Integers are refused above the Rust field's width** (u8 for the sensitivity, u32 for the memory fields, u64 for the seed), whatever the C field's width (the C sensitivity is `uint32_t`; 256 is refused). `rr_dr60_get_settings`: `struct_size_at(out) == SETTINGS_SIZE` first, then the existing `write_sized(out, &[SETTINGS_SIZE], |t, _| fill_settings(t, s))`, the path Miri already proved. The Miri gate gains the new functions' tests, including a switch byte of 2 read by index (refused).

**Out of scope, recorded**: `to_settings`/`check_struct_size` form `&RrDr60Settings`, so a caller's settings structure with a `bool` byte of 2 is undefined behavior in create, validate and reconfigure (pre-existing since 0.1). The guide gains a sentence ("C callers store 0 or 1 in `bool` fields"); the fix (switches read as `u8`, an appended field code) is queued for the next ABI-touching feature.

## R-04 The conversion to the five setters

**Decision**: the reading maps directly to each setter, never through an f64 round trip: `Continuous(v)` → `set_volume(v + 0.0)` / `set_battery_volts(v + 0.0)` (−0.0 normalized by index; the plain setters keep their own behavior, documented); `Integer(n)` → `u8::try_from(n)` (else `INVALID_ARGUMENT`, representability) → `set_playback_speed`; `Choice(c)` → an exhaustive match to `Route` or `SpeedMode` (else `INVALID_ARGUMENT`). **Reachable setter statuses by index**: `INVALID_VOLUME` (a finite position outside 0 … 1), `INVALID_SPEED_LEVEL` (an integer 0 or 6 … 255), `INVALID_BATTERY_VOLTS` (finite, out of range). A level above 255, a non-option route or mode, and a non-finite value are `INVALID_ARGUMENT`; `INVALID_SPEED_MODE` and a route status are unreachable by index (the spec's D7 narrowed; dated). By index a NaN volume returns `INVALID_ARGUMENT` where the plain `rr_dr60_set_volume` returns `INVALID_VOLUME`, documented. `reading_value` → f64 exists only for the schedule twin of the tests.

## R-05 What the read holds

**Decision**: `Pipeline::settings()` unchanged: the last value set or landed on any stream (spec 017's mirror; spec 021's switches at their target during a blend); a stream applies it from its next produced sample (the one-pass at its next call's first sample; the recorder adopts at `start_recording`); an unlanded scheduled change is absent. The guide states it; US1 AS3 pins it.

## R-06 The refusal order

**Decision**, nothing written on any refusal. Handle functions (`get_settings`, `control_value`, `set_control_value`): `live(pipeline)` first (NULL or poisoned, spec 022's rule, as `rr_dr60_get_volume`), then the out or reading pointer (NULL), its size, the index (`NO_SUCH_CONTROL`), the class (`NOT_A_SETTING` / `NOT_A_PLAIN_LIVE_CONTROL`), representability (`INVALID_ARGUMENT`), the setter's status (R-04). Pure functions (`settings_control_value`, `set_settings_control_value`): the pointers (NULL), the settings size, the reading or out size, the index, the class, an invalid stored value (on read: a switch byte other than 0/1, a choice not an option) or representability (on write). `setting_field_control`: the out pointer, then the field (`NO_SUCH_CONTROL`). Each function joins `abi_tests`' matrix with a poisoned handle where it takes one. The Rust errors: `Error::NotASetting { control: u32 }`, `Error::NotAPlainLiveControl { control: u32 }` (the house field name), representability `Error::InvalidControlValue { control, value }` with `value` the reading's number as f64 (NaN for a wrong-type reading).

## R-07 The oracles and the mutants

**Decision**:
- **The Rust one-hot is a core test** in `control_map.rs` (the harness cannot destructure the `#[non_exhaustive]` structures): for each settings index, from the defaults, write the index's unique non-default value (a switch flipped; a continuous index + 0.5 within its range or the nearest representable; an integer index + 2 within the width; a non-default option), destructure `Settings` exhaustively in the test source with a literal identifier per field, assert exactly one field changed and its literal is the manifest's identifier (D5 restated: a core test; dated).
- **The C one-hot** (`us2_one_hot_c`, the harness through the FFI): `RrDr60Settings` is a plain `repr(C)` struct the harness can build by field name; for each index the bytes after the write equal a struct set by name; the buffer is painted 0xAA outside the fields (a raw aligned `[u8; 120]`) and every byte outside the target field must survive (this, not `tap = 99` alone, catches a whole-structure round trip). `smoke --settings`: per index, the identifier and the changed byte offsets from `offsetof` (the C compiler names the field), diffed against `examples/settings_rows.rs` (`offset_of!`), on `rr_dr60_settings_default(48000)`; `--settings` is not added to the promise script's mode loop (neither old revision knows it).
- **The live rows**: the conversion and status rows of R-04 are the oracle; the log identity is a corroboration: the set-by-index, the plain setter and a schedule with tag 1 at `stream_position(stream)` on each stream the control exists on (route, volume, battery: playback and one-pass; speed and mode: playback), tap `RouteOutput`, during a playback at block size 1; entries equal in position, control, before, after and stream (the tag 0, 0, 1); the −0.0 difference of the plain setter pinned.
- **Mutants**, under `__test-hooks` on the pure functions (`control_map::__hooks::{settings_value_with, set_settings_value_with}(MapMutation, …)`; the public functions call the `None` variant; off the audio path): index i → field of i + 1; attack ↔ release; speaker ↔ earphone; a too-wide integer wrapped (`as u8`, tested with 259, which wraps to the valid level 3) instead of refused; the setter's validation bypassed (restated 2026-11-01: the wide-integer wrap on the speed level by index); the default instead of the live value. In the FFI crate a `#[cfg(test)]` whole-structure round-trip variant, caught by the painted repair case. "A landing not mirrored" folded into spec 017's landing branch, never a per-sample compare.

## R-08 The record's table rebuilt

**Decision**: `record.rs`'s `get`/`set` call the mapping for its 24 lines; `SETTING_IDS` (24) stays the record's filter ahead of the mapping, so a `seed`, `host_rate_hz` or `route` line in the settings block still raises the unknown-name flag (a test pins it); the text formatting unchanged; `golden-record-v1.json` byte-identical (its guard); `setting_table_matches_the_manifest` restated on the mapping.

## R-09 The Swift wrapper

**Decision** (the product review's M1, M3): in `RRDR60`, `public enum ControlReading: Equatable, Sendable { case \`switch\`(Bool), integer(UInt64), continuous(Float), choice(UInt32) }` with `init?(_ c: RrDr60ControlReading)` and `var c: RrDr60ControlReading`; `init?(defaultOf index: UInt32)` (nil for the host rate, which has no default, and for an index past the count); `struct ControlIndex: RawRepresentable, Hashable, Sendable { init?(identifier:) }`; throwing wrappers around all six calls: `controlValue(_ pipeline: OpaquePointer, index:) throws -> ControlReading`, `setControlValue(_:index:_:) throws`, `appliedSettings(_:) throws -> RrDr60Settings` (sets the size itself), `RrDr60Settings.value(index:) throws -> ControlReading` and `.setValue(index:_:) throws`, `controlIndex(forField:) -> ControlIndex?`; `RRDR60Error.status(Int32)` for non-ABI statuses. `RrDr60ControlReading: RRDR60Sized`. A Swift test reads every default and runs the one-hot round trip through the wrappers.

## Restatements at implementation (2026-11-01)

- **R-07, the mutants**: "the setter's validation bypassed" is implemented as the wide-integer wrap on the speed level by index (259 → level 3 accepted), caught by the representability row; `Pipeline`'s fields are private to its module, so a mutant cannot bypass a setter's own check from `control_map`. "A landing not mirrored" is not a separate mutant: spec 017's and 021's mirror tests already pin it, and `us1_settings_read_landed` reads it. The whole-structure round trip is the FFI crate's `whole_struct_round_trip_mutant_is_caught`. The harness's mutation module has five mutants with named oracles.
- **R-07, the Rust one-hot** is the core test `control_map::tests::one_hot`; the harness's `mutation::settings_read` reaches the Rust write through the C structure (`configs::c_settings`) and the field assignment by name, which needs no destructure.
- **T004's placement**: `Pipeline::control_value` and `set_control_value` are in `control_map.rs` (an `impl Pipeline` block beside the mapping), not `pipeline.rs`.
- **R-08, the record's −0.0**: the record's round trip keeps a −0.0 value's sign (an internal `keep_sign` flag on the mapping's write); a set by index stores 0.0 as D3 states.
- **D11, the guide's paragraph**: records.md's text plus one sentence ("A read back confirms a `reconfigure` exactly; that a live value took effect is confirmed by its change-log entry, …") so the wording check's "read back" and "confirm" hold; the README has no list of C functions (the guide carries the API), so only its stale version line moved.
- **The Swift package**: the test-only `RRDR60.abiOverride` is `@TaskLocal`; set globally it leaked into the parallel `ControlReadingTests` (and could into the re-render tests).
