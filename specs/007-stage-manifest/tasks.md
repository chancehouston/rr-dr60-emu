# Tasks: Stage Manifest

**Input**: Design documents from `specs/007-stage-manifest/`: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/) (rust-api, c-api, cross-check), [quickstart.md](quickstart.md).

**Tests**: REQUIRED. Constitution III says tests are written first and must fail before the implementation exists. Every story phase lists its tests before its implementation tasks. "Fail first" has two shapes here: the story tests fail because the module, the check or the C functions do not exist yet; the doctored-input tests (US2) are the proof that the guard itself works.

**Organization**: Setup → US1 (P1, MVP: the manifest in the core, read from Rust) → US2 (P2: the register edits, the cross-check, the canonical text, CI) → US3 (P3: the C surface) → String reviews → Records → Polish and the final reviews. The order follows plan.md › "Phase order and conventions for `/speckit-tasks`".

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependency on an incomplete task)
- **[Story]**: The user story the task belongs to (US1 – US3)
- Paths are relative to the repository root.

## Conventions that apply to every task

- **Traceability**: cite spec 007 FR, SC and S-/A-IDs in code comments, rustdoc and test names, e.g. `// A-026: 6 kHz device rate`, `// 007 FR-004: status rule`, `// 007 FR-011: denylist (docs/product/front-and-inside.md)`. Constants that are not device properties are commented `// engineering target (007 FR-0xx)`; the list is research R-10. Harness results and findings cite requirements as `007/FR-0xx`.
- **No DSP change**: no task touches `paths.rs`, `stages/`, `memory.rs`, `transport.rs`, `pipeline.rs`, `rate.rs` or `settings.rs` (except a doc comment). **The golden JSON window is closed**: `golden`, `golden_agc`, `golden_vas` and their SHA guards must stay green through every task, and no task may touch `crates/rr_dr60_harness/golden/*.json`. A moved hash is a defect, never a re-bless (FR-018).
- **Never weaken a rule to make a string pass**: never lengthen a length limit (24 / 48 / 160 / 120 / 120 / 160 / 200 characters), drop a denylist stem or phrase, widen the parser or loosen a cross-check rule. Reword the string. A bound change is a spec Clarification, decided by the user.
- **Strings are sourced properties only** (FR-010): a description or coverage note may state only what an `S-###` row supports; assumed figures and behaviors stay in the registers. The string reviews (Phase 5) are the judge; the tests are the gate.
- **Story boundaries (Principle VII)**: `us1_manifest.rs` reads only `rr_dr60::manifest()` (no register files, no engine); `us2_cross_check.rs` reads the manifest plus the four texts and doctors copies; US3 compares C with Rust. No story test depends on another story's harness code beyond `manifest_checks.rs`'s renderers.
- **Real-time safety**: every manifest read, Rust or C, allocates nothing and does no I/O; `alloc_free` asserts it (T031). The renderers and parsers live in the harness and may allocate.
- **Before ticking a task**: `cargo fmt --all -- --check`, `cargo clippy --all-targets --all-features -- -D warnings` and `cargo test --all-features` must pass (inside a story's test-first window, that story's new tests are the expected red).
- **Commits**: Conventional Commits, on branch `007-stage-manifest`, after each task or logical group. Merge to `main` only through a green PR, and only after the user says so.

## Implementation Strategy

### MVP first (User Story 1)

1. **Phase 1**: version and baseline. Stop at the checkpoint.
2. **Phase 2**: the tests, then the module in four steps (types, content, assertions, twin table), the re-exports and the example. Stop at the checkpoint, demo the example's output. This is the MVP: an app can already generate its view from Rust.

### Incremental delivery

1. **US2**: the register edits, then the check, the golden text, the workflow and the script block. Validate by the seven doctored inputs.
2. **US3**: the C surface and the smoke diff.
3. **String reviews**, then **Records**, then **Polish**, the PR, CI, the two final reviews and the merge, with the user's approval at the PR and at the merge.

### Risk notes

- **The content is the deliverable.** A string that reads well but states an assumed property (a knee position, a release time, an enclosure) is a defect even if every test passes; Phase 5 exists for that. When in doubt, say less.
- **Lengths**: the longest strings today are stage 3's description (144 characters) and stage 5's controls note (118). A review that wants more words must cut elsewhere, not raise a limit.
- **The parsers are literal.** A register edit that adds a column, puts a `|` in a cell or renames a status word fails the check loudly; that is the design. Fix the register, not the parser, unless the convention itself changes (a spec Clarification).
- **The canonical text is a golden.** Any string change re-blesses `manifest-v1.txt` and the README regions, with a CHANGELOG line (FR-015).
- **CI**: the PR runs both workflows; a later docs-only PR runs `registers` alone. Do not mark `registers` as a required check (research R-06).
- **Honesty**: "modeled on", "not checked against a real unit", "the engine leaves out …", never "verified", never a claim about recordings.
