# Research: Stage Manifest (feature 007)

Decisions for feature 007. The feature adds data and tests, not signal processing: nothing here touches `paths.rs`, the stages, the memory or the transport, and the three golden files stay byte-identical (spec FR-018). Figures below were checked on 2026-10-12 against the committed registers (`docs/hardware/assumptions.md` A-001 – A-039, `docs/hardware/sources.md` S-001 – S-007, `docs/hardware/signal-chain.md` rows 1–15) and the committed code (`lib.rs`, `settings.rs`, `rr_dr60_ffi/src/lib.rs`, `ci.yml`).

## R-01 The manifest as constant data in the core (FR-001 – FR-003, FR-016; spec Assumptions "new fields")

- **Decision**: a new module `crates/rr_dr60/src/manifest.rs` holds one `static MANIFEST: Manifest` built from a single macro invocation, `stage_table!`, that lists the fifteen stages once (number, identifier, name, description, status, path, confidence, sources, assumptions, coverage note, controls note, model version). The public types:
  - `#[non_exhaustive] pub struct Manifest { pub header: Header, pub stages: [StageEntry; 15] }`;
  - `#[non_exhaustive] pub struct Header { pub library_version: &'static str, pub device_rate_hz: u32, pub stage_count: u32, pub counts: StatusCounts, pub basis: &'static str, pub evidence_link: &'static str, pub assumptions_link: &'static str, pub sources_link: &'static str }`;
  - `#[non_exhaustive] pub struct StatusCounts { pub not_modeled: u32, pub assumed: u32, pub sourced: u32, pub checked: u32 }`;
  - `#[non_exhaustive] pub struct StageEntry { pub number: u8, pub identifier: &'static str, pub name: &'static str, pub description: &'static str, pub status: StageStatus, pub path: StagePath, pub confidence: Confidence, pub sources: &'static [&'static str], pub assumptions: &'static [&'static str], pub coverage: &'static str, pub controls: &'static str, pub model_version: &'static str }`;
  - `#[non_exhaustive] pub enum StageStatus { NotModeled, Assumed, Sourced, Checked }`, `#[non_exhaustive] pub enum StagePath { Record, Playback, Both }`, `#[non_exhaustive] pub enum Confidence { NotApplicable, Low, Medium, High }`; all `Copy, Clone, Debug, PartialEq, Eq` (the enums also `Hash`).
  - Access: `pub fn manifest() -> &'static Manifest`, `Manifest::header(&self)`, `Manifest::stages(&self) -> &[StageEntry]`, `Manifest::stage(&self, number: u32) -> Option<&StageEntry>` (None for 0 or > 15), `StageEntry::has_sources()`-style helpers are not added (YAGNI). Re-exported at the crate root with the module public as `rr_dr60::manifest`.
- **Why `#[non_exhaustive]` on the structs**: a later feature adds a field as a minor change (spec Edge Cases "new fields"); hosts read fields and never construct the structs. The harness can still mutate a **copy** of the `Copy` value field by field, which is how the doctored-manifest test (US2 scenario 7) is built: `let mut m = *rr_dr60::manifest(); m.stages[2].confidence = Confidence::High;` — field assignment is allowed on a non-exhaustive struct, only literal construction is not.
- **Counts at compile time**: `StatusCounts` is computed by a `const fn` loop over the fifteen entries, so the header's counts cannot disagree with the entries inside the core (FR-013 (f) is still re-checked by the harness against the register-derived statuses). The header's `library_version` is `crate::VERSION` and `device_rate_hz` is `settings::DEVICE_RATE_HZ` (A-026), so neither is typed twice.
- **Compile-time invariants** (`const _: () = assert!(...)` with small `const fn` helpers, no `unsafe`): exactly fifteen entries numbered 1..=15 in order; identifiers ASCII `[a-z0-9_]`, 1..=24 bytes, unique; `name.len() <= 48`, `description.len() <= 160` ending in `.`, `coverage.len() <= 120`, `controls.len() <= 120`, `basis.len() <= 160`, each link `<= 200`; a `NotModeled` entry has `confidence == NotApplicable`, empty `model_version` and empty `coverage`; a modeled entry has a non-empty `model_version` and `confidence != NotApplicable`; ID lists ascending and well-formed (`A-` or `S-` plus three digits). These are the form rules of FR-002 and FR-003 that need no register; the build fails on a typo before any test runs. Lengths are bytes, which is stricter than the spec's characters for the non-ASCII strings (µ, Ω are two bytes), so the spec's limit holds whenever the assertion does.
- **Strings for C** (FR-017): the same macro also emits, for every string, a NUL-terminated twin as `&'static [u8]` (`concat!($lit, "\0").as_bytes()`) into a `#[doc(hidden)] pub mod __c` table: `__c::HEADER` and `__c::STAGES: [StageEntryC; 15]` with `&'static [u8]` fields and `&'static [&'static [u8]]` ID lists. The core needs no `unsafe` and no raw pointers (statics holding `*const c_char` would need `Sync`, which the core's `#![forbid(unsafe_code)]` cannot provide). The FFI casts `bytes.as_ptr().cast::<c_char>()` at call time; the pointee is a `'static` literal, so the pointer is valid for the life of the process. A unit test in the core asserts that every twin equals its `&str` plus one trailing NUL, so the two tables cannot drift.
- **Alternatives**: `&'static CStr` fields via `c"..."` literals (available since 1.77, within the MSRV) with `to_str()` for Rust callers (rejected: a non-idiomatic Rust surface and a runtime UTF-8 check per read); a `Text` newtype carrying both forms (rejected: a wrapper type on every field for the sake of C); `build.rs` generation from the Markdown registers (rejected: the registers would become build inputs of a `no_std` crate, and the Markdown parser would live in the build, where the drift it is meant to catch would be invisible; the spec wants the manifest hand-written and *checked*); a `const fn` that trims a NUL at runtime (rejected: needs `from_utf8` on every access or `unsafe`).

## R-03 The C surface (FR-017; contracts/c-api.md)

- **Decision**: five functions, two output structs, three enums and one status code, all appended; no existing symbol changes.
  - `uint32_t rr_dr60_manifest_stage_count(void)` → 15.
  - `RrDr60Status rr_dr60_manifest_header(RrDr60ManifestHeader *out)`: copies the header (`NULL_POINTER` on NULL).
  - `RrDr60Status rr_dr60_manifest_stage(uint32_t number, RrDr60StageEntry *out)`: `NO_SUCH_STAGE` (new code **20**) for 0 or > 15 with no write; `NULL_POINTER` on NULL.
  - `RrDr60Status rr_dr60_manifest_stage_source(uint32_t number, uint32_t index, const char **out_id)` and `rr_dr60_manifest_stage_assumption(...)`: the i-th ID (0-based) of the stage's list; `NO_SUCH_STAGE`, then `INVALID_ARGUMENT` when `index >= count`; the entry struct carries `source_count` and `assumption_count`. This is "every ID of a stage reachable by index" without a static array of pointers (which would need an `unsafe impl Sync` in the FFI crate for no gain).
  - `RrDr60ManifestHeader { const char *library_version; uint32_t device_rate_hz; uint32_t stage_count; uint32_t count_not_modeled, count_assumed, count_sourced, count_checked; const char *basis; const char *evidence_link; const char *assumptions_link; const char *sources_link; }` and `RrDr60StageEntry { uint32_t number; const char *identifier, *name, *description; uint32_t status, path, confidence; uint32_t source_count, assumption_count; const char *coverage, *controls, *model_version; }`, both `repr(C)`; the enums `RrDr60StageStatus { NOT_MODELED = 0, ASSUMED = 1, SOURCED = 2, CHECKED = 3 }`, `RrDr60StagePath { RECORD = 0, PLAYBACK = 1, BOTH = 2 }`, `RrDr60Confidence { NOT_APPLICABLE = 0, LOW = 1, MEDIUM = 2, HIGH = 3 }` as `repr(u32)` with the fields typed `uint32_t` (the existing convention: `RrDr60EngineState.state` is a `uint32_t` holding `RrDr60State`).
  - Every string pointer is non-NULL, NUL-terminated UTF-8 into the core's `__c` table (R-01), valid for the life of the process; an empty note is `""`, never NULL. Nothing allocates; the functions are real-time safe and are listed as such in the header comment; none takes a handle, so they can be called before any `rr_dr60_create`.
  - Struct growth: like `RrDr60Settings`, the two output structs grow only at the end, and before 1.0 that is a minor change for C callers who recompile (the contract says so); after 1.0 a new field would come with a new accessor instead. Layout tests pin the sizes and offsets (`RrDr60ManifestHeader` 64 bytes and `RrDr60StageEntry` 80 bytes on 64-bit targets, 44 and 48 on 32-bit: four pointers plus six `uint32_t` in the header, six pointers plus eight `uint32_t` with two padding gaps in the entry; asserted through `size_of::<usize>()` arithmetic like `transport_struct_layouts`).
- **Alternatives**: pointer-to-static entries (`const RrDr60StageEntry *rr_dr60_manifest_stage(n)`; rejected: a static table of raw pointers needs `unsafe impl Sync`, and the copy-out form matches every other output of the API); ID lists as one comma-separated string (rejected: parsing on the C side); a JSON string (rejected by clarify Q3).

## R-04 The cross-check (FR-013; contracts/cross-check.md)

- **Decision**: a harness module `crates/rr_dr60_harness/src/manifest_checks.rs` with
  - `pub struct Registers<'a> { pub sources: &'a str, pub assumptions: &'a str, pub signal_chain: &'a str, pub changelog: &'a str }` and `pub fn committed_registers() -> Registers<'static>` that reads the four files from the repository root (`env!("CARGO_MANIFEST_DIR")/../..`) at test time (the harness is `std`; the core never sees them);
  - `pub fn cross_check(manifest: &Manifest, registers: &Registers) -> Vec<Finding>` where `Finding { rule: Rule, stage: Option<u8>, id: Option<String>, detail: String }` and `Rule` is one variant per FR-013 clause (a)–(h) plus `Parse`; the check never panics on malformed input, it reports;
  - `pub fn wording_findings(manifest: &Manifest) -> Vec<Finding>` for FR-002/FR-003 form and length rules (characters, not bytes, so the spec's limit is what is tested) and the FR-011 denylist, which lives as `pub const DENYLIST_STEMS: &[&str]` and `pub const DENYLIST_PHRASES: &[&str]` at the top of the module with the product note cited, applied to every string of the header and the entries (names, descriptions, notes, basis; identifiers and links too, trivially);
  - the register **parsers**: Markdown table rows are lines starting with `|`; cells are split on `|` and trimmed (no cell in the three registers contains a literal pipe; the parser reports `Rule::Parse` if a row has the wrong cell count). Assumptions: rows whose first cell matches `A-\d{3}`; columns ID, Stage, Assumption, Rationale, Confidence, How to verify, Status. Sources: rows `S-\d{3}`; columns ID, Source, Type, Reliability, Key facts. Signal chain: rows whose first cell is an integer; columns #, Stage, Identifier (new, R-07), Known, Assumed, Character; "modeled" = the row text contains `**Modeled by`. CHANGELOG: plain text searched for the version string as a whole token.
  - **Status classification** of an assumption's Status cell (FR-004): lowercase, trim; `superseded*` → Superseded; `verified*` with no `A-\d{3}` anywhere in the cell → DocumentVerified; `measured*` → Measured; otherwise Open. `adopted*` or `revised*` → AdoptedOrRevised (a flag beside the class). **Headline confidence**: the first match of `(?i)\b(high|medium|low)\b` in the Confidence cell; a cell without one (the superseded rows have "—") is Unknown and only matters if cited, which (b) already fails.
  - The **denylist matcher**: for each stem, the regex `(?i)\b{stem}(s|es|ed|ied|ies|y|ying|ing|ion|ions|or|ors)?\b`; for each phrase, `(?i)\b{phrase}\b`. The suffix set is a superset of the spec's (s, es, ed, ing) so that "verified", "detection", "detector", "entities" and "anomalies" are caught; stricter is allowed because the committed strings pass (stage 3's description says "peak-following circuit", not "peak detector"). "sensitivity" is not matched by the stem `sense` (the suffix set has no `itivity`). Implemented with the `regex` crate (a new dev-time dependency of the harness only; the core gains nothing).
  - **Semantic version compare** for (g): split on `.`, three integers, lexicographic; the library's own version is `rr_dr60::VERSION`.
- **Tests** (`crates/rr_dr60_harness/tests/manifest.rs`): the committed registers pass with zero findings (US2 scenario 1); each of the seven doctored inputs (US2 scenarios 2–7 and the row-removed variant) yields at least one finding of the expected `Rule` naming the expected stage and ID (SC-002: 7 of 7); the wording findings are empty on the committed manifest (SC-003); the US1 scenarios (fifteen entries, counts, identity across reads); plus the parser's own unit tests on small inline tables. The doctored register texts are made by string replacement on the committed texts inside the test (`replace("| A-028 |", ...)`, appending a row, deleting a row), so they track the real files.
- **Alternatives**: a Markdown crate (rejected: three tables with a fixed shape; a line splitter is 40 lines and reports its own failures); `include_str!` of the registers (rejected: a doc edit would then need a rebuild of the harness to be seen, which `cargo test` does anyway, but runtime reads keep the file list in one function and allow the doctored copies to be plain strings); running the cross-check in the core's unit tests (rejected: the core is `no_std` and must not read files).

## R-05 The canonical rendering, the README table and the examples (FR-019, SC-001, SC-004)

- **Decision**: one canonical plain-text rendering serves three purposes.
  - `rr_dr60_harness::manifest_checks::render(manifest) -> String`: one line per header field (`key: value`), then one block per stage with every field, IDs comma-separated, in a fixed order; UTF-8, `\n` line ends.
  - **Golden text** `crates/rr_dr60_harness/golden/manifest-v1.txt`: the committed rendering. `tests/manifest.rs` compares `render(manifest())` to the file byte for byte; `RR_DR60_BLESS=manifest` rewrites it (the existing convention; a re-bless is a CHANGELOG-recorded content change, FR-015). The `determinism` test file gains the same comparison so the **golden-matrix** and **ios** CI jobs run it on their six desktop targets and the simulator (SC-004: identical on every CI platform).
  - **Example** `crates/rr_dr60_harness/examples/manifest.rs`: prints `render(manifest())`; the README's Rust snippet is the example's read loop (the README shows reading, not the renderer).
  - **C**: `crates/rr_dr60_ffi/tests/c/smoke.c` gains a `--manifest` mode that walks the header, the fifteen stages and their IDs through the five C functions and prints the same rendering with `printf`; `run_smoke.sh` diffs it against `cargo run -q -p rr_dr60_harness --example manifest` (SC-001: the two outputs identical; US3 scenario 1 is additionally asserted field by field in `ffi_parity.rs`). The smoke test's normal mode also checks `rr_dr60_manifest_stage(0)` and `(16)` → `NO_SUCH_STAGE` and that a kept pointer is unchanged after a create/destroy cycle (US3 scenarios 2, 3).
  - **README table** (FR-019): the "Fidelity status by stage" table is replaced by a table generated from the manifest, between `<!-- manifest-table:start -->` and `<!-- manifest-table:end -->` markers: columns #, Stage, Status, Confidence, Basis (the IDs), Not modeled here, Model version; the vocabulary is the manifest's. `manifest_checks::render_readme_table(manifest)` produces it; `tests/manifest.rs` asserts the README's marked region equals it; `RR_DR60_BLESS=readme` rewrites the region. The sentence above the table says the manifest is the canonical per-stage status and that this table is generated from it. The release checklist gains "the README table equals the manifest's output (`cargo test -p rr_dr60_harness --test manifest`)".
- **Alternatives**: a pinned digest (rejected: a hash tells a reviewer nothing; the text file shows the diff); keeping the hand-written README table and asking the release checklist to compare (rejected: untestable, the coach's C12).

## R-06 CI for register-only changes (FR-020, SC-007)

- **Decision**: a second workflow, `.github/workflows/registers.yml`, with one job `registers` on `pull_request` and `push` to `main` with `paths: [docs/hardware/**, CHANGELOG.md, README.md, crates/rr_dr60/src/manifest.rs, crates/rr_dr60_harness/src/manifest_checks.rs, crates/rr_dr60_harness/tests/manifest.rs, crates/rr_dr60_harness/golden/manifest-v1.txt, scripts/check-traceability.sh]`, `ubuntu-latest`, `rustup toolchain install`, `Swatinem/rust-cache`, then `cargo test -p rr_dr60_harness --test manifest` and `scripts/check-traceability.sh`. Expected 2–4 minutes warm. `ci.yml`'s `paths-ignore` is unchanged, so a register-only change runs this job alone and a code change runs both (the `check` job runs `--test manifest` too as part of `cargo test --all-features`, a cheap duplicate).
- **Gating**: the job's result gates the merge the way every CI job does here: through the PR's checks. Whether a check is *required* is a repository setting outside the tree (no job is marked required today; the user merges on green). The quickstart records how to add `registers` to the required checks if the user wants it; a required check that is skipped by its `paths` filter would block unrelated PRs, so the recommendation is to leave it unrequired like the others.
- **Alternatives**: removing `docs/hardware/**` and `**.md` from `ci.yml`'s `paths-ignore` (rejected: the 30-minute coverage job for a one-line register edit); a `paths-filter` step inside `ci.yml` (rejected: `paths-ignore` is workflow-wide, so the workflow would not even start).

## R-11 Risks

- **The register parsers are tied to the tables' shapes.** A new column in a register breaks the parser, loudly (`Rule::Parse`), which is the intended failure mode; the contract lists the expected columns so a register edit knows the rule.
- **Byte versus character lengths.** The core asserts byte lengths (stricter); the harness checks characters (the spec's rule). A string with many non-ASCII characters could pass the spec but fail the build; today the longest description is 142 bytes.
- **Required checks.** If the user later marks `registers` as a required status check, PRs that do not touch its paths will wait on a check that never runs; the quickstart notes the trade-off (R-06).
- **Future field additions in C.** Growing the output structs changes their size, which is a recompile for C hosts; the contract says the structs grow only at the end and that after 1.0 new data comes through accessors.
- **The denylist stem matcher is stricter than the spec's letter.** If a future legitimate word collides (for example "sensor"), the stem list is edited, not the matcher; the spec allows a stricter test as long as the committed strings pass.
