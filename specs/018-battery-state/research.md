# Research: Battery State (018)

## R-01: The control's plumbing

**Decision.** `battery_volts: f32` is a `Pipeline` field beside `route`, `volume` and `speed_level`, default `battery::DEFAULT_BATTERY_VOLTS` (3.0), kept by `reset` and `reconfigure` (carried into `with_memory`). `set_battery_volts(v)` validates (finite, within `BATTERY_VOLTS_RANGE` = 2.2 … 3.0 inclusive; `Error::InvalidBatteryVolts { volts }`, C status 30) and stores the value; like the volume it lands at the first sample of each stream's next producing call through spec 015's `StreamState::begin_call` (a fourth pending plain value) and is logged with tag 0 when it moved. `schedule_change` accepts `LIVE_BATTERY` = 29 (the control manifest's index of `battery_volts`, **appended** after the 0.14 entries so no existing index moves, pinned by a test; coach 1, hardware B15) on the playback and one-pass streams in the output clock, the value narrowed to f32 (`as f32 + 0.0`) and validated as the setter does; `Apply::Battery(f32)` reaches the chain's `set_battery(b)`. `start_playback`, `reset` and `reconfigure` take it as a start value (no entry). The readings follow landed values (`landed_battery`), so `battery_volts()` reads the most recently landed value on any stream.

`set_battery_volts` and the chain's `set_battery` are **idempotent against the target**: a request equal to the target volts returns early (the volume's `volume != self.target` rule), so the per-call plain apply never restarts a transition in flight (hardware B6). The apply point orders `Apply::Chain` before `Apply::Battery`.

**Rationale.** D1; the volume's path is blessed by `golden-changes-v1.json`, so every spec 015 oracle (the block-size-1 setter oracle, the partitions, the chaining) applies unchanged. Spec 014's order rule is restated: the 0.14 entries in their order, later entries appended (indices are stable; recorded for the pre-1.0 ABI pass).

**Alternatives.** A setting (rejected: live). A per-stream reading (rejected by 015 D5).

## R-02: The transition on the factor

**Decision.** `OutputChain` gains `batt: f64` (the factor in force), `batt_from`, `batt_to`, `batt_k: u32`, `batt_n: u32` (= `ramp_n`, the volume's N) and `batt_inv_n`. `set_battery(b)`: at once (`batt = batt_from = batt_to = b; batt_k = batt_n`) when the chain is fresh (the stream's first sample, spec 011's rule), when stage 11 is bypassed, when the route is the earphone, and at a route change (`reset_sections` marks the chain fresh, so the next `set_battery` is at once; a transition in progress ends at the switch by `batt = batt_to; batt_k = batt_n`); otherwise `batt_from = batt; batt_to = b; batt_k = 0`. `reset_sections` (a route change, `reset`) also ends a battery transition (`batt = batt_to; batt_k = batt_n`) and recomputes the thresholds, so a route change without a battery change completes one (hardware B9); a value taken at once on the earphone route is chain state and is in force when the speaker returns. Per speaker-route sample, before the knee: `if batt_k < batt_n { batt_k += 1; batt = if batt_k == batt_n { batt_to } else { batt_from + (batt_to − batt_from) · s(batt_k · batt_inv_n) } }` with s the smoothstep: the landing sample is transition sample 1, sample N exactly `batt_to`, no hold (b is interpolated directly, monotonic). The volume's `ramp_k` is untouched; the two transitions are independent.

**Rationale.** D4; hardware B4 of the spec review (a shared scalar under the running hold could freeze or reverse).

**Alternatives.** Folding 1/b into `k_spk` (rejected, B4). An instantaneous step (rejected, clicks on clipped material).

## R-03: The scaled clipper

**Decision.** `knee_b(x, k, b)`: `u = |x|`; `if u <= k·b { u } else if u >= (2 − k)·b { b } else { d = (2 − k)·b − u; b − d·d / (4·(1 − k)·b) }`, the sign restored. At b = 1.0 every branch reduces to `knee`'s (`k·1.0 = k` exactly, `(2 − k)·1.0` exactly, `4·(1 − k)·1.0` exactly, `1.0 − d²/…` identical), so the default is bit-identical: a core test asserts `knee_b(x, k, 1.0).to_bits() == knee(x, k).to_bits()` over a sweep. The thresholds `k·b` and `(2 − k)·b` and the parabola's denominator `4·(1 − k)·b` are recomputed by one `recompute_knee()` when `batt` changes (per transition sample, three multiplies), at construction, in `reset_sections` and in `__mutate` (the SC-006 knee mutant moves `knee_start`; hardware B8), and stored in the chain; the hot path at the default reads three fields where it computed `2 − k` and `4·(1 − k)` (loads only) plus one `batt_k < batt_n` compare. The denominator stays a divisor (a stored reciprocal is inexact at b = 1 and would move the goldens; hardware B7). No exact joint equality is pinned for b ≠ 1. Below `k·b` the sample passes untouched: FR-002's identity. The speaker branch applies `knee_b(k_spk · amp_hpf(u) + 0.0, k, batt)`; the earphone branch and every earlier stage are untouched (FR-004).

**Rationale.** D3; coach 4 and hardware B4 (scaling the sample breaks the identity).

**Alternatives.** `knee(x / b) · b` (rejected: not bit-identical below the knee; two multiplies per sample). The output scale following the ceiling (rejected by D3).

## R-04: The law and the public data

**Decision.** `pub mod battery` in the core: `pub fn ceiling_factor(volts: f32) -> f32 = ((f64::from(volts) − 1.8) / 1.2) as f32`, the register's form (A-056): in f64 `3.0 − 1.8` is exact and equals the double nearest 1.2, so the default is **exactly 1.0**, pinned by `ceiling_factor(3.0).to_bits() == 1.0f32.to_bits()` (hardware B7 checked every f32 in the range: this form and `(v − 3.0) / 1.2 + 1.0` agree after narrowing; the earlier `(v − 0.2) − 1.6` form is the one that rounds to 0.9999999999999998). The chain stores `batt = f64::from(ceiling_factor(volts))`, never a second computation, so the engine's factor and the published law agree to the bit. `pub fn ceiling_db(volts) -> f32 = 20·log10(ceiling_factor(volts))` through `rr_dr60_detmath::ln`. Both are total over finite inputs (the law is a formula; refusal belongs to the setter; coach 8). Constant data: `ALKALINE_TRAJECTORY: [(f32, f32); 7]` (hours of **recording** under S-001's load, volts; row 0 at 2.96 V is a loaded-cell reading and not the default: "fresh" is `DEFAULT_BATTERY_VOLTS` = 3.0, the nominal mark; product M2), `NIMH_PAIR_VOLTS: f32 = 2.45` (A-056's 2.4 – 2.5 V; product M1, so an app's NiMH preset follows the register), `BATTERY_VOLTS_RANGE = (2.2, 3.0)`, `DEFAULT_BATTERY_VOLTS = 3.0`. The design script's `--battery` section starts from the f32-rounded volts (as it does for P_REF), prints the f32-rounded factor as hex bits and the dB from it at the six law points, the seven rows and the NiMH figure, and `--write` generates the constants into `output_coeffs.rs` (byte-identical gate); `battery.rs` re-exports them (coach 14). The core pins: bit equality on the factor, 1e-5 on `ceiling_db` (hardware B2). C: `rr_dr60_battery_ceiling_factor(volts, *out)`, `rr_dr60_battery_ceiling_db(volts, *out)` (`INVALID_ARGUMENT` only for a non-finite input), `rr_dr60_battery_trajectory_row(i, *out_hours, *out_volts)` (`INVALID_ARGUMENT` at or past 7), the defines `RR_DR60_BATTERY_TRAJECTORY_ROWS 7`, `RR_DR60_BATTERY_VOLTS_MIN 2.2`, `RR_DR60_BATTERY_VOLTS_MAX 3.0`, `RR_DR60_BATTERY_VOLTS_DEFAULT 3.0`, `RR_DR60_BATTERY_NIMH_PAIR_VOLTS 2.45` (double defines, as `RR_DR60_VOLUME_REFERENCE`). `battery_ceiling` in the meters is a factor; the guide says "20·log10 for dB" (product M5).

**Rationale.** D2, D11; hardware B2, B7; coach 4, 8, 14; product M1, M2, M5. The seven rows land at −0.294, −1.938, −2.894, −4.437, −5.736, −7.264, −9.119 dB, within 0.044 dB of the register's rounded table; 2.5 V reads −4.7 dB (hardware B13).

## R-05: The meters

**Decision.** `Meters` gains `amp_clip_count: u32` (speaker-route host samples of the call the amplifier's knee or ceiling **changed**, `|x| > k·b` at the knee's input; hardware B12: the other two counts count changed samples too) and `battery_ceiling: f32` (the factor in force at the call's end). They are accumulated where the knee is applied (the speaker branch with stage 11 on) and finalized by `PlaybackPath::finalize_into` under a construction-time gate `meter_amp` = the tap is `AfterVolumeAmp`, `AfterSpeaker` or `RouteOutput` (the taps that run the knee; coach 7): then `amp_clip_count` is written and cleared and `battery_ceiling = batt`; otherwise both keep their rest. On the earphone route or with stage 11 bypassed the count rests at 0 and the factor is still reported (product M4). `rest_meters()` carries `battery_ceiling = ceiling_factor(self.battery_volts)` (1.0 at the default; the hang's precedent since 017; hardware B11); `Meters::default()` (the C zero twin) carries 0.0. `RrDr60Meters` grows 56 → 64 bytes (`amp_clip_count` at 56, `battery_ceiling` at 60) under a **compatible prefix-fill rule** (hardware B5): a `struct_size` below 56 is refused, 56 … 63 is filled to the size (the 0.17 layout, nothing else written), 64 and above is filled and the tail zeroed; spec 016's "smaller refused" rule is amended with today's date, so a 0.17 binary keeps working. `meters_checks::row` keeps its eleven columns, so `golden-meters-v1.json`, `examples/meters_rows.rs` and `smoke --meters` are byte-identical (coach 3, hardware B4); a new `meters_checks::battery_row(m)` = `row(m)` plus the two fields (the count decimal, the factor as hex bits) serves the battery golden, `examples/battery_rows.rs` and `smoke --battery`. The field's documentation says what it counts ("samples in the amplifier's clip region, the knee's start and above", meaningful on the speaker route; product M4).

**Rationale.** D10, FR-010; the spec's FR-005 (the twelve golden files unmoved) holds.
