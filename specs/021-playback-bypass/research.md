# Research: Live Playback-Stage Bypass (spec 021)

**Date**: 2026-10-31 | **Spec**: [spec.md](spec.md) (D1 – D11 approved) | **Baseline**: 0.20.0, merge commit f303c99

Every item: Decision, Rationale, Alternatives. Code references are to the tree at f303c99. The plan reviews (coach 1 – 11, hardware B1 – B12, product M1 – M9, 2026-10-31) are applied; each item names the findings it absorbed.

## R-01 The weight per sample: the expression, `u = k · inv_n`, exactly 0.5 at the midpoint

**Decision**: w = u·u·(3 − 2u) computed per sample from `u = k · inv_n` (k the phase index 0 … N, `inv_n = 1 / N` computed at construction), the form spec 011's volume transition uses (`stages/output.rs:462, 496`) and spec 019 pins (`u * u * (3.0 - 2.0 * u)`). N = `output::volume_transition_samples(rate)` (0.02 × rate: 120 … 1920) for stages 11 – 13 and `speed::CROSSFADE_SAMPLES` (120) for stage 10 (hardware B11: no new literal; A-045, the engine's 20 ms transition, a convention).

**Rationale**: a table would be 1920 f64 per stage at 96 kHz for one multiply-add while a fade runs and nothing while idle; the expression is the pinned form the harness reference and spec 019's script already use. **Exactness (hardware B5, verified for the seven N)**: (N/2)·fl(1/N) is exactly 0.5 for N = 120, 160, 320, 882, 960, 1764, 1920 (the product is 0.5(1 + δ) with |δ| < 2⁻⁵³, nearer to 0.5 than to either neighbour), so the spec's pin **w(N/2) = 0.5 exactly** stands and the core asserts it with `==` at the seven rates; w is monotone in k within a direction (a positive constant multiply is monotone under rounding, and the smoothstep's steps are ≥ 1.6e-6). The end samples are selected, not computed (spec D3). The first draft's "within 1 ULP" restatement is withdrawn (coach 5, hardware B5).

**Alternatives**: a per-rate table (no gain); `k as f64 / n as f64` (also exact at N/2, a division per fading sample; unnecessary); a linear weight (the mutant).

## R-02 The fade state and the reverse-from-phase arithmetic

**Decision**: per stage a `Fade { k: u32, dir: i8, n: u32, inv_n: f64 }`, `dir` ∈ {−1, 0, +1} (+1 toward bypassed, −1 toward on, 0 at rest), the rest state read from k (0 = on, N = bypassed). A landing of value v: if the stream's last applied value already is v, the stream logs a no-op entry and the fade is untouched (the no-op is decided by `StreamState`'s last value, never by k; coach 4e); else `dir = if bypassed { +1 } else { −1 }` from rest or as a flip of a running fade (k kept). The per-sample step, **clamp first** (hardware B2): `let k = (i64::from(self.k) + i64::from(self.dir)).clamp(0, i64::from(self.n)); self.k = k as u32; if self.k == 0 || self.k == self.n { self.dir = 0; select } else { blend w = smooth(k · inv_n) }`. The landing sample P computes k = 1 (a return from rest computes N − 1). **At once** on a stream's first produced sample (spec 011's rule): decided by the stream's clock (`StreamState::produced == 0`, passed as `at_once` in the apply), **never by the chain's `fresh` flag**, which a route switch also sets (hardware B7, coach 4b); the snap is `k = if bypassed { n } else { 0 }; dir = 0`. `PlaybackPath::reset` (run by `start_playback`) snaps all four fades to the adopted values (a playback stopped mid-blend restarts at rest).

**Cases pinned by core tests**: a reversal at k = N/2 reaches k = 0 in exactly N/2 samples; the same-position pair off-then-on from rest-on (dir ends −1 at k = 0 → the clamp holds 0 → select y, dir = 0: no blend, two entries) and on-then-off from rest-bypassed; a landing at P where sample P − 1 selected x (k = N) is a return from rest (first sample k = N − 1); a landing at the sample that *would* compute k = N reverses from k = N − 1 and never reaches w = 1 (the spec's edge case "a toggle back exactly at the blend's last sample" restated: the first reading, hardware B2).

**Alternatives**: a float phase (accumulates rounding); a wait (spec 019 D4) or a restart from rest (spec 011).

## R-03 Stage 10's blend and its host-output settle; the device-rate trace hook

**Decision**: stage 10's blend sits in `PlaybackHalf::process` (`paths.rs:347`): `y = playback.process(d)` always runs when `run_playback`; the returned value is the fade's select/blend of y and d. The landing reaches the half through the player's existing pre-pull apply (`transport.rs:680`): `Apply::Bypass { stage: 10, .. }` handled in `PlaybackPath::apply_if_due` by `self.half.land(bypassed, at_once)` and effective on the next device sample pulled, d(P) = `changes::speed_landing(P, rate)` (confirmed by the hardware review, the identity rate's `pending` path included: d(P) = P). On the host output the blend passes the interpolator (a linear-phase FIR of delay D, `paths.rs:1270`; the full span 2D is the settle, not D + half) and then the chain when it runs (IIR: R-10). **The harness measures per rate, with the chain off, the first bit-different host sample and the first identical one** and the records quote those figures; P + ⌈119·rate ÷ 6000⌉ + 2D is the bound. No onset figure is pre-quoted (hardware B6: spec 015's "+1 … 16" was a step's onset; a smoothstep's first device sample differs by w₁·(x − y) with w₁ ≈ 2·10⁻⁴ through the kernel's edge taps, below the f32 ULP for several samples).

The device-rate trace hook: `__test_hooks` `stage10_trace` (a `Vec<f32>` reserved at construction with 8192 entries like `speed_place_trace`) records the half's **output** per device sample pushed during a play call (the existing `trace` records the half's input, so the pair gives x and y). The player's only (D6).

**Rationale**: the stage keeps running (D3), `run_playback` stays construction-time (D4), the apply point precedes the pull. At 6 kHz `up` is `None` and the host output is the device stream.

**Alternatives**: blending after the interpolator (a second interpolator); a one-pass device-clock apply point (rejected, D6).

## R-04 "Runs on the stream": the refusal predicate with the tap reach

**Decision**: `schedule_change` refuses with `Error::StageNotConfigured { control }` (C status 36) **any change** (0 or 1) of a stage switch whose stage does not run on the target stream. "Runs" = the construction switch on **and the stream's tap reaching the stage**, through one predicate `OutputChain::reaches(stage) -> bool` beside `PlaybackHalf::runs()`: the player (tap `RouteOutput`) reaches every configured stage; the one-pass at `AfterVolumeAmp` reaches 11 only, at `AfterSpeaker` 11 and 12, at `AfterEarphone` 11 and 13, at `RouteOutput` all three, at the taps before the chain none (the chain's `run_*` flags alone overstate this: `enabled` is true for every tap after stage 10 other than `AfterPlayback`, `output.rs:258 – 278`, while `inner()` returns at `AfterVolumeAmp` before stages 12/13: coach 2, hardware B4). The route is not part of the rule (stage 12 runs on the one-pass and the player whatever the route; its blend's phase advances regardless). Restated from the spec's "a change that would switch on": a change *to off* of a non-running stage is refused too (landing it would write `settings()` to off for a stage whose setting may be on, after which an on-change is refused: one rule, no trap); D4's "no-op entry" applies only to a running stage already at the value. The refusal text (product M5): `"control {n} ({identifier}, stage {k}) does not run on this stream: its setting was off at construction or the one-pass's tap stops before it; build the engine with the stage on (and a tap at or after it) and switch it with schedule_change instead"`, the identifier and stage from `control(n)`. A core test covers the five taps × three stages; `us2_bypass` has a one-pass at `AfterVolumeAmp` refusing stages 12 and 13.

**Alternatives**: refuse on-from-off only (the spec's first wording; the trap); land-and-log silently.

## R-05 The mirror between the player and the one-pass; the bound 142

**Decision** (hardware B8 replaces the first draft's symmetric `xpend`): a one-pass processing call is refused while a path is active (`refuse_if_active`), so a one-pass landing can never happen during a playback and the player's only mirror path is `start_playback`'s adopt (`set_start_values` extended with the three switches from `settings`; no entry). The one-pass mirrors player landings by spec 017's compare-at-`begin_call` form (`RecordCtl::begin_call`, `changes.rs:1028 – 1051`): `StreamState` gains `last_bypass: [bool; 3]` and `landed_bypass: [Option<bool>; 3]`; after each `play` call the pipeline writes the landed switches into `settings` and keeps their tags (`bypass_tags: [u64; 3]`, as `take_landed_record` does at `pipeline.rs:1137`); at the one-pass's next call its stream compares the three settings switches to `last_bypass` and lands the differing ones first, with the stored tags, for the stages the one-pass **reaches** (R-04; the others are skipped, `settings()` still reflecting the landing). "Its next sample" is the first sample of the other stream's next call. The player's stage 10 has no mirror (D6). `MAX_CHANGES_PER_CALL` = 2·64 + 3 + 8 + 3 = **142**: the one-pass attains 64 + 3 plain + 3 mirrored + 64 + 8 in one call, the player at most 64 + 4; `bypass_matrix::the_tight_bounds` pins both (coach 7; 017's `record_matrix.rs:148` pattern). Not an ABI change: the C calls take a capacity and return the count; a host that sizes by the constant recompiles; a 0.20 binary's 139-entry buffer can be short by up to three entries in one one-pass call, reported by the count, never overrun (the CHANGELOG says so, as 0.17's did).

**Alternatives**: a symmetric pending set per stream (dead code on the player); independent values per stream (`settings()` ambiguous).

## R-06 The click reader at 48 kHz and the per-stage stimulus rows

**Decision**: `analysis::click_energy_band(y, rate, centre, window_s, exclusions_hz, top_hz)` with `click_energy_in` delegating at 2750 Hz. The asserted rows (6 kHz, the stage-only configurations, a −6 dBFS stored 1 kHz tone 1.5 s long, the landing at 0.75 s, a 40 ms window centred on the blend's midpoint, ±250 Hz around the tone excluded, the floor the reader on the all-on held run, the step realized by the `fade_step` mutant): stage 10 (`playback_only`), stage 11 alone (`output_only_amp`: stages 12/13 off at `RouteOutput`, `configs.rs:723`; the speaker route at the reference position and the earphone route at position 1), stage 12 (`output_only_speaker`), stage 13 (`output_only_earphone`). The reported rows: stage 10 at 2.6 kHz (recorded on `playback_only` at 6 kHz, whose record side is off, so the stored stream is the narrowed input: no `import` detour, hardware B12), stage 12 at 300 Hz, stage 13 at 100 Hz, stage 11's corners at 100 Hz at the neutral positions, stage 11's level-change rows (speaker at position 1, earphone at the reference position) printed as the level change in dB beside their reader figures, every asserted row at 48 kHz with `top_hz = 0.45 × rate`, the voiced stimulus per stage, the reversal at u = 1/2 for stage 12, and (hardware's evidence gap) a third-octave difference of stage 10 on against off at 48 kHz on the voiced stimulus, backing D1's "audible mainly at 6 kHz".

**Alternatives**: a new reader; asserting 48 kHz (the ratio inside 2750 Hz understates the step).

## R-07 Stage 11's level change: one published function

**Decision** (product M3, hardware B3): `output::stage11_bypass_level_db(route: Route, position: f32) -> f32` (C `rr_dr60_stage11_bypass_level_db(route, position)`, no handle, like the gain-law functions): the level of stage 11's input at unity relative to the stage's output below the knee, in dB, positive = louder when bypassed, +∞ at position 0; the speaker route −(speaker_gain_db(p) + SCALE) with SCALE = 20·log10(CODEC_FULL_SCALE_V ÷ V_CLIP_V) ≈ **−1.214 dB** (the chain's scalar `k_spk = g_spk · 1.0 / 1.15`, `output.rs:62`; the first draft's formula subtracted the constant: a sign error, hardware B3, product M2), the earphone route −earphone_gain_db(p). The constant stays private (a `from_bits` literal printed by `design_output_chain.py --write`, checked by `--check`, pinned against `db(k_spk(1.0)) − speaker_gain_db(1.0)` within 1e-5, traced to A-030 and A-031). Figures the core test pins within 0.01 dB: earphone at the reference position **+19.21 dB**, at position 1 **0.00**; speaker at the reference position **0.00** (k_spk(P_REF) is unity after the f32 rounding), at position 1 **−21.46 dB**. The neutral positions: the speaker route's reference position, the earphone route's position 1. The D10 deviation (one new function rather than "the status and the bound only") is recorded in the plan's decisions and the spec's Clarifications.

**Alternatives**: a public constant with the app composing the formula (the sign trap; three footnotes); a level-kept bypass (rejected, D11).

## R-08 The hot-path cost plan

**Decision** (hardware B10): one `bypass_state: u8` adjacent to `active` (bit 0 "any fade running", bits 1 – 3 the rest-bypassed flags) with `#[repr(C)]` on `OutputChain` so the placement is real (coach 11d; spec 015's `StreamState` precedent); `if self.bypass_state == 0` takes 0.20's path unchanged (bit-identity for free), else the cold path with the selects and blends; a cached `amp_counting: bool` updated in the fade step and at the snaps replaces a per-sample `k < n` compare (the `count_ungated` mutant forces it true at the snap, so it costs nothing on the hot path). Stage 10's half: one `dir != 0` test per device sample plus the rest select. The A/B `bypass` mode against f303c99 (`tests/bypass_timing.rs` against 0.20's API) asserts the all-on state on the player and the one-pass at 3 % (`RR_DR60_BYPASS_COST_CEILING` 0.05 on the label job); the bypassed steady state and a blend in progress are reported with the worst block.

**Alternatives**: four separate flags and a per-sample gate (017's first measurements: +2.5 … +3.6 %).

## R-09 The golden, the gates and the mutants

**Decision**: `golden-bypass-v1.json` (`RR_DR60_BLESS=bypass`, `golden_bypass.rs`), 20 entries per rate × 7 = 140 (R-09 of the first draft's layout: stage 10 on the player × 2 schedules; stage 11 × 2 routes × 2 streams × 2; stages 12 and 13 × 2 streams × 2; two two-stage entries), each with the configuration, route, stream, rate, schedule, produced count, changes and the output's digest. **Bless-time gates** (coach 1, 8; hardware B1): the bit-exact endpoint identities on the entries where no stateful stage follows the switched one (the stage-only configurations; stage 12 on the speaker route and 13 on the earphone route with the chain's earlier stages on; stage 11 alone; stage 10 with the chain off) and the convergence bound (R-10) on the default-engine entries; the partition identity including block size 1 (the switches have no 0.20 setter, so there is no setter oracle: the twins and the blend trace are the independent oracles). Six mutants in `BypassMutation`: `weight_inverted`, `fade_step` (the switch at once; the click reader's step reference), `fade_linear`, `stage_cold`, `count_ungated`, `phase_frozen_off_route`.

## R-10 Where the endpoint identities are bit-exact; the convergence bound; the live tail

**Decision** (coach 1, hardware B1): the identities "from the blend's last sample the output equals the configured-off twin over its length" and "after a return the output equals the all-on run" are **bit-exact where no stateful stage follows the switched stage on the active route**: the stage-only configurations, stage 12 on the speaker route and stage 13 on the earphone route (the last stages), stage 11 alone (`output_only_amp`), stage 10 on the device-rate trace and on the host output with the chain off (after 2D). In the default engine a downstream IIR stage (stage 12/13 after 11; the chain's 32 Hz corner after 10) remembers the pre-landing history, so the live output **converges** to the twin's: asserted |live − twin| ≤ −100 dBFS from P + N − 1 + N_OUT (the drain's own criterion, spec 009 R-08) at every rate, the max |Δ| in f32 LSBs after that point pinned once at the bless (006's narrowing-delta pattern), and the first bit-identical host sample reported where it exists. The blend identity (c) stays bit-exact everywhere (it reads the switched stage's own input and output on a trace). The live engine's extra drain samples (its drain is the all-on drain: stage 10's N₁₀ and the chain's N_OUT where the twin runs none) are the bypassed stage's **selected input**, the upstream residue (hardware B9, coach 6): asserted **exactly 0.0** for stage 10 at 6 kHz and for a bypassed last stage whose upstream has drained (a non-zero there is a stage leaking past its select), otherwise reported as a peak and asserted ≤ −80 dBFS. The live engine's total length equals the all-on no-schedule length (D4). `derive_figures` (`paths.rs:1129`) is untouched.

**Alternatives**: asserting bit-exactness everywhere (cannot hold; the gate would be weakened at implementation).

## R-11 The `reconfigure(settings())` trap, `reset`, and the guide's contract

**Decision**: `reset` re-applies `settings()`'s landed values at once to every fade, **the one-pass's stage 10 included** (a player landing writes `playback_stage_enabled` into `settings()`, so after `reset` the one-pass's half rests bypassed while its reported latency stays the all-on figure by D4; one lifecycle rule for all four; coach Q1 at the default). `reconfigure(s)` rebuilds from `s`: a switch off in `s` means the stage does not run (not a fade state). `us2_bypass` has the trap test (bypass stage 12 live, `reconfigure(settings())`, the on-change refused with 36) and the contract's recipe (take `settings()`, set the four switches on, `reconfigure`, re-schedule the bypasses at position 0: they land on the first sample with no blend, bit-identical to the live bypass's steady output). The guide's section carries the contract (contracts/api.md, eleven points after the product review), the loudness rule for stage 11 on the earphone route (product M1: the Workbench moves the volume to position 1 before offering the switch, or compensates, or confirms; the engine does not compensate), the inert volume and battery while stage 11 is bypassed, the toggle order 12, 11, 13, 10, nothing shown during the 20 ms, the card reading the state at playback start (landed values persist), the meter rule, and the wording rule (a bypassed branch is "stage N bypassed (emulator)", never "raw", "clean", "unfiltered" or "true": the forbidden-list scan gains those stems; product M6, M8).
