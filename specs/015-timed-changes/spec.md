# Feature Specification: Sample-Timed Control Changes and the Change Log

**Feature Branch**: `015-timed-changes`

**Created**: 2026-10-30

**Status**: Implemented on `015-timed-changes` (2026-10-30); awaiting the merge

**Input**: User description: "015 sample-timed control changes and the change log. As an app replaying a session, driving a preset or scripting a fade, I want to schedule a change of a live control (the route, the volume position, the playback speed level) at an exact sample position of the output stream, and to receive a log of every change the engine applied with the position it landed on, so that the same session reproduces bit for bit at any audio buffer size and a listener can see what changed when. Product request: controls-discussion.md § 2c gaps 1 and 2 and § 4 item 2; decisions.md 2026-10-29 (engine order 014 → 016 → 015 → 017 …; no AI control for now, so the feature stands on presets, sessions and replay); front-and-inside.md engine requests (the timeline map is noted). Today a live change is read once per call at the block boundary (spec 009 FR-009 for the route and the volume, spec 011's 20 ms transition from the next block, spec 013 FR-001 for the speed from the first device sample computed after it was set), so the same change gives different output under different buffer sizes; iOS changes the I/O buffer under the app. Scope: the three live controls on the playback path and the one-pass (the record-side values follow in spec 017 through the same mechanism, so the form must carry any control of the control manifest, spec 014). A change carries a position in the stream's own clock: the host output samples the player has produced since start_playback, or the one-pass since reset; the engine applies it at exactly that sample (the volume transition of spec 011 starts there, the route switches there with the new branch from rest as 011 FR-005 says, the speed level applies from the first device sample computed for host output at or after it under spec 013's latch and whole-place rules). A position already passed applies at the next sample and is logged where it landed. The existing setters keep their meaning (at the next call), so every existing golden file and smoke hash stays byte-identical and a change at a boundary of every partition equals today's behaviour. Pending changes live in a bounded schedule reserved at construction (no allocation in the processing path; a full schedule refuses the change with a distinct error; reset and reconfigure and start_playback clear it, stated). The change log: every applied change is reported to a caller buffer in the form the VAS events use (position, control, the value before, the value after), per call, with a length function that is always enough; no callbacks. Oracles: partition independence (bit-identical output at block sizes 1, 64, 4096 and an irregular partition for arbitrary change positions); spec 011's splice identity at the tap after stage 11 and spec 013's schedules against the harness reference for positioned changes; the log against the schedule. Determinism and real-time safety as every spec; a cost budget as a build A/B against 0.15 (idle, no pending change: 3 % on the development machine, 45 alternating runs, a runner ceiling via the ab-timing label; with changes pending, reported). Not a device behaviour: an engine convention (no new assumption unless the plan finds one; the control manifest's timing classes stay). Free tier. Out of scope: a programmed volume fade over N ms (a later option; the schedule gives a script the same), record-side values (017), the settings serialization and the session sidecar (020), the timeline map of meters to positions (020, on the stream clock 015 defines), AI control, callbacks, threading (the Swift package's queue carries the change form)."

## Overview

Since spec 009 the route and the volume position, and since spec 013 the playback speed level, are **live controls**: the host sets them at any time and they take effect at the next processing call (spec 009 FR-009; spec 011's 20 ms transition starts at the next block; spec 013 FR-001's level applies from the first device sample computed after it was set). Where a change lands therefore depends on the host's block size: the same `set_volume` made between two calls lands 64 samples apart at a 64-sample block size and 4096 apart at 4096. iOS changes the audio buffer size under an app (on a route change, for example), so a session replayed later, a preset applied by a script, or a record of "what was changed when" cannot reproduce the output bit for bit, and the engine reports no control change at all, only the voice-activation splices.

This feature adds **sample-timed changes** and a **change log**. A change of a live control can carry a position in the stream's own clock, and the engine applies it so that exactly that output sample is the first one it affects, whatever the block size. Every change a stream applies, positioned or not, is reported back to the caller with the position it landed on, in the form the voice-activation events already use. Together they make a session a list of events that reproduces bit for bit, and a timeline the app can show.

What 1.0 gets from this feature alone is the reproducibility of playback review (route, volume and speed during a playback) and the form the record-side values will use; a recording session's own values become live through that form in spec 017, and the settings snapshot and the session sidecar are spec 020's. The plain setters keep their meaning and every existing output is unchanged.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - The same session at any buffer size (Priority: P1)

An app replays a session: it starts a playback, schedules the route, volume and speed changes the session recorded at their positions, and plays it in blocks of whatever size the device gives it. The output is bit-identical to the output of the original session at a different block size.

**Why this priority**: it is the whole value of the feature: replay, presets and scripts are useless unless they reproduce.

**Independent Test**: a stimulus is played (or run through the one-pass) with a set of positioned changes at block sizes 1, 64 and 4096 and the irregular partition; the outputs are compared sample for sample; each change is also compared with the plain setter at block size 1 called right after output P − 1 (the primary oracle) and with the harness's existing oracle for that control.

**Acceptance Scenarios**:

1. **Given** a playback (and separately the one-pass) with changes scheduled at arbitrary positions, including positions inside blocks, **When** the same stimulus is processed at block sizes 1, 64 and 4096 host samples and the irregular partition, **Then** the outputs and the concatenated logs are bit-identical at all seven host rates, on both routes, and equal the output of 0.15's plain setter at block size 1 called right after output P − 1 for each change.
2. **Given** a volume change scheduled at position P at the tap after stage 11 (the stream past its first sample, stage 11 on), **When** the stream is processed, **Then** output samples before P equal a constant run at the old position, sample P is the first transition sample and sample P + N − 1 carries exactly the new position's gain (spec 011's splice identity, with P in place of the block boundary), at all seven host rates and on both routes.
3. **Given** a route change scheduled at position P, **When** the stream is processed, **Then** samples before P equal the old route's run and samples from P on equal the run spec 009's route-change check uses (the new route with its branch from rest and the volume at the position reached, spec 011 FR-005) started at P.
4. **Given** a playback with speed level changes scheduled at positions, with the speech codec bypassed and on, **When** it plays to the end, **Then** at 6 kHz the output equals the harness's reference playback (spec 013's reference bank, a device-index schedule at d(P) computed from the formula) bit for bit, including two changes within 4 device samples where a deferred switch into level 3 is overridden and a change landing after the latch; at the other rates it equals the block-size-1 oracle; the recording's length rule is unchanged and `finished` is reported once at the end of the drain.
5. **Given** a change scheduled at a position below the stream's position, **When** the next call runs, **Then** the change lands on the first sample that call produces and the log reports that index, which differs from the requested one; a change at exactly the stream's position lands on that sample.
6. **Given** a change scheduled at an all-partition boundary of the output clock (a produced count that is a call boundary at block sizes 1, 64 and 4096 of the input; with the voice activation bypassed or in mute mode, and a second case in drop mode at a 4096-input boundary), **When** the stream is processed, **Then** the output equals the output of the plain setter called between the two calls at that boundary, bit for bit, at every partition, for every control.
7. **Given** two changes of one control at the same position, **When** the stream is processed, **Then** both are applied before sample P is produced and logged in submission order (the second entry's value before equals the first's value after), and the output equals the second change's alone, for every control.
8. **Given** changes submitted at P = 1000 and then at P = 500, **When** the stream is processed, **Then** the 500 lands at 500 and the 1000 at 1000.
9. **Given** a full-scale square on the one-pass with the route switched at P inside a block, **When** the block is processed, **Then** the meters' route peak and output-clamp count of that call cover both routes' samples (the maximum over the whole call's route-output tap).

### User Story 2 - A log of what changed when (Priority: P2)

An app shows a timeline of a session: every change a stream applied, with the output sample it landed on, the control, the values before and after and the caller's tag, read from the engine, not reconstructed from what the app sent.

**Why this priority**: the timeline, and showing which changes a preset or a script applied and where, are the product's reasons for the log; the engine alone knows where a change landed.

**Independent Test**: a stimulus is processed with scheduled changes and plain setter calls; the log of every call is collected and compared with the schedule and the setter calls: one entry per applied change, in order, with the landed position, the control's identifier, the chained values and the tag.

**Acceptance Scenarios**:

1. **Given** a schedule of changes, **When** the stream is processed in blocks of any size, **Then** each change appears in the log exactly once, in the call that produced the sample it landed on, with that position, the control's manifest identifier, the value before (the stream's last applied value: each entry's before equals the previous entry's after for that control on that stream, or the value the stream started with), the value after and the tag; the concatenated logs over the partition are identical at every block size.
2. **Given** a plain setter call between two processing calls of a stream, **When** the next call runs, **Then** the log holds one entry at the first sample that call produced, with the old and new values and tag 0; several setter calls of one control between two processing calls log only the last (spec 011: only the last counts); **Given** a setter call before `start_playback`, `reset` or `reconfigure`, **When** the stream runs, **Then** no entry is logged for it (the lifecycle call took the value at once).
3. **Given** a log buffer shorter than the changes applied in a call, **When** the call runs, **Then** every change is still applied, the first entries fill the buffer, the report says how many there were, and the published length (67) is always enough.
4. **Given** a processing call without a log buffer, **When** changes land in it, **Then** they are applied and nothing is reported (the existing calls are unchanged in form).
5. **Given** a scheduled change to the value already applied, **When** it lands, **Then** it changes nothing and is logged with equal before and after values; **Given** a plain setter to the value already applied, **Then** nothing is logged.
6. **Given** a volume (or route) set during a playback, **When** the playback ends and the one-pass stream's next producing call runs, **Then** that call logs the change again on the one-pass stream at the position where its own transition (or branch reset) lands, with tag 0, and the output shows the transition there.

---

### User Story 3 - The schedule is bounded and the same from C (Priority: P3)

The iOS app schedules changes and reads the log through the C API, and can rely on a fixed schedule capacity, a distinct error when it is full, a readable pending count and position, and a clear call.

**Why this priority**: the first app reaches the engine through C; a bounded schedule is what keeps the processing path real-time safe.

**Independent Test**: the C smoke program schedules the Rust test's changes, processes its stimulus and prints the log; the print equals the Rust test's; a 65th change is refused; the pending count, the position and the clear are checked.

**Acceptance Scenarios**:

1. **Given** a C program, **When** it schedules changes, processes blocks with a log buffer and reads the log, **Then** it receives the Rust entries field for field and the same output hash.
2. **Given** 64 pending changes on one stream, **When** a 65th is scheduled, **Then** it is refused with the schedule-full status and nothing changes; the other stream's schedule is unaffected.
3. **Given** a schedule with pending changes, **When** the pending count is read, **Then** it equals the number scheduled minus the number landed; after a clear, `reset`, `reconfigure` or the end of a playback by any path (`finished`, `stop_playback`, an `erase` of the played item, `erase_all`) it reads 0 and no cleared change is ever applied or logged; a refused `start_playback` leaves it unchanged.
4. **Given** an invalid value (a volume outside 0 … 1, a speed level outside 1 … 5), a control not on the stream's path (the speed on the one-pass stream, the record stream), or on the one-pass stream a route the configured named tap cannot read, **When** it is scheduled, **Then** it is refused with the control's existing error, the not-on-stream error or the tap error respectively, and nothing is stored.

### Edge Cases

- **Positions on the playback stream** count every sample the playback produces: the recording's part at the levels played, the speed control's tail and the drain. A change scheduled during the drain lands there (a route or volume change is audible in the settle; a speed change after the latch has no effect on this playback and is logged as applied). The playback's total length is known at the speed latch (spec 013 R-05), so a position inside the drain can be computed in advance only at a constant level (`playback_length_samples`).
- **A change past the end of a playback** is never reached; it stays pending until the playback ends, which clears it, and is never logged (an app learns of dropped changes by comparing). A change past the current one-pass position stays pending until the stream reaches it. Changes for the next playback cannot be scheduled while the current one is still draining (its end clears them): schedule after `finished`.
- **Scheduling before `start_playback`**: allowed; the positions count from the playback's first sample. Changes left over from a previous playback do not exist (cleared at its end).
- **A change on the one-pass stream while a path is active**: accepted into the one-pass schedule (the stream is idle; it lands when the one-pass runs again).
- **The transition's at-once cases** (spec 011 FR-005): a change landing on a stream's first producing sample after construction, `reset`, `reconfigure` or `start_playback`, or with stage 11 bypassed, or on an inactive chain, takes the position at once; it is logged as a change if the stream's applied value moved.
- **The route change ends a volume transition** in progress at that sample (spec 011 FR-005); the transition's own change was already logged when it started.
- **The speed change and the latch**: a change whose d(P) falls after the place reaches K has no effect (spec 013 FR-007); it is logged where it landed with before and after values.
- **The speed change and the whole-place rule**: a switch into level 3 at d(P) waits for a whole place (at most 4 device samples); a change to another level before the wait ends drops the pending switch (spec 013 FR-007) and both are logged where they landed.
- **Simultaneity across controls**: a volume and a speed change at the same P are not simultaneous at the output: the volume acts at sample P, the speed about one playback latency later; an app aligning them subtracts the latency from the speed's position (the plan publishes the figure per rate).
- **A volume change within N samples of a playback's end** starts a transition the end cuts (spec 011 FR-005's drain rule is for an unchanged volume); it is logged.
- **Volume positions and the knob**: the value before is the stream's last applied target, not the knob's position during a transition (spec 011 FR-011).
- **A call that produces no sample** (a zero-length call; a block the voice activation drops entirely): nothing lands and nothing is logged; the change waits for the next produced sample.
- **Several changes of different controls at the same position** are applied in submission order; the output does not depend on the order except where the rules of D3 make it (a route and a volume at the same sample: the new route starts at the new position, spec 011). A plain setter and a scheduled change at the same boundary: the setter lands first, then the scheduled ones in submission order (so a scheduled change wins).
- **The schedule and the voice activation**: the one-pass clock is the output's, so a change scheduled at position P lands on output sample P whatever the gate dropped before it; a route change scheduled at a splice event's position starts the new branch on the event's first post-splice sample.
- **Determinism**: the schedule's state is part of the engine's; two engines fed the same calls, schedules and stimuli give the same output and log on every platform. A one-pass replay also needs the same recording counter (D9).
- **The C form**: the log entry is a plain structure without a size field (D8); a null handle, or a null buffer pointer with a non-zero length, is refused.

## Requirements *(mandatory)*

### Functional Requirements

**The schedule**

- **FR-001**: The engine MUST accept a **scheduled change** of a live control carrying the stream (an enumeration: playback, one-pass; the record stream reserved for spec 017), the control (the control manifest's identifier), the value, a position in that stream's clock (D2) and a caller tag. The value is validated as the plain setter validates it; a control whose manifest paths do not include the stream is refused with a distinct error; on the one-pass stream a route value the configured named-route tap cannot read is refused with the existing tap error (spec 009 FR-011); nothing is stored on a refusal. The call is accepted in every engine state and is real-time safe.
- **FR-002**: Each stream's schedule MUST hold up to **64** pending changes, reserved at construction, kept in position order (ties in submission order) at the schedule call, never allocated in the processing path; a change beyond the capacity MUST be refused with a distinct error (Rust and C) and nothing stored. The pending count and the position of each stream MUST be readable; each schedule MUST be clearable by the host. The one-pass schedule is cleared by `reset` and `reconfigure`; the playback schedule by `reset`, `reconfigure` and the end of a playback by any path (`finished`, `stop_playback`, an `erase` of the played item, `erase_all`), and is kept by `start_playback`; a refused `start_playback` or schedule call leaves it unchanged; recording and playback calls leave the one-pass schedule and clock untouched.
- **FR-003**: A scheduled change at position P at or above the stream's position MUST be applied before sample P is produced (D3): the volume's transition sample 1 is sample P (spec 011 FR-001, FR-002, with P in place of "the first sample of the next block", and FR-005's at-once cases); the route is switched for sample P with the new branch from rest and a transition in progress ended (spec 011 FR-005), leaving the call's meter accumulators intact (spec 016: the route peak and clamp count cover both routes' samples); the speed level applies from device-rate output sample d(P) = ⌊(P − 1) · 6000 ÷ rate⌋ + 1 (d(0) = 0; P at 6 kHz), under spec 013 FR-007's whole-place rule and the latch. A change at P below the stream's position MUST land on the next sample produced and be logged at that index. Changes MUST be applied in position order, those at one position in submission order, after a plain setter landing at the same boundary.
- **FR-004**: The plain setters (`set_route`, `set_volume`, `set_playback_speed`) MUST keep their meaning: the change lands on the first sample the next processing call of each stream the control is on produces, the last call of one setter between two processing calls being the one that lands; a lifecycle call that takes the values at once (`reset`, `reconfigure`; `start_playback` for the playback stream, spec 009 FR-009) consumes it without a log entry. The control readings (`route`, `volume`, `playback_speed`) MUST move when a scheduled change lands and at once for a plain setter, as today.

**The log**

- **FR-005**: An entry MUST be reported exactly once for each change a stream applies (its own applied value moves: the chain's volume target or route, the speed stage's requested level), by the processing call that produced the sample it landed on, to a caller-provided buffer, as a **change entry**: the landed position (the stream's clock), the control's identifier, the value before (the stream's last applied value: each entry's before equals the previous entry's after for that control on that stream, or the value the stream started with), the value after and the tag (0 for a plain setter). The call MUST report how many changes it applied even when the buffer is shorter (the first entries written, as the voice-activation events do). The published always-enough length is **67**. Processing calls without a buffer MUST apply the changes and discard the entries.
- **FR-006**: A scheduled change to the value already applied MUST be a no-op for every control (spec 011: a transition starts only when the target differs) and MUST still be logged with equal before and after values; a plain setter to the value already applied MUST NOT be logged. A change that can have no effect (a speed level after the latch) is applied and logged where it landed.

**Nothing existing moves**

- **FR-007**: With no scheduled change the output MUST be bit-identical to version 0.15: the ten audio golden files and their SHA guards byte-identical, every smoke hash unchanged; a change scheduled at an all-partition boundary of the output clock (US1 AS6) MUST give the plain setter's output bit for bit.
- **FR-008**: A positioned change MUST be partition-independent: bit-identical output and identical concatenated logs at block sizes 1, 64 and 4096 and **the irregular partition** (a fixed, seeded sequence of block lengths between 1 and 4096 that includes 1, a prime and a length above 1000, stated once in the harness and shared by every partition check; for US1 AS6 built with a boundary at the tested position), at all seven host rates, on both routes, for every control, with the speech codec bypassed and on for the speed; and for every control at every rate the output MUST equal 0.15's plain setter at block size 1 called right after output P − 1 (the primary oracle, defined by the previous version's behaviour).
- **FR-009**: The schedule and the log MUST be deterministic (the same calls, schedules and stimuli give bit-identical output and entries on every supported platform; integer positions, a stable order, exact values) and real-time safe: no allocation, lock or I/O in any processing, scheduling, reading or clearing call; the per-sample work bounded (one comparison against the earliest pending position per produced sample). A new golden file (`golden-changes-v1.json`) MUST hold, per entry, the output digest and the full log for a set of schedules, configurations and the seven host rates, including entries for the plain setters, the three controls, the same-position cases, the passed-position case, the cross-stream entry and the drain.
- **FR-010**: The per-sample cost at 48 kHz with the schedule empty MUST be within D7's budget against the 0.15 merge commit (`f1449c2`), measured as a build comparison (`scripts/ab-timing.sh`, 45 alternating rounds, solo) on the development machine and on the CI runner through the `ab-timing` label, with the runner ceiling; the cost with one pending change per block MUST be reported.

**Access and records**

- **FR-011**: The schedule call (not a `set_` name, for spec 014's setter scan), the pending count, the position, the clear, the recording counter reading (D9), the change entry and the log-taking processing calls MUST exist in Rust and in C; one new log-taking variant per processing call, the one-pass's taking the event buffer too (both optional by length 0); the C entry is a plain structure whose one numeric value field represents every control-manifest value type exactly (switch, integer, continuous, choice), the control the manifest's index, the stream an integer; the entry has no size field and joins the pre-1.0 ABI-pass list; the existing calls, reports and the settings structure are unchanged (120 bytes); distinct statuses for the full schedule and for a control not on the stream; the header regenerated.
- **FR-012**: **Documentation.** (The stage-manifest clause is restated above: the API-item lines keep their text.) The user guide MUST explain the two stream clocks and their positions, how to schedule a change and read the log in Rust and C, the landing rules per control (D3, with d(P) and the speed's audible lag per rate), the capacity, ordering and clearing rules (D4, with the refill-per-block note for longer schedules), the log's per-stream chaining, the tag and the same-value rules (D5), that a one-pass replay needs the seed and the recording counter (D9), that a change past a playback's end is dropped without an entry, and that positioning is an emulator convention (D8: "Positioning a change on a sample is a feature of the emulator's API; the recorder's own controls move whenever a hand moves them."); the real-time list MUST include the new calls; the CHANGELOG MUST record the feature as version 0.16.0 without the word "provable"; the stage manifest's canonical text MUST move in its version line only (restated at implementation, Clarifications: its "Rust API items" lines of stages 9 and 11 keep their 0.15 text); controls-discussion.md § 2c MUST carry a status line (gaps 1 and 2 built for the three controls on the two streams; record-side values in 017; the snapshot in 020); front-and-inside.md's engine requests MUST note the two clocks the timeline map (spec 020) is built on; investigation-mode.md § 5's 015 bullet MUST be updated (the counter getter built, the host-input index and construct-at-counter moved to 020); decisions.md MUST gain a row (the tag; the free tier includes the schedule and the log; the timing classes unchanged).
- **FR-013**: The feature is **not a device behaviour**: no assumption is registered, no stage's model version moves, the control manifest's canonical text is unchanged (the three controls stay "live"; no "positionable" class), and no setting is added.

### Out of Scope

- A programmed volume fade over a duration (a later emulator option; a script schedules positions instead); the record-side values (spec 017, through this form and the reserved record stream); a settings serialization, the session sidecar and constructing an engine at a given recording counter (spec 020); the timeline map of the meters to positions and the map from a playback position to the recording's place under a speed schedule (spec 020, on the clocks defined here; `PlayInfo::place` leads the audible output by the playback latency); AI control; callbacks or a push of entries; threading (the Swift package's lock-free queue carries the change form into the audio callback); scheduling in time units (the app converts with the host rate); a schedule capacity setting; changes during recording of the record-side values.

### Key Entities

- **Stream**: the playback stream (one per playback, clock from `start_playback`) or the one-pass stream (clock from construction, `reset`, `reconfigure`); the record stream is reserved. Each has a schedule, a position (host output samples produced; the next sample has that index) and its own last applied value per control.
- **Scheduled change**: stream, position, control, value, tag; pending until applied or cleared.
- **Change entry**: position landed, control identifier, value before, value after, tag; one per change a stream applies, reported by the call that applied it.
- **Schedule**: a per-stream bounded list of pending changes, capacity 64, position order with ties in submission order.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For every control on its streams, the output and the concatenated log are bit-identical across block sizes 1, 64, 4096 and the irregular partition at all seven host rates and on both routes, and equal the block-size-1 plain-setter oracle: 0 mismatches.
- **SC-002**: A positioned volume change equals spec 011's splice oracle at the tap after stage 11 (sample P the first transition sample, sample P + N − 1 exactly the new gain); a positioned route change equals spec 009's route-change oracle from P; a positioned speed schedule equals the harness reference at 6 kHz bit for bit with the codec bypassed and on, including the overridden deferred switch and the post-latch change: 0 mismatches.
- **SC-003**: The ten audio golden files and their SHA guards are byte-identical; every change at an all-partition boundary equals the plain setter's output; the new golden is reproduced on every golden target, and the C smoke program's scheduled run (its entries and output digests) equals the Rust example's rows byte for byte (restated at implementation: the smoke's stimulus is the exactly representable square of spec 006's lesson, not a golden entry's); the meters across a mid-call route switch cover the whole call.
- **SC-004**: The log holds exactly one entry per applied change with the landed position, the chained values and the tag on every scenario of US2; the published length (67) is at least the largest per-call entry count over every scenario, and one scenario reaches exactly 64 scheduled changes plus one plain change per live control in a single call.
- **SC-005**: The per-sample cost at 48 kHz with an empty schedule is within 3 % of the 0.15 merge commit on the development machine (5 % on the CI runner); with one pending change per block the figure is reported.
- **SC-006**: Coverage stays at or above 80 % and within 1 point of the baseline (0.15: 97.69 % locally).

## Assumptions

- **D1 alternatives:** every control in `Settings` schedulable now (rejected: the record-side values need their own landing rules, a sensitivity step moves a decision per device sample, a hiss offset needs a ramp, and the owner's order puts them in 017); the speed accepted on the one-pass stream as a logged no-op (rejected: the control manifest's paths would lie or need a re-bless, and a change logged on one stream would move another stream's output).
- **D2 alternatives:** positions in input samples (the one-pass output is shorter than the input in drop mode, so an input position maps to no output sample during a pause; the events use output positions); positions in time (the host rate converts); one schedule for both streams (ambiguous when idle, and a session's playback changes could not be scheduled before `start_playback`). The playback clock counts the drain so that a change can be positioned anywhere the stream produces samples.
- **D3 alternatives:** applying a passed position never (refuse it) or at the requested position by rewinding (impossible); logging the setters that `start_playback`, `reset` and `reconfigure` consume at sample 0 of the first processing call (rejected: up to three entries at the start of every playback for values that are the stream's starting state, which the session snapshot of spec 020 carries). The "next sample" rule matches what a late UI event does today and the log records the truth.
- **D4 alternatives:** an unbounded schedule (allocation in the processing path or at the schedule call, breaking the real-time rule); a capacity setting (a C structure change without an app request); clearing at `start_playback` (prevents schedule-then-start); strict submission order (a later submission at an earlier position would wait and then count as passed). 64 holds a session's live changes and a scripted fade of 64 steps (1.28 s at one 20 ms transition per step); longer schedules are fed in order, refilled after each call while the pending count is below the capacity.
- **D5 alternatives:** a callback (the engine must not call the host); a pull after the call like the meters (a call applying several changes needs a list anyway; the events' form already exists in Rust and C); not logging plain setter changes (the log would miss the UI's changes and the timeline would be wrong); no tag (the app would match entries to its schedule by control, value and order, which breaks exactly where the engine's truth differs from the request); a one-bit origin instead of a tag (cheaper, but it cannot name a preset or a script step); logging per control reading instead of per stream (misses the one-pass transition after a playback's change, B2).
- **D6, D7:** the protocol of specs 011 – 013 (the idle A/B against the previous merge commit, the 45-run estimator, the runner ceiling, the `ab-timing` label). The per-sample lookup is one integer comparison against a cached earliest pending position (about 0.3 – 0.5 ns of about 73 ns at 48 kHz, the hardware review's estimate); the one-pass needs it per produced sample because output production is irregular under the voice activation.
- **D8 alternatives:** registering the convention as an assumption (rejected: the registers describe the device; a scheduling API describes the emulator, spec 010's clamp and spec 016's meters set the precedent); a size field on the C entry now (rejected for an array element the events' form lacks too; the entry is on the pre-1.0 ABI-pass list with the play report, so one pass fixes both).
- **D9 alternative:** deferring the counter reading to 020 with construct-at-counter. The reading is a getter with no structure change and lets an app record what a replay needs now; construction at a counter is a settings change, which belongs with the snapshot.
- The retarget rule of spec 011 (a retarget restarts from the knob at rest) stays; a scripted fade is a sequence of scheduled positions, each starting a 20 ms transition, and the "programmed fade" option is a later feature.
- The speed's d(P) rests on the playback conversion being causal (host sample n reads device samples up to ⌊n · 6000 ÷ rate⌋, spec 004), so d(P) is the inverse of the voice-activation events' position rule (spec 003 R-06); the plan publishes d(P) as a helper and the harness computes it independently.
