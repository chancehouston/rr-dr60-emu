# Research: Sample-Timed Control Changes and the Change Log (015)

Each entry: decision, rationale, alternatives. Code references are to `main` at the 0.15 merge (`f1449c2`). The spec's reviews (coach 1 – 18, hardware B1 – B10, product M1 – M9) are applied in the spec; the plan reviews of 2026-10-30 (coach 1 – 18, hardware P1 – P11, product M1 – M9) are applied here and recorded in plan.md.

## R-01: Where the clock, the schedule and the "last applied" values live

**Decision.** Each stream is a `PlaybackPath` (`paths.rs:832`: the one-pass's `one_pass.play` and the player's `player`), so the stream state lives there: `produced: u64` (the clock, D2), a `Schedule` of 64 entries (R-03), `next_apply: u64` (the cached earliest pending position, or 0 while a plain change is pending, `u64::MAX` when nothing is; R-09), the stream's last applied `route`, `volume` and (the player only) `speed_level` for the log's before field (D5), the pending plain change set at every processing call's entry from the engine's control values (today's `set_controls` and `speed.request` at entry, `pipeline.rs:683`, `transport.rs:465`, `:480`), a `landed` record of the last landed value per control for the call's epilogue (R-07), and a **staging log** of up to `MAX_CHANGES_PER_CALL` entries drained into the caller's buffer at the end of the call (R-06).

**Resets (hardware P3, coach 3).** `PlaybackPath::reset` (called by `start_playback`, `Pipeline::reset` and construction) zeroes the clock, the pending plain change, the staging log and `next_apply`, and **never touches the schedule**. Clearing is an explicit `PlaybackPath::clear_schedule()` called from `Pipeline::reset` (both paths), `reconfigure` (both paths are rebuilt), and on the playback stream by `play` when it sets `finished`, by `stop_playback`, by `erase` in the branch that sets `Idle` (`transport.rs:605`; not the renumbering branch) and by `erase_all` when it stopped a playback. So schedule-then-start works and a refused `start_playback` touches nothing.

**Rationale.** The three play-side objects that must agree (the clock, the chain the changes act on, the before values) are all reachable from the path; the one-pass and the player then share one implementation, and the player's `cursor.produced` (`transport.rs:154`) becomes the path's counter (the cursor keeps `total`).

**Alternatives.** The schedule on the `Pipeline` with a stream tag (rejected: the apply point is inside the path's host-sample production, R-02, and two streams would need two apply paths anyway); a separate `Stream` object the host holds (rejected: a second handle in C).

## R-02: One apply point per stream: the top of host sample `produced`

**Decision.** Every change lands at **one point per stream, keyed by the clock only**: when the stream is about to produce host sample `produced`, and `produced >= next_apply`, the path's cold `apply_due` runs: it takes the pending plain change (the chain pair, and on the player the level) and then pops every schedule entry with `position <= produced` in order; a chain entry calls `chain.set_controls` (R-05), a speed entry calls `speed.request` through a closure the player passes (the one-pass passes none: the speed is not on its stream); each applied change that moves the stream's own value is logged (R-06); then `next_apply = schedule.earliest()`.

**Where "about to produce" is** (hardware P1, coach 2): the one-pass's `tick` (`pipeline.rs:373`) has a front-tap branch that returns `rec.front_only(x)` without the resampler, so the apply point cannot sit inside `try_next_host`. `PlaybackPath` gets `next_wide() -> Option<f64>` (the resampler or the pending slot) and `emit(y) -> f32` (apply_due → the reconstruction peak → `chain.process` → `narrow_out`, `produced += 1`); `tick`'s normal branch calls `next_wide` then `emit`, and its front branch calls `apply_due` and `produced += 1` before returning its sample (the chain is inactive there and takes the position at once; the clock counts; the log is written; `stream_position` equals the produced count at every tap). In `play` (`transport.rs:522`) each host iteration runs `apply_due` first (before any pull for that sample), then the pull loop, then `emit`.

**The chain controls are bit-identical to 0.15** (FR-007; hardware P11, verified case by case): between a call's entry and the first `chain.process` nothing touches the chain (the one-pass runs `rec.push` → codec → `half.process` → `up.push_device`; the player `speed.next` → `push_device_f64`; the transition advances only inside `inner`'s `ramp_step`, `output.rs:447`; `fresh` changes only in `inner` and `reset`), so applying the plain pair at the first produced sample gives the same state at the first `process`; a route change at a boundary differs from 0.15 only in the accumulators, which are zero there (R-05); a fresh chain, stage 11 bypassed and an inactive chain take the position at once either way; a call that produces nothing (a zero-length call, a block the gate drops) applies nothing, and the chain is observed only through `process`, so the output is identical and only the log differs (the entry is reported by the call that produced the sample, plan F1). The plain pair always calls `chain.set_controls` as 0.15 did, whether or not it moves the stream (hardware P4: no idempotence argument is needed); the log entry is decided separately from the stream's last applied values.

**The speed needs no device-index apply point** (hardware P2, verified numerically at the seven rates): every `speed.next` is followed by exactly one `push_device_f64`, at most one pull happens per host sample (l ≤ m), after host P − 1 the pull count is exactly d(P) = ⌊(P − 1) · 6000 ÷ rate⌋ + 1 (d(0) = 0; the 6 kHz pending slot gives one pull per host sample), and the pull with index d(P) happens during host P or the first later host sample that pulls, never earlier; `speed.request` only writes `requested`, read by the next `next` (`speed.rs:192`, `:334`). So a request at the top of host sample P is the request "immediately before the `speed.next` with index d(P)", and it is exactly what the block-size-1 plain setter does (a request at the entry of the call producing P). A scheduled speed change is therefore logged at P and lands on device output d(P), which the guide and `changes::speed_landing` state; a change whose d(P) is never pulled (the last ⌈m ÷ l⌉ − 1 host samples before the total at the converting rates: 6 positions at 48 kHz, 13 at 88.2 kHz) is still applied (the request is made) and logged, with no `next` left to act on, as the spec's post-latch edge case says. The plain level is requested at the same point (the first produced sample's top; bit-identical to 0.15's entry request, no `next` runs between) and logged there, like the other two controls (coach 4; FR-004).

**Alternatives.** Splitting the caller's block at the positions and running the entry-time `set_controls` per sub-block (rejected: wrong on the one-pass, whose sub-block boundaries are input samples; and a route reset mid-block would still need the sections-only reset); the apply inside `try_next_host` (rejected: the front taps never reach it); a second apply point keyed by the device pull for the speed (rejected: a counter and a compare more, F2's special case, and the never-pulled hole).

## R-03: The schedule: a sorted inline array of 64

**Decision.** `Schedule { entries: [Entry; 64], len: u8, next_seq: u64 }`, `Entry { position: u64, seq: u64, value: f64, tag: u64, control: u32 }` (40 bytes; 2.5 KB per stream, inline); the schedule call validates (R-04), then inserts at the first index whose `(position, seq)` is greater (a memmove of at most 63 entries, bounded, no allocation); `earliest()` is a cached field (`entries[0].position` after every insert and pop, `u64::MAX` when empty), so the hot path reads one `u64`. A pop takes `entries[0]` and shifts (at most 64 per call). `seq` is `u64` (no wrap; hardware P9). Capacity `SCHEDULE_CAPACITY = 64` and `MAX_CHANGES_PER_CALL = 67` are published constants. The staging log is 67 × 40 bytes (2.6 KB); about 5 KB per stream in all (coach 9).

**Alternatives.** A binary heap (no gain at 64, and ties need a sequence anyway); a ring in submission order with a scan per sample (rejected: 64 comparisons per sample).

## R-04: Validation at the schedule call

**Decision.** `schedule_change(stream, position, control: u32, value: f64, tag)` validates in this order and stores nothing on a refusal: (1) the stream: `Stream::Record` or an unknown C value → `ReservedStream` (C status 28); (2) `control` is the control manifest's index of `route`, `volume` or `playback_speed` and the control's manifest paths include the stream (the speed on the one-pass fails here), else `ControlNotOnStream` (28); (3) the value: the volume is first checked finite, then **narrowed with `value as f32`** and validated as `set_volume` does (0 … 1), the narrowed value stored and the entry's `after` the stored `f32` widened (coach 6: a C or Swift double literal 0.1 must be accepted as `set_volume(0.1f)` is; the guide says the value is rounded to single precision); −0.0 is normalized to 0.0 (`+ 0.0`; hardware P9); the level must be integral 1 … 5 (`InvalidSpeedLevel`); the route integral 0 or 1 (`InvalidControlValue`, C `INVALID_ARGUMENT`); (4) on the one-pass stream a route value the configured named-route tap cannot read (`tap_on_route`'s rule, `pipeline.rs:562`) → `TapNotOnRoute` (spec B1); (5) `len == 64` → `ScheduleFull` (27). The call is accepted in every engine state. Equality in the log's same-value rules is numeric (`==`), not bitwise.

**Note (hardware P10):** a route change scheduled on the playback stream moves the shared reading at landing, so a one-pass configured with a named-route tap of the other route is then refused at its next `process`, exactly as after a plain `set_route`; the guide says so and an edge case tests it.

## R-05: The route switch and spec 016's accumulators

**Decision.** `OutputChain::reset` (`output.rs:499`) is split into `reset_sections` (what it does today minus the last two statements: `fresh`, `ramp_k`, the scalars, the knob, the six sections) and `reset` (sections plus `route_peak = 0`, `clamp_count = 0`: construction, `reset`, `reconfigure`, `start_playback`). `set_controls` calls `reset_sections` on a route change. Nothing else in the chain or the path is touched by a route switch (hardware P6, verified). Bit-identical at a block boundary because `finalize_into` had zeroed the accumulators in the previous non-empty call.

## R-06: The log: a staging buffer drained per call

**Decision.** Each path has `log: [ChangeEntry; 67]` and `log_len`; `apply_due` pushes an entry when the stream's own value moved (volume target or route; the player's requested level), or for any scheduled change (a scheduled no-op is pushed with `before == after`, FR-006), with `position` = `produced` (the host index about to be produced; for a scheduled change that is P, or the landing index of a passed position), `control`, `before` = the stream's last applied value, `after` = the applied value, `tag` (0 for a plain change). A plain change equal to the last applied is not pushed. At the end of the call the log-taking variant copies the first `min(log_len, buffer.len())` entries to the caller and the report's `changes` carries `log_len`; the plain variants fill `changes` too and discard the entries. `log_len` ≤ 67: at most 64 pops plus the plain route, volume and level.

**Alternatives.** Passing the caller's slice down the path (rejected: three signatures change); a pull API like the meters (rejected by D5).

## R-07: The plain setters, the lifecycle calls, the cross-stream entry and the readings

**Decision.** At every processing call's entry the stream's path records the pending plain change from the engine's readings (`route`, `volume`; the player also `speed_level`) and sets `next_apply = 0`; `apply_due` applies it at the first produced sample (`chain.set_controls`, `speed.request`, unconditionally) and logs it if it moves the stream's last applied values. `start_playback` (`transport.rs:418`) resets the player and sets its controls at once as today, then sets `last_applied = (route, volume, speed_level)` with no entry; `Pipeline::reset` and `reconfigure` do the same for the one-pass path. Consequences: a value set **or scheduled** on one stream reaches the other stream as a tag-0 change at its next producing call (the shared reading moved; spec B2, coach 14: the guide says so and the golden holds a scheduled-origin cross-stream entry); a setter made before `start_playback` is consumed without an entry (coach 6).

**The readings** (`route()`, `volume()`, `playback_speed()`) are the `Pipeline` fields: a plain setter writes them at once; for a scheduled change the path records `landed` (the **last** landed value per control in the call) and the call's epilogue writes the fields (hardware P7: nothing reads the fields during a call, so this equals writing them at the sample; an edge case pins one landed, two landed, one pending beyond the block). The `play` destructuring (`transport.rs:468`) may instead pass `&mut route/volume/speed_level` into the loop; either form.

## R-09: Cost

**Decision.** The hot path is **one predictable `u64` compare per produced sample per stream** (`produced >= next_apply`; `next_apply` is 0 after a call's entry while the plain change is pending, then the schedule's cached earliest position, `u64::MAX` when empty), `apply_due` being cold; nothing per device pull (R-02). Measured by `tests/changes_timing.rs` (the 0.15 API: a 4096-block playback and a one-pass at 48 kHz, speaker route, codec bypassed, fastest of 45 runs, printed as `playback_ns=` / `one_pass_ns=`), run in both builds by a new `changes` mode of `scripts/ab-timing.sh` (the `meters` mode's pattern: the test copied into the baseline tree, three alternations), asserting 3 % (`RR_DR60_CHANGES_COST_CEILING`, 0.05 on the label job); a second print with one change scheduled per block (`playback_pending_ns=`), reported.

**Measured (2026-10-30, solo A/B against `f1449c2`, this machine):** the player −0.09 ns (−0.33 %), the one-pass +0.68 ns (+0.95 %), one change per block +0.41 ns (+1.61 %) reported. Two earlier runs: +3.24 % on the one-pass with the off-by-one mutant's branch on the hot compare (folded into the cached position), then +2.33 % with the hot pair `produced` / `next_apply` 2.6 KB apart in the stream state (the `repr(C)` reorder of hardware review B1 put them in the first cache line).

## R-10: The golden and the C parity

**Decision.** `golden-changes-v1.json`: per entry the configuration, rate, stream, the schedule (positions, controls, values, tags), the block partition, the output digest (FNV-1a over the narrowed samples, as the codec golden's frame digest) and the full log with its f64 values written as shortest round-trip text (`{:?}`; hardware P9); the entries: the three controls at inside-block positions on both streams, two at one position, a passed position, a scheduled no-op, the plain setters (one per control), the cross-stream entry of both origins (a setter and a scheduled change on the other stream), a change in the drain, a speed change past the latch, 64 + 3 in one call (SC-004's tight bound); at the seven rates with `output_only_amp`-style and default configurations; blessed once. The C smoke gains `--changes`: it looks the three control indices up by identifier through `rr_dr60_control` (product M4), schedules one entry's changes, runs it and prints the log and the digest; diffed against `examples/changes_rows.rs`.

## R-13: The mutants

`ChangeMutation { apply_at_entry: bool (0.15's entry-time apply for the chain controls: caught by the partition identity), off_by_one_position: bool (lands at P + 1: caught by the splice identity), submission_order: bool (ignores position order: caught by AS8), log_reading_before: bool (before = the engine's reading, not the stream's: caught by the cross-stream entry), full_reset_on_route: bool (caught by AS9), speed_landing_ceiling: bool (the published d(P) written as ⌊P · 6000 ÷ rate⌋: caught by the place pin at 48 kHz, coach 17) }` behind `__test-hooks`.
