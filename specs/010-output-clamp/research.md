# Research: Optional Output Clamp (feature 010)

Each entry: decision, rationale, alternatives. IDs are cited from the plan, the data model, the contracts and the tasks. The coach's plan review (P1–P17) and the hardware reviewer's (D1–D10) of 2026-10-15 are applied throughout; the spec's Clarifications record the session.

## R-01 Where the clamp sits and the identity it must satisfy (FR-001, FR-003, FR-005)

**Decision.** The clamp is one gate on `OutputChain` (`stages/output.rs`): `clamp: bool`, set at construction as `settings.output.clamp_enabled && tap == Tap::RouteOutput`, where `tap` is the chain's return point (`RouteOutput` for the player, which is built with `honour_tap = false`; the configured tap for the one-pass), and `bound: f64`, in production always 1.0 (A-042: the route's full scale; a field only for the mutation hook, the `knee_start` pattern). `OutputChain::process` becomes a wrapper: today's body, including the `active` early return and the `AfterVolumeAmp` returns, moves into an inner function, and the wrapper applies the bound to `inner`'s result when the gate is set, so a bypassed chain at the route-output tap is still bounded (spec Edge Cases "Output chain bypassed"). The bound is a hand-written function, not `f64::clamp` (which asserts `min <= max` and passes NaN):

```rust
/// A-042: the route's full scale. NaN cannot reach it (the output is finite, 002 R-07); mapped
/// to 0.0 so the behaviour is defined (spec Edge Cases). −0.0 passes unchanged.
#[inline(always)]
fn bound(y: f64, b: f64) -> f64 {
    if y > b { b } else if y < -b { -b } else if y == y { y } else { 0.0 }
}
```

The per-stage taps (`AfterVolumeAmp`, `AfterSpeaker`, `AfterEarphone`) are never bounded because the gate is false for every tap but `RouteOutput`; `AfterPlayback` and every earlier tap never reach the chain's gate (at `AfterPlayback` the chain is constructed with `enabled = false` and the gate is false). **The play calls always return the route output** (the player ignores `settings.tap`), so with the option on they are always bounded, whatever tap the settings name; with `tap = AfterPlayback` the option is inert in the one-pass. Both sentences go into the `clamp_enabled` rustdoc, the C header and the README (D9). The player's and the one-pass's route-output sample both pass through `PlaybackPath::try_next_host → narrow_out(chain.process(y))`, which also serves the drain, so one gate covers every path (verified by the hardware reviewer).

**The identity holds exactly in `f32`.** The spec's oracle is `on == clamp(off)` on the narrowed output. `narrow_out` rounds to nearest, flushes `f32` subnormals (values far inside the bound) and saturates to ±`f32::MAX` (≥ 1 in magnitude); all three are weakly monotone and preserve "≥ 1" and "≤ −1", and ±1.0 are representable. For an `f64` sample x with |x| ≤ 1, `narrow(bound(x)) = narrow(x) = clamp(narrow(x))`; for x > 1, `narrow(bound(x)) = 1.0` and `narrow(x) ≥ 1.0`, so `clamp(narrow(x)) = 1.0`; symmetric below −1. The hardware reviewer fuzzed `narrow_out(x.clamp(−1, 1)) == narrow_out(x).clamp(−1, 1)` bit for bit over 2 × 10⁸ finite inputs (random bit patterns, ±1 ± ε, ±1e300, ±`f64::MAX`, `f32::MAX`·(1 + 1e−7), ±1e−40): zero failures. So bounding in `f64` before the narrowing and bounding the `f32` output afterwards give the same bits, and the harness computes the expected output from the option-off run with `f32::clamp`. A core unit test pins this on a vector that crosses the bound (including 1.0 + 2⁻⁶⁰, which narrows to 1.0 either way, and −0.0), plus ±∞ → ±1.0 and NaN → 0.0 through `bound` directly (the oracle's `f32::clamp` would give NaN for a NaN input, which is unreachable).

**Rationale.** One gate on an already-active path; no new state, so `reset`, `at_rest`, `runs_any` and `n_out` (the drain) are untouched: the bound is memoryless and cannot lengthen the chain's settle, and `derive_figures` reads only `runs_any()` and `n_out()`. The chain already owns the tap decision (`honour_tap`, `tap`), so the gate sits beside it (Complexity Tracking row 1).

**Alternatives.** The same bool in `PlaybackPath` applied after `narrow_out` (equally cheap, but FR-003's rule would then live in two types). A `ClampStage` struct like the ADC clamp (not a stage; a struct for one gate reads like one). `f64::clamp` (a `min <= max` assertion in the per-sample path once the bound is a field, and NaN passes through).

**As built (T017, T038 N3).** The function takes both ends, `bound(y, lo, hi)`, and is branchless: `let r = y.max(lo).min(hi); if y.is_nan() { 0.0 } else { r }` (IEEE maxNum / minNum return one operand exactly, so the identity proof stands and the result is bit-identical on every target; one instruction each on aarch64, a short branchless sequence on x86-64). The production ends are −1.0 and +1.0; the mutation hook moves `hi` (`clamp_bound`) or sets `lo = −∞` (`clamp_positive_only`), so there is no `positive_only` branch in the per-sample path. The first, two-branch form measured +3.6 ns per host sample (branch mispredictions at the 13.9 % bounded rate); the branchless one +0.33 ns.

## R-02 The settings field and the presets (FR-002, FR-008; clarify Q1)

**Decision.** `OutputSettings` gains `clamp_enabled: bool` (the fourth field; `#[non_exhaustive]`, so external literals were never possible; the crate's own literals are updated). `OutputSettings::DEVICE` sets it `false` (the device has no such bound) and `OutputSettings::BYPASSED` sets it `false` (0.8's output). `Default` stays `DEVICE`. No validation (a bool cannot be invalid). The rustdoc on the field, on `OutputSettings`, on `Tap::RouteOutput` and on the three per-stage taps carries the FR-003 sentence: with the option on, the route-output tap and the selected route's last per-stage tap (or `AfterPlayback` when the chain is bypassed) are no longer the same signal; and the player sentence of R-01.

**Rationale.** The spec's Q1: a static property of the host's output format, beside the three stage bypasses it modifies. The presets must both be `false` or `configs::settings_008` (built on `BYPASSED`) would change every pre-009 golden.

**Alternatives.** A field on `Settings` itself (it belongs to the output group it acts on). A control (deferred by the user; the controls discussion is queued).

## R-03 The C layout: 104 → 112 (FR-008; coach C3, P1; hardware D1; contracts/c-api.md)

**Decision.** `RrDr60Settings` holds `seed: u64`, so its alignment is **8** on all eight targets (which is why 0.9 has padding at 99–103). The struct gains three fields at the end: `reserved_010: [u8; 5]` at offsets 99 – 103 (the 0.9 layout's tail padding made explicit, written 0), `output_clamp_enabled: bool` at **104**, and `reserved_010_tail: [u8; 7]` at 105 – 111 (this layout's tail, explicit so that 0.11 can append at 112 and refuse 112). `size_of == 112`; `struct_size = 104` is refused by `check_struct_size` as `RR_DR60_STATUS_INVALID_ARGUMENT` (and by `rr_dr60_settings_validate` naming `RR_DR60_SETTING_FIELD_STRUCT_SIZE`), a compile-and-run break like 0.5, 0.6, 0.8 and 0.9. `rr_dr60_settings_default` fills 112 with the field `false` and both reserved fields zero. Three const assertions keep the tail honest: `size_of == 112`, `offset_of!(reserved_010_tail) + 7 == size_of`, `align_of == 8`. `RR_DR60_VERSION_MINOR` becomes 10. No new status, field enum value, tap or function.

**Rationale.** A `bool` appended alone lands at 99 and leaves the size at 104: a 0.9 caller's `struct_size = 104` would pass and byte 99 would be read as the option from uninitialized memory (CLAUDE.md's 009 lesson; coach C3). A 3-byte tail (the plan's first draft) leaves bytes 108–111 as implicit padding and repeats the problem one version later (both reviewers compiled it: 112 bytes with the planned fields).

**Alternatives.** Reusing `reserved_009` bytes (documented "write 0, ignored", not validated; the convention would be broken for the next field). A `uint32_t` flag word (the three bools set the convention).

**Findings.** (1) The primary stimulus exceeds the bound at every rate, as the spec claims by construction; at 6 kHz a 1 kHz tone has six samples per period and its sample peak is 1.5·sin 60° = 1.299 (four of six samples bounded), so the **count** is the figure to report there. (2) The three secondary stimuli exceed the bound at every rate: the precondition is answered (all of them, everywhere); the checks report the figures rather than tolerance them. (3) The earphone route's square-wave overshoot (1.37 – 1.52 chain-only; 1.04 – 1.07 in the default, where the limiter and the ADC clamp hold the input) comes from the coupling corners: the reviewer's standalone simulation of `VOL_HPF → EAR_IN → EAR_OUT` on the 6 kHz square reproduces 1.522 (1999) exactly; at the resampled rates the interpolator band-limits the square, hence 1.37. (4) The chain-only reference-position tone never exceeds the bound (0.88 – 0.97); the 0.9 default at the reference position is measured in Phase 1 for the sixth golden configuration (expected zero, by the clipper and the template's gain ≤ 1 on a steady tone). (5) A full-scale 1 kHz tone is **not** a non-overshooting case on the earphone configurations or with every stage bypassed at most rates (1.02 – 1.04; D2), so the spec's "one that does not overshoot" is the reference-position configuration, not that stimulus. (6) At position 1 the option replaces about 29 – 33 % of the samples on the speaker route (13858 / 48000 on the tone, 15832 / 48000 on the square): it is a second hard bound after the transducer template, flattening up to 6 dB of ringing, which adds odd-harmonic distortion the device has no stage for (D4); at the default position typical material is untouched.

**Decision.** The figures above go into `data-model.md` as the expected report and are re-printed by `output_clamp_matrix` with 1 s stimuli (so the counts reproduce), plus: the 0.9 default on both routes with all three golden stimuli, `tone_1k_0` on every golden configuration (the 18 stimulus × configuration cells), `voiced` at −1 dBFS and band-limited noise at −3 dBFS at the reference position (zero counts), a "% of samples bounded" column, and the L1 bound per rate **recomputed from the committed coefficients** by a harness helper (`analysis::impulse_l1` on the discrete sections, 2 s of impulse response) and pinned within ±0.02 of the table above, with every measured speaker-route peak asserted ≤ that bound (the 008 lesson: a design figure is pinned by a test that recomputes it). Assertions beyond the identity: the option-off peak exceeds 1.0 for the four overshooting stimuli at every rate, never for the reference-position configuration, and the speaker-route peaks never exceed the L1 bound.

## R-05 Stimuli and the golden file (FR-010; contracts/golden-format.md; coach P2, P15, P17; hardware D2)

**Decision.** `stimulus::square(freq_hz, amp, fs, len)` is a new helper: a half-period of `round(fs / (2·freq))` samples, starting at `+amp` (spec Key Entities), with a unit test of the rule. The golden file `golden-output-clamp-v1.json` holds 3 stimuli × 6 configurations × 7 rates = **126** entries: `sine_1k_1p5` (amplitude 1.5, 2 s), `square_1k_fs` (±1.0, 2 s), `tone_1k_0` (reused) × `output_clamp_only` (every stage bypassed, the clamp on, the speaker route), `output_only_speaker_clamp` (speaker, position 1), `output_only_earphone_clamp` (earphone, position 1), `default_output_clamp` (speaker, position 1), `default_earphone_clamp` (earphone, position 1), `default_output_ref_clamp` (speaker, `VOLUME_REFERENCE`: the non-overshooting case of FR-010, which is also US1 AS4). Every entry stores, beside the SHA, `n_at_bound`: the count of output samples exactly equal to ±1.0, bounded or already there (T038 N6), recomputed on every run (it needs no twin). **At bless time only** (`RR_DR60_BLESS=output_clamp`), the generator also asserts the identity against the configuration's option-off twin for every entry, that the twin of `default_output_ref_clamp` has zero samples beyond ±1.0 on the two tones at every rate (as built: the square reads 3 samples over at 96 kHz, T006), and record-then-play equals the one-pass for the three `default_*` configurations (spec 008 FR-009's rule); the identity is proven on every run by `us1_output_clamp` and `output_clamp_matrix`, so the compare path stays one one-pass per entry (the coverage job grew 29 → 39 min with 009's golden; this file costs about the same as `golden_output`). Blessed once, last, guarded by `GOLDEN_OUTPUT_CLAMP_V1_SHA256` in `tests/golden_output_clamp.rs`; the five earlier guards unmoved; CI runs it wherever the five run (`ci.yml` lines 81, 140, 152) and `scripts/ios-device-golden.sh` adds `--test golden_output --test golden_output_clamp` (closing 009's omission of `golden_output` there).

**Naming.** "Clamp" already names a device behaviour in this repository (the codec's full-scale clamp, A-030, `adc_clamp_enabled`, `record_only_clamp_off`), so every new name carries the `output_clamp` prefix: `OUTPUT_CLAMP_CONFIGS`, `output_clamp_only`, `generate_output_clamp`, `golden-output-clamp-v1.json`, `RR_DR60_BLESS=output_clamp`, the check module `output_clamp_checks.rs`, the tests `us1_output_clamp`, `output_clamp_matrix`, `output_clamp_edge_cases`, `golden_output_clamp`, `timing::output_clamp_cost`. A wording test for FR-004 searches the manifest for "output clamp" and `clamp_enabled`, never for "clamp" (stage 4's controls note carries `adc_clamp_enabled`).

**Rationale.** Every position-1 entry clamps something (R-04); the reference-position configuration is the deliberate non-overshooting case. Position 1 on the `default_*` configurations departs from 009's reference position so the limiter-held full-scale square still rings above the bound.

**Alternatives.** Appending entries to `golden-output-v1.json` (its guard is closed; FR-002). A quieter stimulus as the non-overshooting case (`tone_1k_m10`; the reference position is the user's default and doubles as AS4). Storing the twin's count (unverifiable at compare time without the twin run).

## R-06 The measurement harness (FR-003, FR-005, FR-006, FR-011; SC-001 – SC-004; US1 – US2; coach P3, P4, P11 – P14; hardware D5, D10)

**Decision.** A new module `output_clamp_checks.rs` with:
- `identity(make, rate, config, route, volume, stimulus)`: runs the option on and off, asserts `on[i] == off[i].clamp(-1.0, 1.0)` for every i (bit equality on the `f32`), returns rows with the option-off peak, the count beyond ±1.0, the percentage bounded and whether the option-on run contains a sample equal to a bound (required wherever the count is above 0).
- `per_stage_taps_unclamped(rate, route)`: the taps after stages 11, 12 (speaker) or 13 (earphone) bit-identical with the option on and off on **all three golden stimuli**; `AfterPlayback` with the chain bypassed likewise; and, with `bypass_all` plus the option on, every earlier tap (`AfterRecord`, `AfterAgc`, `AfterVas`, `AfterDecoder`, `AfterPlayback`) bit-identical to the option off on `sine_1k_1p5` with a peak above 1.0.
- `bypassed_chain_bounded(rate)`: the `output_clamp_only` configuration: the route output bounded, `AfterPlayback` above 1.0.
- `equivalence(rate, route, volume)`: `output_checks::chain_equivalence` through a configuration-name parameter (the function gains one; the 009 callers pass the old name) at the four named positions (speaker and earphone × `VOLUME_REFERENCE` and 1.0), with an assertion that at position 1.0 the option-off one-pass of the equivalence stimulus has at least one sample beyond ±1.0 at every rate (so the equivalence exercises the bound; coach P4).
- `change_timing(rate)`: 009's route and volume change schedule re-run on `square_1k_fs` at position 1 with the option on, asserting the option-on output equals `clamp(option-off output with the same schedule)` sample-wise at every change point.
- `stored_form_unchanged(rate, route)` (as built: on the full-scale square, which exceeds the bound at position 1 on both routes; the voiced stimulus never does in the default engine, T018): record it in `default_output_clamp` and in `default_output`; `split_checks::export_bytes` byte-identical between the two; then the option-off export imported into an option-on engine plays back as `clamp(option-off playback)` sample-wise (coach P3; FR-006).
- `latencies_and_drain_unchanged(rate)`: `output_checks::chain_latencies_unchanged` and `chain_drain_table` re-run with `default_output_clamp`, equal to the option-off figures.
- `l1_bound(rate)`: the speaker template's impulse-response L1 norm from the committed sections (R-04), pinned, and the measured speaker-route peaks asserted ≤ it.

Tests: `us1_output_clamp` (US1 and US2 at `measurement_rates()`; functions named `identity_*`, `taps_*`, `equivalence_*`, `change_timing_*`, `stored_form_*`, `latencies_*`), `output_clamp_matrix` (the seven-rate report: every row of R-04's tables plus the counts, the 18 cells, the quiet-material rows, the "% bounded" column and the L1 bound, 1 s stimuli, `all_rates()`), `output_clamp_edge_cases` (every spec edge case: the bound inclusive, ±∞ and NaN into `bound`, −0.0, volume 0, the bypassed chain, the taps, a route change mid-playback, reconfigure on and off, the play calls bounded whatever the tap), `golden_output_clamp`; extended: `determinism::output_clamp_partitions` (the six configurations partition-invariant and record-then-play), `alloc_free::output_clamp_cases`, `timing::output_clamp_cost` (R-08), `ffi_parity` (R-09), `us2_cross_check` (R-07), `mutation` (R-06 mutants below).

**Mutants** (`__test_hooks::OutputMutation` is a struct with a `Default`; it gains `clamp_bound: f64` (default 1.0) and `clamp_positive_only: bool` (default false), mirrored on `OutputChain` through `__mutate`): the bound at 0.5 and at 1 + 2⁻²³ each fail `identity` on `square_1k_fs` at 48 kHz; positive-only bounding fails it on the negative half-cycles. The structural mutant the hardware reviewer named (the bound placed inside the `!active` early return) is caught without a hook by `output_clamp_only`'s golden entries and `bypassed_chain_bounded`.

**Rationale.** The identity is the whole oracle (coach C5): it subsumes "no sample exceeds", "at least one equals", "inside the bound unchanged" and "no time behaviour", at every rate without rate-specific reasoning. Everything else is the 009 harness with the option on, plus the three checks the coach found missing (the stored form, the engaged equivalence, the change-timing identity).

## R-08 Cost (FR-007; SC-005; hardware D10)

**Decision.** `timing::output_clamp_cost` (release, `--ignored`): `default_output` with the codec bypassed at 48 kHz, 30 s of **full-scale noise at position 1** (so a large fraction of samples is replaced: the worst case if the compiler emits a branch rather than selects), 4096-sample blocks, the speaker route, the option on and off in **alternation**, five runs each, the **median** of each; assert `median_on − median_off ≤ 2.0 ns`; print both routes and the bounded fraction. Expected: `bound` is two compares and two selects per sample, under 1 ns at 48 kHz on this machine; the 009 figure for the chain is 68.2 ns per sample. Both runs execute the same machine code (a runtime bool), which suits a sub-2 ns delta.

**As built (PR #23's CI, 2026-10-16).** The assertion is the ratio, `100 × (on / off − 1) ≤ 3`, each side the fastest of nine alternating runs, and CI runs the timing tests one at a time. The fixed 2 ns failed on the x86-64 runner (+4.14 ns, +2.4 %): it is about twice as slow, and its IEEE max / min with NaN handling takes a few instructions where aarch64 takes one. Measured: +0.47 ns (+0.56 %) on the development machine, +4.25 ns (+2.46 %) on the runner.

**Rationale.** Coach C9: 3 % of the codec-bypassed cost is about 2 ns, inside the spread of best-of-five figures, so the spec states nanoseconds and a median of alternating runs. The assertion is a smoke bound; the quoted figure comes from a solo run.

## R-09 The smoke loop and parity (US4; contracts/c-api.md; coach P8)

**Decision.** `smoke.c` adds: two cases with the option on, a ±1.0 square wave (exactly representable; a half-period of 24 samples at 48 kHz) at position 1 on each route through record-then-play, hashed (FNV-1a 64) against two new pinned references `SMOKE_SPEAKER_CLAMP_HASH` and `SMOKE_EARPHONE_CLAMP_HASH` in `crates/rr_dr60_harness/src/smoke_reference.rs` (pinned by `ffi_parity::smoke_reference_hash_is_pinned`; mirrored as `RR_DR60_SMOKE_*_CLAMP_HASH` defines in `smoke.c`), with every output sample checked in C to lie within [−1, 1]; the same square with the option off on the speaker route checked to exceed 1.0 (the loop shows the option acting); `struct_size = 104` refused by `rr_dr60_create` with `RR_DR60_STATUS_INVALID_ARGUMENT` and by `rr_dr60_settings_validate` naming `RR_DR60_SETTING_FIELD_STRUCT_SIZE`. `configs::c_settings` maps `output.clamp_enabled` → `output_clamp_enabled`. `ffi_parity` gains `c_api_output_clamp_matches_rust_at_all_rates` (the six configurations, bit equality at the seven rates). The C header's tap docs (`RrDr60Tap`) carry the same sentences as the Rust taps (FR-003; the player sentence).

## R-10 Risks

- **The `!active` early return**: the one-pass's chain with `tap = RouteOutput` and every output stage bypassed returns `y` untouched today; the wrapper must apply the bound to `inner`'s result, or the "bypassed chain still bounded" edge case fails silently. `output_clamp_only`'s golden entries and `bypassed_chain_bounded` catch it.
- **The C layout**: any further field must keep the explicit-tail rule; the three const assertions enforce it from now on.
- **Harness struct literals** of `OutputSettings` inside the crate break on the new field; `#[non_exhaustive]` keeps external callers safe.
- **The canonical-text re-bless** moves `golden/manifest-v1.txt` in Phase 1; a second re-bless means a string moved, a defect under FR-004.
- **The documented figures are the model's**: A-010 (low) sets the size of the overshoot the option acts on, and the unmodeled A-032 cut-off would change the earphone figures; a real-unit capture changes the numbers in A-042 and the README, not the option's behaviour (the hardware reviewer's evidence gaps, ranked: the speaker template, the earphone cut-off, the clip ceiling as the speaker route's 1.0).
- **A sample-peak bound is not a true-peak bound**: later resampling or filtering by the host can exceed full scale again; documented (D7), not preventable here.
- **The timing assertion** can fail on a loaded runner; it is `--ignored` and release-only like the other timing tests.
- **The ×32767 statement** and the 0.42 headroom figure are documentation; the wording test checks their presence, the L1 test pins the figure behind 0.42.
